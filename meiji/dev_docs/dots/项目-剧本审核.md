# 项目-剧本（`script-review`，AI）

剧本本身是节点，剧本审核与按审核意见修改都是作用于剧本节点的任务，不另设独立节点。节点状态为 `script.node_state`，内容就是剧本正文（`script.body`）；剧本的有无即其数据状态，界面不展示状态标签。

**固定属性：**

- 误差时长：无
- 重试轮次：1（仅修改任务：修改与审核最多两轮）

## 任务一：审核剧本（`generate` / `regenerate`）

**触发：** 剧本模式导入剧本、创建项目后自动提交一次；之后在剧本卡片点「AI审核 / 重新审核」。自由创作没有剧本，不提交。

**步骤：**

1. 前置条件检查（程序）。
2. AI 审核剧本。通过 → 剧本节点已生成；未通过 → 剧本节点未通过，`node_state.reason` 为修改意见。不自动修改剧本。

重新审核不把上次的修改意见当作本次审核要求；公共执行意见作为补充要求。

## 任务二：按审核意见修改剧本（`revise`）

**触发：** 剧本节点未通过时，原因下方的「修改」按钮。携带未通过原因及公共执行意见。

**步骤：**

1. 前置条件检查（程序）。
2. 按审核意见修改剧本（AI）：多轮消息，assistant 为当前剧本，最后 user 为修改意见；返回修改后的完整剧本。
3. AI 审核剧本（审核修改后的剧本）。未通过时：
4. 第 1 轮修改剧本（AI，以上一稿和本轮审核原因为依据）。
5. 第 1 轮 AI 审核剧本。仍未通过则任务以未通过结束。

通过时写入新剧本，剧本节点已生成；两轮仍未通过时保存最后一稿，剧本节点未通过，原因为最后一轮审核意见。每次写入新剧本：`version` 加 1，更新 `updated_at`，`revision_history` 追加 `{timestamp, task_id, revision_notes: 修改意见}`；依据剧本正文的项目摘要与角色按依赖 hash 过期。已拆分的剧集不自动改写。

## 审核规则

1. 只评估剧本本身。
2. 剧情连续性：人物身份、时间线、地点、因果和事件推进是否前后一致；是否有无交代的跳跃、断裂、矛盾，或人物突然出现、消失。
3. 拍摄适配：能否用画面和对白呈现；是否大量依赖无法直观呈现的心理描写、抽象叙述或纯文字信息；场景、人物数量和特效需求是否明显超出短剧视频的常规制作范围。
4. 只报告能指出具体段落或情节的问题；剧本未写明的内容不算错误，除非造成剧情断裂。
5. 不通过时原因写成逐条、可执行的剧本修改意见。

审核返回结构：

```json
{ "是否通过": true, "原因": "" }
```

## 修改规则

1. 只改动修改意见涉及的段落及必要衔接，其余段落逐字保留，保持场次结构、格式与换行。
2. 不新增与修改意见无关的人物、情节或结局；不擅自改变结局与主要人物关系，除非意见明确要求。
3. 返回修改后的完整剧本全文，不附说明。

## 前置条件

1. 项目剧本正文非空。

## 界面

概要页剧本卡片即该节点：剧本文件名下方是公共节点状态 UI——按钮（AI审核 / 重新审核、人工放行〔仅未通过〕、取消、任务历史）与最新任务同一排，然后是本次执行意见、失败原因、未通过原因，未通过时原因下方单独一排为「修改」。不展示状态标签、剧本版本和审核说明。不提供人工编辑和原结果修订。

## 人工放行

仅未通过时。只要求剧本正文非空，不再审核；成功后剧本节点已生成，原因清空。

## 依赖与对下游的拦截

- 依赖 `script.body`；剧本正文变化使剧本节点过期。
- [项目-提取剧集](项目-提取剧集.md) 与 [项目-剧本重要角色](项目-剧本重要角色.md) 在各自前置条件通过后，要求剧本节点已生成且未过期：未通过时提示“剧本审核未通过：<原因>。请在剧本上按审核意见修改，或人工放行”；未审核提示“请先完成剧本审核”；过期提示“剧本已变化，请重新审核剧本”。被拦截的任务以失败结束，不调用模型。项目摘要不受拦截。
