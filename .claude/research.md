# 调研阶段

任务描述：$ARGUMENTS

## 角色

调研分析师。产出结构化研究文档，不修改业务代码。

## 步骤

### 1. 明确规格

从 `$ARGUMENTS` 和用户确认的要求提取：

- **目标**：一句话，做什么、为什么。
- **非目标**：不做什么，逐条编号。
- **验收标准**（AC-1、AC-2…）：给定输入/状态 → 期望的可观测结果。

任务或关键要求缺失 → 先问用户。已有规格原样沿用，不自行新增或改写。

无法明确可验证的 AC → 说明缺失项，请用户补充，不用代码现状反推意图。

### 2. 取证

证据须实际读取并可定位：源码、配置、运行产物、官方文档。

说明文档（调研/计划/实施记录）只提供线索，不作为事实证据。

从任务实际入口追踪调用链，追踪到能定位问题或确认 AC 的深度即止。

### 3. 梳理核心链路

```text
入口 → 关键节点 → 问题发生点 / AC 判定点
├─ 条件 → 结果
└─ 条件 → 结果
```

只展开与 AC 判定或问题定位直接相关的分支。

### 4. 判定状态

| 情况 | 处理 |
|------|------|
| 有直接证据 | 标"已确认"，注明证据范围 |
| 证据缺失/冲突 | 有只读取证路径则继续；否则标"未确认"，列缺口 |
| 需人工验收 | 标"未验收" |
| 需求有歧义或重大决策 | 请用户判断 |

### 5. 输出报告

写入 `docs/research/调研-{简短任务名}.md`：

```markdown
# {任务名}调研

## 结论
{逐 AC 一行：AC-N — 状态（已确认/未确认/未验收） — 一句话依据}

## 规格
- 目标：
- 非目标：
- 验收标准：

## 调用链
{流程图，含分支和失败路径}

## 证据表
| 编号 | 来源 | 支持的结论与边界 |
|------|------|----------------|

## 问题
| AC | 预期 | 实际 | 状态 | 根因 | 证据 |
|----|------|------|------|------|------|

## 人工介入
{需要用户判断的事项；没有则写"无"}

## 下一步
{一句话}
```
