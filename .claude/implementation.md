# 实施与验证规范

## 1. 实施前

开始修改前确认：

- 当前目录、真实 Git 根目录和目标分支。
- 工作区已有改动，不覆盖、不清理、不暂存无关内容。
- 需求、非目标和验收方式明确。
- 实际执行路径已经定位。
- 涉及契约或多模块职责时，已有确认的设计。
- 涉及性能或质量结论时，已有实验方案。

## 2. 实施原则

- 每行改动都能追溯到需求、设计决策或验证需要。
- 修复真实断点，不在上层增加判断掩盖断点。
- 同类入口共享同一断点时一次修全，并用测试覆盖。
- 不顺手重构、改名、格式化或清理历史代码。
- 不为一次性需求增加抽象层或配置项。
- 只清理本次改动产生的无用代码。
- 公共契约变化必须同步调用方、测试和文档。

## 3. 实施顺序

1. 建立或确认能暴露问题的验证方式。
2. 修改最靠近根因的最小代码范围。
3. 运行聚焦验证，确认原问题已解决。
4. 运行受影响模块的回归验证。
5. 对照设计检查实际行为和失败行为。
6. 更新相关文档、勘误和未决项。
7. 检查最终 diff，只保留可追溯改动。

## 4. 验证层级

| 层级 | 目标 | 示例 |
| --- | --- | --- |
| 静态检查 | 格式、schema、依赖和职责边界 | lint、schema check、架构约束测试 |
| 单元验证 | 核心分支与失败行为 | 单元测试、夹具断言 |
| 集成验证 | 模块间契约真实连通 | API、队列、持久化、工具调用 |
| 实机验证 | 外部服务、模型和产物符合预期 | 真实任务、产物检查、性能采样 |

验证强度与风险匹配。外部依赖未运行时，不得用单元测试结果代替实机结论。

## 5. 偏差处理

实施与设计不一致时停止扩写，记录：

| 项目 | 内容 |
| --- | --- |
| 原设计 | 原先预期的行为 |
| 新证据 | 实施中发现的事实 |
| 影响 | 对契约、范围和验收的影响 |
| 建议 | 修改设计、缩小范围或补充调研 |

未经确认，不得把重大设计偏差直接固化进代码。

## 6. 实施记录模板

```markdown

> 状态：实施中 / 待验收 / 已完成 / 已暂停
> 对应设计：<路径或“不涉及”>
> 基线：<提交、版本或日期>

## 0. 结果

- 未完成：

- ...
```

## 7. 交付报告

对用户的最终改动报告只包含：

1. 改了什么文件。
2. 每个文件改了什么。
3. 如何验证以及验证结果。

不要用计划代替结果，也不要把未运行的验证写成已通过。

## 8. 完成检查

- [ ] 原始问题能够被验证，修复后结果符合预期。
- [ ] 关键失败路径有明确行为。
- [ ] 没有覆盖用户已有改动。
- [ ] 最终 diff 不含无关格式、命名或重构。
- [ ] 测试结果与实机结果没有混淆。
- [ ] 相关设计、契约和运行文档已经同步。
- [ ] 未验证范围已在交付报告中说明。
