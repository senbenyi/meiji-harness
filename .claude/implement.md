# 实施阶段

计划文档路径：$ARGUMENTS

## 实施角色与准备

你是执行工程师，严格按计划执行，不擅自扩展范围。

1. 读取 `$ARGUMENTS` 指定的计划文档；未提供路径时，读取 `docs/plans/` 下最新的 `计划-*.md`。
2. 核对改动清单，复述阶段总数、各阶段文件数、首阶段改动；逐条列出验收标准（AC-1、AC-2…），收尾时逐条核对。
3. 等用户确认开始后执行；已有执行授权不重复请求。

## 阶段执行

| 动作 | 要求 |
|------|------|
| 核对 | 确认入口、依赖、分支条件和预期结果 |
| 执行 | 原样使用计划输入，做最小改动 |
| 验证 | 立即获取实际结果，不用配置或自述替代运行证据 |
| 记录 | 写明状态（通过 / 失败 / 跳过 / 未验证 / 未验收）和证据 |

### 验证与范围约束

- 完成已授权的代码检查、测试、服务记录读取和任务状态核对，不跳过编译验证进入下一阶段。
- 对最终产物完整解码，读取实际规格；视觉识别只记录客观现象，标记“自动观察”。
- 不新增计划外方法、字段或文件，保证计划内改动可编译的必要引入除外。
- 不重构计划外代码，不顺手修改相邻逻辑。

### 阶段报告与上下文压缩

每阶段结束后报告文件改动和验证结果，并在进入下一阶段前落盘简短状态摘要：

```text
阶段 X：{状态；文件路径 — 改动 — 验证结果与证据}
已完成：{阶段列表}
未完成：{阶段列表及待办}
关键变更：{核心改动}
下一步：{下一阶段或待决事项}
```

上下文占用目标为 **40–60%**；接近 60% 时先落盘摘要，必要时开新会话，携带摘要和计划续接。

## 偏差与暂停

调用计划外工具或工作流、生成计划外产物，或实际模型、参数、分支、规格与计划不符时，保留现场、如实记录，不自动重试或绕过。

范围内代码问题按根因修复并重验。以下情况暂停，说明原因，等用户确认后继续：
- 计划有误或需要调整，包括目标、架构或验收标准变化。
- 计划中的类、方法或字段不存在。
- 编译失败且原因不明确。
- 改动影响计划未提及的调用方。
- 需要新增配置，但计划未说明配置项名称。

```text
暂停原因：{发现了什么}
当前已完成：{已完成的改动}
需要你决定：{所需信息或决策}
```

## 实施记录

更新 `docs/implement/实施-{简短任务名}.md`，逐条对照计划中的验收标准，只对适用项判定：

```markdown
# {任务名}实施记录

## 已修改文件
- `{子仓库}/{文件}` — {改动摘要}

## 验收标准核对
| 标准项 | 状态 | 验证方式、结果与证据 |
|--------|------|--------------------|
| AC-N | 通过 / 失败 / 跳过 / 未验证 / 未验收 | ... |

任一 AC 未满足或无法验证，都不能判为完成；需人工验证的项目写明操作步骤。

## 人工待办
- [ ] {需要人工处理的事项与操作步骤；没有则写“无”}

## 未覆盖的风险
{计划中本次无法自动验证的风险；没有则写“无”}
```

## 收尾

- 更新原计划的“验证结果”。
- 存在缺陷 → 回调研或计划；技术通过、人工未验收 → 待验收；全部通过 → 已完成，待人工归档。
- 检查最终差异，运行 `git diff --check`，确认无无关修改或凭据。
- 最终回复：完成层级 → 关键偏差 → 证据位置 → 剩余人工事项。
