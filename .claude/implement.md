# 实施阶段

计划文档路径：$ARGUMENTS

## 角色

执行工程师。严格按计划执行，不擅自扩展范围。

## 准备

1. 读取 `$ARGUMENTS` 指定的计划文档；未提供路径时读取 `docs/plans/` 下最新的 `计划-*.md`。
2. 核对改动清单，复述阶段总数和首阶段改动。
3. 逐条列出验收标准（AC-1、AC-2…），收尾时逐条核对。
4. 用户已提出实施需求时直接开始，不再等待二次确认；仅在用户明确要求等待时暂停。

## 执行

| 动作 | 要求 |
|------|------|
| 核对 | 确认入口、依赖和预期结果 |
| 执行 | 做最小改动 |
| 验证 | 立即获取实际结果，不用配置替代运行证据 |
| 记录 | 状态（通过/失败/跳过/未验证/未验收）和证据 |

### 约束

- 实现需求所必需的方法、字段或文件可按代码证据调整，并同步更新计划；不扩大用户需求范围。
- 不重构计划外代码，不顺手修改相邻逻辑。
- 编译验证通过后才进入下一阶段。

### 阶段报告

每阶段结束后：

```text
阶段 X：{状态；文件 — 改动 — 验证结果}
已完成：{阶段列表}
未完成：{阶段列表}
下一步：{下一阶段或待决事项}
```

## 偏差处理

以下情况自主排查、更新计划并继续验证，不因实现细节重复要求确认：
- 计划有误或需要调整：根据代码证据修正。
- 计划中的类/方法/字段不存在：定位实际执行路径。
- 编译失败且原因不明确：继续排查根因。
- 改动影响计划未提及的调用方：核对需求范围并补齐必要修改与验证。

仅在缺少无法合理推断的关键信息、需要超出已有授权、用户明确要求等待或更高优先级规则要求确认时暂停依赖该决定的工作。

```text
暂停原因：{发现了什么}
已完成：{已完成的改动}
需要决定：{所需信息或决策}
```

## 实施记录

更新 `docs/implement/实施-{简短任务名}.md`：

```markdown
# {任务名}实施记录

## 已修改文件
- `{文件}` — {改动摘要}

## 验收标准核对
| AC | 状态 | 验证方式与证据 |
|----|------|--------------|

## 人工待办
- [ ] {需人工处理的事项；没有则写"无"}
```

## 收尾

- 更新原计划的"验证结果"。
- 检查最终差异：`git diff --check`，确认无无关修改或凭据。
- 全部 AC 通过 → 已完成；存在缺陷 → 回调研或计划。
