# 工程文档规范入口

本目录只保存从项目作者现有文档中逆向归纳出的工程规范，不保存项目进度、临时结论或具体业务状态。

这些规则复现的是可观察的产出标准，不声称还原作者未公开的提示词、模型或工作方式。

## 1. 文件职责

| 文件 | 职责 | 何时读取 |
| --- | --- | --- |
| `documentation-standard.md` | 所有工程文档共同遵守的证据、结构和写作规范 | 任何文档任务开始前 |
| `research.md` | 调研、技术选型、可行性分析和源码走查 | 尚未确定事实或方案时 |
| `design.md` | 架构、接口、契约、迁移和方案定稿 | 已掌握现状，需要作决策时 |
| `experiment.md` | Benchmark、A/B、质量与性能实验 | 结论依赖实测时 |
| `implementation.md` | 实施、验证、偏差和交付记录 | 修改代码、配置或运行环境时 |

只读取与当前任务有关的阶段文件；不得把模板中的可选章节机械地填满。

## 2. 标准工作流

```text
明确问题与边界
  → 读取当前实现和运行状态
  → 区分事实、推断与未知
  → 必要时形成调研报告
  → 必要时形成设计或契约
  → 实施最小改动
  → 用测试或实验验证
  → 回填文档、勘误和未决项
```

以下条件未满足时，不得进入下一阶段：

1. 调研转设计：实际执行路径已经定位，关键未知项已列出。
2. 设计转实施：职责、接口、取舍、失败行为和验收方式已经明确。
3. 实施转完成：验证已运行，结果已记录，文档与当前实现一致。

## 3. 统一判定词

- **已确认**：由当前代码、配置、官方资料或本次实测直接支持。
- **推断**：由已确认事实推导，但尚未直接验证。
- **未确认**：缺少足够证据，不能写成事实。
- **已否决**：已经评估且有明确否决理由的路线。
- **已推翻**：旧结论被新证据推翻，必须保留勘误说明。

## 4. 硬约束

- 结论先行，但结论不得先于证据形成。
- 当前实现、目标设计和未来建议必须分开书写。
- 数字必须带环境、口径或来源；没有口径的数字不得用于决策。
- 不把计划写成完成，不把能编译写成已验收，不把理论收益写成实测收益。
- 不静默删除失败记录、旧结论或已知限制；使用勘误说明变化。
- 文档必须能指导下一步行动，不能只复述背景。
- 每项实现改动都必须能追溯到已确认需求或设计决策。

## 5. 完成定义

一项工程任务只有同时满足以下条件才算完成：

- 文档描述与当前代码、配置和运行结果一致。
- 关键结论有可定位的证据。
- 验证命令、环境和结果可复查。
- 风险、未测范围和未决项没有被隐藏。
- 新证据推翻旧判断时，相关文档均已同步勘误。
