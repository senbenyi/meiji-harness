# 短剧真实生产流程系统缺陷与链路断层分析

> 状态：已完成事故分析；2026-10-02 已实施第一阶段根因修复并通过测试
> 基线：`dsh-short-video-studio` 1.8.2，Git `83a11be`，2026-10-02，本机 DSH Web + Elysium 私有模型网关 + 私有 ComfyUI
> 范围：插件安装、模型路由、项目数据、H3 提示词、参考资产、视频生成、审核、拼接、验收、Canvas 交付与 Harness 轨迹。本文不评价模型本身的画面审美质量，也不把临时生成的成片视为架构修复已经完成。

> **勘误（2026-10-02）**：进一步检查 `runRender()` 实际执行路径后确认，Canvas 生成入口已经创建 Generation Attempt 并登记 candidate asset，并非完全绕过 Project Domain；准确缺口是生成后的人工审核、批准、timeline 与 delivery 没有在本次对话流程中形成闭环。本文相关表述已按这一边界理解。

## 0. 结论

- 本次事故不是单个 FFmpeg 参数错误，而是生产系统缺少一条贯通的交付契约。计划时长、生成参数、实际媒体、审核状态和 Canvas 节点分别存在，却没有由同一状态机保证一致。
- 最核心的系统缺陷是没有“真实生产编排器”和“交付门禁”。当前主要依赖模型在对话中手工调工具、保存 node ID、解释结果并决定下一步，因此模型的文字判断事实上代替了系统状态。
- 最核心的设计缺陷是把 `shot.duration` 等计划字段当成成片事实，又把 `video_concat` 这种硬切工具当成 episode 交付能力。计划正确不代表媒体正确，文件存在也不代表交付合格。
- 最核心的流程缺陷是先执行高成本 GPU 生成，再发现提示词、参考资产和时长契约不满足；生成之后又没有强制经过实际媒体探测、审核、批准、组装、交付验收和发布回读。
- 当前实现并非全部错误。项目领域已经具备 attempt、review、approval、timeline、失效传播和恢复等基础设计；H3 skill、工作流注册、ComfyUI 幂等线索、Canvas 路径保护和 FFmpeg 参数数组化也都是合理基础。问题是快捷生成路径绕开了这些基础能力。
- 继续重复生成不能解决问题。应先把 Prompt 编译、媒体事实、审核状态、目标时长组装和 Canvas 原子发布连成一个确定性管线，再做一次受控的端到端验收。

## 1. 问题与判定标准

### 1.1 要回答的问题

1. 为什么一个项目的两集分镜都校验为 60 秒，真实成片却只有约 52.697 秒？
2. 为什么轨迹多次报告“已经验证”“已经更新”，随后又发现时长或节点路径仍不正确？
3. 为什么已经存在 H3 skill、Project Domain 和审核状态机，真实执行仍然依赖临时 prompt 改写与 Shell 修补？
4. 哪些问题属于系统能力缺失，哪些属于抽象或契约设计错误，哪些属于执行流程错误？
5. 当前有哪些设计可以保留，根治时不应推倒重来？

### 1.2 成功条件

一个真实生产任务只有同时满足以下条件才算完成：

1. 使用明确且经过预检的私有模型与 ComfyUI 路由。
2. 每个镜头的 prompt、引用资产、生成模式和媒体约束在提交 GPU 前有效。
3. 生成产物经过实际媒体探测，计划值和实际值分开保存。
4. 镜头经过可追溯的审核与批准，未批准资产不能进入成片。
5. episode 按显式时长策略组装，音视频同步且目标时长在允许误差内。
6. 技术验收和最低限度视觉验收均通过。
7. 文件、Canvas 节点和资产库元数据原子发布，发布后重新读取仍一致。
8. 最终成功结论来自机器可验证的交付门禁，而不是模型文字陈述。

### 1.3 非目标

- 本文不讨论如何提升人物美术风格或剧情质量。
- 本文不把所有宿主能力都迁入插件。
- 本文不建议用更多重试掩盖契约错误。
- 本文不把某次手工 FFmpeg 命令成功视为正式生产能力已经具备。

## 4. 系统缺陷

系统缺陷指运行系统缺少必要能力，即使操作者完全按说明操作，也无法稳定保证正确交付。

### 4.1 缺少真实生产编排器

当前没有一个系统组件负责从 episode 计划一路推进到交付完成。实际编排者是对话模型：模型读取节点、记住 ID、分批调用工具、判断是否继续，再用文字汇报结果。

这造成四个后果：

- 状态主要存在对话上下文中，而不是持久化状态机中。
- 中断恢复依赖模型重新理解轨迹。
- 工具成功与业务成功容易混淆。
- 轮次和 token 消耗随镜头数线性甚至超线性增长。

### 4.2 缺少统一交付门禁

系统没有一个权威函数同时验证：

- 实际时长；
- 音视频流；
- 分辨率和帧数；
- 黑帧、冻结帧和静音；
- 镜头顺序；
- 审批状态；
- Canvas 路径和文件 hash；
- episode 与完整片之间的来源关系。

因此“文件生成”“工具退出码为零”“ffprobe 某些字段正常”都可能被错误提升为“成片合格”。

### 4.3 缺少媒体事实回写

生成结束后，真实 duration、fps、frames、streams 和 hash 没有成为 Project Asset 的权威字段。后续 timeline 只能继续依赖计划值或临时探测结果。

计划数据和媒体事实没有统一，正是 60 秒计划得到 52.697 秒成片而校验仍通过的直接系统原因。

### 4.4 缺少原子发布

正式媒体文件、Canvas 节点、资产库索引和替代关系可以分别成功或失败。0 字节文件、新文件存在但节点仍指向旧路径，都属于缺少事务边界的表现。

正确发布至少需要：

```text
写临时文件
  → 探测和验收
  → 写入带 expected revision 的节点元数据
  → 原子替换正式文件/节点
  → 回读验证
  → 标记旧产物 superseded
```

### 4.5 缺少部署一致性校验

插件管理依赖包版本，而本地 `file:` 开发场景中源码可以变化、版本不变。系统没有比较：

- 工作区源码指纹；
- profile 安装副本指纹；
- 实际加载入口；
- 关键文件清单。

这会使开发者误以为已经重新安装，实际仍运行旧代码。

### 4.6 审计日志能力不足

普通 Web 日志为空，完整轨迹主要通过 UI 查看，工具参数和结果还可能被截断。系统缺少可离线查询的结构化操作日志，不能可靠计算每个阶段的耗时、失败类别、重试次数和重复计费风险。

## 5. 设计缺陷

设计缺陷指系统拥有相关组件，但职责划分、抽象或契约定义不正确。

### 5.1 把计划时长与实际时长混为一谈

`shot.duration` 表达的是创作计划，媒体文件的 duration 表达的是生成事实。这两个字段不应共享一个语义，更不能用前者验证后者。

应明确区分：

| 字段 | 含义 | 产生阶段 |
| --- | --- | --- |
| `plannedDuration` | 剧作和剪辑目标 | 分镜规划 |
| `requestedFrames` / `requestedFps` | 工作流请求参数 | Prompt/Workflow 编译 |
| `actualDuration` | ffprobe 实测媒体时长 | 生成完成 |
| `deliveryDuration` | 组装后实测时长 | Episode 交付 |

### 5.2 Prompt skill 与 Prompt compiler 职责割裂

H3 skill 已经清楚定义 Ref2VA 六段式，但正式编译器不知道该结构。结果是规范存在于说明层，执行层只做字符串拼接。

正确设计应当是：skill 解释创作规则，compiler 负责确定性地产出和校验结构。不能让第一次 GPU 调用充当 prompt 单元测试。

### 5.3 `video_concat` 抽象级别错误

硬切拼接是文件操作；“生成一集 60 秒成片”是业务操作。当前上层把前者当成后者，工具名和使用方式掩盖了能力边界。

合理拆分应是：

- `concatMedia`：仅按顺序拼接兼容媒体；
- `conformTimeline`：按照目标时长和策略处理 PTS、帧率、音频 tempo；
- `deliverEpisode`：组装、探测、验收和发布。

### 5.4 裸 node ID 缺少语义

`ref_nodes: string[]` 只能证明节点存在，不能证明它扮演什么角色。现代博物馆场景被映射成长安城墙就是这一抽象的直接后果。

引用至少应包含：

```json
{
  "nodeId": "...",
  "role": "location",
  "entityId": "museum-restoration-studio",
  "required": true
}
```

### 5.5 Canvas 快捷工具绕过领域模型

Project Domain 已经设计 attempt、candidate asset、review、approval 和 timeline，但 `comfy_generate_video` 可以直接生成 Canvas 节点。快捷路径没有被限制为实验用途，也没有自动同步到领域状态。

这造成同一个媒体在 Canvas 中是 `ready`，在项目领域中却可能没有 attempt、review 或 approved asset。

### 5.6 “validate”概念过于宽泛

`studio_shotlist_validate` 检查的是计划表结构，却被使用者理解为生产完成校验。名称和输出没有明确声明验证层级。

应拆分为：

- `validatePlan`
- `validateGenerationInputs`
- `validateGeneratedAssets`
- `validateDelivery`

每一级只对自己的事实负责。

### 5.7 状态投影存在多个事实来源

项目报告称 `dialogue-led / 60 秒`，Canvas projection 却返回 `native / 0`。这不是显示问题，而是数据所有权不明确。

正确设计应指定一个 canonical production spec，其他 projection 只能从它派生，不能持有独立可漂移副本。

## 6. 流程缺陷

流程缺陷指现有能力的调用顺序、检查点或操作纪律错误。

### 6.1 高成本操作前没有全量预检

正确顺序应当先验证全部 16 镜的：

- 模型路由；
- 工作流可用性；
- H3 prompt 结构；
- 引用资产是否存在且语义匹配；
- 计划时长与模型能力是否兼容；
- 输出尺寸、帧率和音频模式。

本次却在生成第一个视频时才发现 prompt 不合格。

### 6.2 缺失资产没有阻断流程

“博物馆修复工作室”参考资产未生成，流程没有失败，而是把长安城墙节点命名为 `museum_studio` 继续执行。这属于输入不完整时的静默降级，且降级改变了创作语义。

### 6.3 没有真正逐镜审核

工具返回媒体文件后，流程就继续生成下一镜。轨迹没有形成 16 个镜头分别通过技术检查、视觉连续性检查和批准的证据。

“生成成功”只能说明 ComfyUI 返回文件，不能说明镜头可用。

### 6.4 拼接后先宣告完成，后做独立验证

验证应是成功状态的前置条件。本次顺序相反：先报告完成，再由外部 ffprobe 发现时长错误。

这说明流程中的完成态由模型触发，而不是由 validator 触发。

### 6.5 修复过程直接操作正式输出

FFmpeg 调参阶段产生过 0 字节文件。如果正式路径在验证前可见，任何下游读取都可能拿到损坏产物。

所有转码和组装都应写入临时路径，通过验证后原子发布。

### 6.6 节点更新后没有立即以回读为准

流程先说“画布节点已更新”，之后读取才发现仍指向旧文件。正确顺序是写入、读取、对比 path/hash/revision，全部一致后才能输出成功报告。

### 6.7 轨迹存在无效调度动作

轨迹中出现使用 Bash `node -e` “保存 node ID”但没有真正持久化的动作，以及大量“继续生成剩余镜头”的模型轮次。这些动作增加 token、认知和中断风险，却没有增加系统状态的确定性。

## 7. 关键链路断层

### 7.1 配置断层

```text
用户指定 Elysium
  ✕
会话默认 provider route
  ✕
插件工作流能力配置
```

表现：首次调用仍走 `deepseek-official`。

缺失契约：一次生产运行必须绑定不可静默回退的 provider/model/base URL 快照。

### 7.2 计划到生成断层

```text
shot.duration = 6–9 秒
  ✕
workflow frames / fps
  → H3 固定输出约 6.587 秒
```

表现：计划总长 60 秒，实际总长约 52.697 秒。

缺失契约：计划时长必须在编译期映射为模型支持的生成或后期 conform 策略。

### 7.3 Prompt 规范到执行断层

```text
H3 skill 六段式规范
  ✕
compilePromptSnapshot 字符串拼接
  → 首次 GPU 提交失败
```

缺失契约：Prompt IR 应是正式、可测试的编译产物。

### 7.4 参考资产到镜头语义断层

```text
节点 ID 存在
  ≠
节点语义与镜头角色匹配
```

表现：现代修复室错误引用长安城墙。

缺失契约：引用必须包含角色、实体和适用范围。

### 7.5 生成产物到项目状态断层

```text
Canvas video node ready
  ✕
Generation Attempt completed
  ✕
Review approved
  ✕
Timeline assembled
```

表现：文件存在，但项目领域缺少完整生产证据。

缺失契约：快捷生成结果必须进入统一资产生命周期。

### 7.6 组装结果到交付断层

```text
video_concat 成功
  ≠
episode 达到目标时长
  ≠
episode 通过交付验收
```

表现：52.697 秒成片被报告为 60 秒完成。

缺失契约：组装必须输出可被 delivery validator 验证的 manifest。

### 7.7 文件到 Canvas 状态断层

```text
新 MP4 存在
  ✕
Canvas node path 更新
  ✕
资产库索引更新
  ✕
旧节点失效
```

表现：新文件存在，节点回读仍指向旧文件。

缺失契约：文件和节点必须以单个发布事务对外可见。

### 7.8 执行轨迹到审计断层

```text
UI 中可见部分轨迹
  ✕
结构化持久日志
  ✕
可查询的成本与失败统计
```

表现：`web.log` 为空，UI 内容截断后无法完整离线复盘。

缺失契约：每个生产操作必须有 operation/attempt ID 和结构化事件。

## 8. 当前合理的设计

根治不意味着推倒重来。以下基础设计合理，应继续使用。

### 8.1 Project Domain 的状态模型方向正确

仓库已有 generation attempt、review task、approved asset、timeline、依赖失效和 recovery。它们已经覆盖真实生产所需的大部分业务概念。

问题不是这些概念错误，而是实际快捷流程没有走它们。

### 8.2 GenerationRunner 的不确定提交处理合理

`lib/media/generation.js` 区分 submit、run、download，并在提交结果不确定时记录 `submissionUnknown`。结合 idempotency key，可以避免盲目重提导致重复计费。

这套机制应成为所有 ComfyUI 生成的唯一入口，而不是只存在于领域路径。

### 8.3 Failure classification 与 recovery 方向合理

网络失败、下载失败和可恢复尝试已经有分类基础。应扩充契约错误、媒体验收错误和发布冲突，而不是重新设计另一套重试系统。

### 8.4 H3 skill 内容合理

六段式 Ref2VA 规范、引用保留规则和声音段落边界是清楚的。本次首镜在按 skill 改写后成功，证明规范本身可用。

需要改变的是把它从“模型临时阅读材料”提升为“编译器的正式输入规范”。

### 8.5 Canvas 路径安全设计合理

Canvas 路由已有相对路径验证和工作区逃逸保护。发布原子性可以在此基础上增加，不应为了事务能力削弱路径安全。

### 8.6 FFmpeg 使用参数数组和超时的方向合理

`lib/concat.js` 没有依赖拼接 Shell 字符串执行 FFmpeg，这降低了注入和转义风险。应继续在该模块内实现正式的 stream mapping、临时文件和验收，而不是把命令重新散落到模型生成的 Bash 中。

### 8.7 能力注册和 workflow inspection 合理

仓库已有 capability registry、workflow inspector、request builder 和 tier resolution。它们适合承担生产前 preflight，只需要把结果提升为强制门禁。

## 9. 核心问题模型

所有问题可以归结为一个核心矛盾：

> 系统把“模型能够调用工具完成动作”当成“生产系统能够证明交付正确”。

两者的区别是：

| 工具动作系统 | 可证明的生产系统 |
| --- | --- |
| 工具调用成功即继续 | 每步产生可验证状态转换 |
| 状态主要在模型上下文 | 状态持久化且可恢复 |
| ID 由模型临时记忆 | ID 由领域关系保存 |
| Prompt 由模型临时改写 | Prompt 由编译器生成并校验 |
| 文件存在即视为产物 | 媒体事实探测后才进入资产库 |
| 模型判断是否合格 | Review 与 validator 判断 |
| Shell 修补正式文件 | staged output 验收后原子发布 |
| 报告先于回读 | 回读一致后才能报告成功 |

因此核心修复目标不是增加更多提示语，而是降低模型在生产正确性上的自由裁量权：模型负责创作意图，确定性组件负责约束、状态、验收与发布。

## 10. 根治原则与优先级

### P0：先建立真实性边界

1. 区分计划时长、请求时长、实际时长和交付时长。
2. 生成完成立即探测媒体并回写资产事实。
3. 成功报告只能由 delivery validator 产生。
4. 文件发布必须使用临时路径和原子替换。

完成 P0 后，系统至少不会把错误成片报告为正确成片。

### P1：贯通正式生产状态机

1. 所有生成统一进入 GenerationRunner。
2. Canvas 快捷工具创建的媒体也必须注册 attempt/candidate asset。
3. 审核、批准和 timeline 组装成为强制阶段。
4. 中断恢复基于 attempt 状态，不依赖对话回忆。

完成 P1 后，系统可以避免重复生成并保留完整证据。

### P2：前移编译与预检

1. H3 prompt 编译正式化。
2. 参考资产增加语义角色。
3. 在一次 GPU 调用之前验证全部镜头。
4. 模型固定时长等能力限制在计划阶段显式化。

完成 P2 后，系统可以减少高成本失败和错误引用。

### P3：完善可观测性与部署一致性

1. 为每次操作记录结构化审计事件。
2. 记录 attempt、prompt snapshot、workflow fingerprint、media hash 和发布 revision。
3. 插件安装校验源码与 profile 副本指纹。
4. 对宿主空日志问题建立单独缺陷跟踪。

完成 P3 后，事故可以被可靠复盘，成本与稳定性可以量化。

## 11. 不应采用的修复路线

### 11.1 不应只在系统提示中要求“记得检查时长”

模型仍可能遗漏或过早判断；这不能建立强制门禁。

### 11.2 不应固定对所有成片执行 60 秒拉伸

这会掩盖镜头缺失、重复、顺序错误或生成时长异常。重定时只能是显式 conform 策略，必须在输入完整和审核通过之后执行。

### 11.3 不应继续用 Shell 修改 Canvas sidecar

这会扩大文件和元数据不一致的窗口，且无法提供 revision 冲突保护。

### 11.4 不应通过提高重试次数解决契约错误

缺少 H3 六段式、错误场景引用和目标时长未传导都属于确定性错误，重试只会重复消耗资源。

### 11.5 不应另建一套平行领域模型

现有 attempt、review、approval 和 timeline 足以承载主流程。应让快捷工具接入它，而不是增加第二套状态和更多同步问题。

## 12. 验证路径

### 12.1 最小复现测试

1. 构造 8 个计划总时长 60 秒、实际媒体各 6.587 秒的 episode。
2. 证明计划校验通过但 delivery 校验失败。
3. 证明显式 `retime` 策略可以生成约 60 秒输出，视频与音频时钟一致。
4. 人为让 Canvas 节点更新失败，验证正式文件和旧节点均保持原状态。

### 12.2 编译与引用测试

1. 普通分镜自动编译为合法 Ref2VA 六段式。
2. 缺少必要场景时在提交 GPU 前失败。
3. location 引用不能绑定 character 或不相干 location。
4. prompt snapshot 和 workflow fingerprint 可重复验证。

### 12.3 状态机测试

1. 未探测媒体不能进入 review。
2. 未批准媒体不能进入 timeline。
3. 某镜失败后只恢复该 attempt，不重复提交已完成镜头。
4. 已发布 episode 的来源资产改变后，成片自动 invalidated。

### 12.4 完整交付验收

最终端到端运行需要提供以下机器证据：

- 16 个镜头的 attempt、媒体探测和 review 记录；
- 两个 episode 的实际时长与镜头 manifest；
- 完整片来源于两个已验收 episode；
- ffprobe 音视频信息；
- 中间帧解码、黑帧和冻结帧抽检；
- Canvas 回读的路径、hash、revision 与磁盘一致；
- 整个运行没有访问非 Elysium 模型路由。

## 13. 诚实边界与未决项

- 已确认原始成片时长不合格，也确认后续生成了 60/60/120 秒文件；尚未把后续文件视为正式系统交付，因为 Canvas 原子更新和完整视觉验收没有可靠证据。
- 已确认现代修复室引用错误映射到长安城墙节点；尚未逐帧评估该错误对最终第一镜画面的实际影响。
- Harness UI 轨迹存在截断，`web.log` 为空；本文对已显示事件作出结论，但不能声称掌握所有内部宿主事件。
- 当前没有修改宿主 Harness 核心代码。结构化轨迹能否通过正式扩展点持久化，需要后续确认宿主 API。
- 本文提出的是缺陷模型和修复优先级，不表示 P0–P3 已经完成。

## 14. 决策建议

| 项目 | 决策 |
| --- | --- |
| 总体路线 | 保留现有 Project Domain，建立贯通的 production orchestration 与 delivery validation |
| 首要原因 | 当前最大风险不是无法生成，而是错误产物会被报告为成功 |
| 接受的代价 | 快捷生成将增加 preflight、探测和审核步骤，单次成功路径略长 |
| 否决路线 | 不采用继续补提示词、无限重试或固定 60 秒后处理作为根治方案 |
| 重审条件 | 如果宿主已提供可事务化的媒体任务和 Canvas 发布 API，应优先复用宿主能力而不是在插件内重复实现 |
