# 短剧不连贯：创作链路与代码根因

> 状态：已完成代码、项目记录与媒体时长核验；尚未逐帧观看或听审视频。
> 基线：2026-10-06，仓库 `92aa3293`；项目 `20261006213635859`；制作 Run `61c59134-6076-4b06-bf08-562858e5308f`。
> 范围：定位最大的全链路质量断点；本次只新增本报告，没有修改业务代码、运行项目或重新生成媒体。

## 0. 结论

**最大的根因是：小说到连续视听剧本之间缺少有效的全局创作约束与验收。系统把“各集输出了结构化文字、各镜生成了视频”当作可拼接的依据，而这些内容在生成视频之前已经发生跨集越界、重复和时间倒退。**

这条错误又被两个下游断点放大：所有镜头没有视觉参考或前镜状态输入；计划时长没有传到实际生成请求。最后只做文件拼接，错误完整进入成片。

责任判断：子 Agent 的输出确实有错；更大的系统责任在主编排的任务边界、上下文交接和验收机制。当前证据不足以把主要责任归给某个模型能力、小说质量或 GPU 视频模型。即使每一段画面都生成得清楚，当前的分集顺序仍然会讲错故事。

上一轮修复解决了“阶段缺失仍可生成”、失败吞掉、时长参数传递等问题；**不能据此宣称短剧创作质量和连续性已经修好。**

## 1. 从短剧创作视角，哪里先坏了

小说可以用叙述解释背景、心理、时间跨度；影片必须让观众通过动作、对白、空间与剪接理解变化。本项目已经有小说分析和分集大纲，但从大纲进入剧本后，缺少可执行的场景边界、事件先后及人物状态交接。

| 创作环节 | 本项目证据 | 对观众理解的影响 |
| --- | --- | --- |
| 分集边界 | 第一集大纲止于赴宴、众人离席和生日揭晓；第一集正式剧本及分镜却已经走到凌晨短信与尾声 | 第一集提前讲完后续内容，破坏后续集的推进空间 |
| 全剧时间线 | 第二集第一镜重新从家宴、离席开始；第三集第一镜又回到餐厅碰杯 | 按既定集序播放产生倒退、重复；记录中没有把这些设计为明确的倒叙或复述 |
| 原文事实保持 | 内容分析写“阿铃临时缺席”；第二集正式剧本却写她在席间起身离开 | 人物是否在场这一基础事实在改编过程中发生矛盾 |
| 可拍镜头拆分 | 第一镜提示词同时包含进门、餐桌、多人离席、关门、倒酒、碰杯、哭泣和拥抱 | 这是一串场景动作，不能仅靠标为一个镜头就得到清楚的动作因果 |
| 时间预算 | 12 镜计划合计 138 秒，实际每镜 5.167 秒 | 原先按 10–14 秒安排的动作和对白被交给更短的生成窗口，进一步增加漏动作、节奏挤压的风险 |
| 视觉连续性 | 12 次生成的参考绑定均为空；没有分镜图；没有前镜续接 | 每次请求缺少同一人物、同一空间与动作接点的视觉依据；具体换脸、空间漂移程度尚未逐帧确认 |
| 剪辑验收 | 三集按节点顺序拼接；视频资产仍为 candidate，12 项媒体审核仍待人工处理 | 文件生成成功、拼接成功并不能证明叙事、表演或声音连续 |

其中，分集越界和事件倒退是**已经写入剧本的确定性错误**。视觉漂移的具体表现仍待观看，但“没有向生成请求传入视觉参考”已经确认。

## 3. 从代码看，问题最大的地方

### P0：主编排缺少全剧语义验收，子任务边界不受约束

历史仓库 `0d496018:lib/index.js` 的小说编排路径存在以下设计：

- `episode-plan` 提示词强制“最多 3 集”。
- `episode-script` 提示词强制“script 不超过 800 个汉字，最多 4 镜”。
- 分集写作者接收故事圣经和当前集规划，未在该提示词中提供本集原文正文或上一集实际完成状态。
- `studio_episode_script_submit` 使用 `autoApprove: true`。

当前产物正好为 3 集×4 镜；这支持“硬性压缩与实际结果吻合”的判断，但没有保留生产进程内代码哈希，不能把该提交直接等同于当时加载版本。

当前仓库已经移除固定集数、镜头数上限，并在 `lib/script/novel-production.js:95` 提供本集原文；但核心缺口仍存在：

1. `NOVEL_SCHEMAS` 的 shot 只有描述、prompt、对白、事件 ID 和绑定，没有明确的场景 ID、镜头起止状态、相邻镜关系或剪接意图。
2. `novelTextProduction()` 的分集写作任务仅依赖分集规划；提示词没有上一集已写结果或明确的入场/离场状态契约。并行本身不是错误，缺少共享且经过验收的边界才是问题。
3. `assertNovelPlan()`、`assertEpisodeCoverage()` 主要检查 ID 集合覆盖与来源区间覆盖。事件 ID 出现过，并不表示事件在正确位置被正确演出。
4. `lib/index.js:4086` 起仍将分析、规划、分集剧本自动批准并直接进入媒体任务。

**本次最小复现：**使用两个不同集 ID，让两集都分配“抵达、离开”两个事件、都引用全文区间；剧本和镜头将顺序写成“先离开、后抵达”，设置一个 30 秒镜头。当前 `validateDevelopmentPayload('episode_plan')`、`validateDevelopmentPayload('episode_script')` 和 `assertNovelCoverage()` 全部通过。该复现只在内存中执行，没有写项目或调用模型。

这证明当前验证器不能阻止重复分集、事件顺序倒置或未声明用途的区间重叠；提示词的“每镜最多 8 秒”也未成为硬校验。`lib/script/contracts.js:94` 只检查时长大于零。

优先修复这里，因为错误在此进入“正式、已批准”的创作输入；下游换模型或改善画质无法恢复正确故事。

### P1：有制作依赖，但没有相邻镜头的连续性契约

历史产物的 12 个镜头均独立生成。当前 `lib/production/drama.js:13` 已建立角色/场景图→分镜图→视频的依赖，这是必要改进。

但是：

- `dramaProductionTasks()` 没有根据镜头关系创建前镜→后镜的连续性依赖。
- `lib/index.js:3901` 的 render-shot 处理器传入本镜时长、参考图或本镜分镜图，没有将 Shot 的前镜关系转换为 `continuity_from`。
- 底层 `runRender()` 在 `lib/index.js:1962`、`:2031` 附近已有续接能力；整剧编排没有按镜头关系接入它。
- 分镜图也按本镜描述和公共参考独立生成，没有验收“上一镜动作结束时的状态能否接上下一镜”。

因此，即使阶段全部有内容，也可能只是“一组人物相似的独立画面”。共享角色图不能独自保证动作、站位、视线、道具与服装状态连续。

修复时不能简单把全剧串成一条续接链：同一动作的延续、同场景换机位、跨场景切换需要不同条件。先明确镜头关系，再选择参考图、首帧或续接能力。

### P1：历史时长没有传递；当前仍缺少动作与对白可演性验收

历史 `lib/index.js` 的批量任务只传 prompt 等字段，render-shot 直接转发 task.input，没有从 Shot 读取 duration。实际项目任务输入和 124 帧输出与此吻合。

当前 `lib/index.js:3907` 已传 `durationSeconds: shot.duration`，`:2017` 换算帧数，`:3916` 校验实际时长。这部分已在代码修复，旧文件不会因此变长。

剩余更上游的问题是：即便生成足额时长，一个镜头是否装入了过多动作、跨了多个地点、对白和动作是否能演完，当前没有有效验收。应先拆出可演镜头，再按所选工作流预算时长。

### P1：自动审核只检查媒体条件，没有审核内容

当前 `lib/index.js:3864` 的 `approveGeneratedAsset()` 记录 `media-metadata: pass` 后直接批准；参考图只检查可解码，视频主要检查阶段和时长。

`deliver-drama` 检查镜头齐全、资产已批准、文件与总时长，然后写入 `qualityReport.visualReview: 'not_performed'` 并完成项目。`runConcat()` 按输入节点顺序拼接，不判断情节是否重复、说话人是否正确或接点是否成立。

“媒体可用”与“创作验收通过”尚未分开落实。上一轮新增的自动批准不能作为连续性已验收的证据。

## 4. Agent、子 Agent、模型分别承担什么责任

| 对象 | 判断 | 证据边界 |
| --- | --- | --- |
| 分集子 Agent | 已确认产生跨集越界与事实矛盾 | 项目内已保存的正式剧本、分镜可直接对照 |
| 主编排与校验 | 最大的软件责任：放任错误变成正式输入，缺少跨集汇总审查与退回修订 | 自动批准路径和最小复现支持 |
| 视频生成接入 | 放大错误：历史请求无参考、无状态交接、时长失配 | Attempt、任务输入、节点参数、ffprobe 支持 |
| 视频模型本身 | 是否还有动作、身份、语音能力缺陷：未确认 | 尚未在正确且固定的输入条件下对比生成；不能从错误输入的失败结果单独归因 |
| 小说 | 本次没有发现需要修改小说才能解释上述错误的证据 | 已定位的错误发生在改编、传参和验收链路 |

增加子 Agent 数量、把全部任务改为串行、提高分辨率或统一随机种子，都不能单独修复已发生的跨集越界。新增审查 Agent 只有在能够读取全剧、定位矛盾、阻止下游并触发修订时才有价值。

## 5. 最大问题的最小修复顺序（建议，尚未实施）

先修“批准了什么”，再修“如何生成”，最后验收拼接结果。

| 顺序 | 拟涉及文件 | 最小改变 | 验证方式 |
| --- | --- | --- | --- |
| 1 | `lib/script/novel-production.js`、`lib/script/contracts.js`、`lib/index.js` 的 Proposal 提交路径 | 在写分集前明确事件归属、场景顺序及边界状态；汇总全剧后检查事实、顺序、重复和越界。结构约束用代码验证，内容矛盾需对照原文与剧本审核；审核失败退回对应任务，禁止进入媒体生成 | 用当前项目的第一集越界、阿铃在场矛盾和重复家宴作为失败样本；新增内存复现必须被阻止；先验收纯文本全剧 |
| 2 | 分镜契约、`lib/production/drama.js`、`lib/index.js` 的 renderPreparation/render-shot | 每镜明确可演动作、起止状态、接续关系与时长；将需要的前镜依赖与视觉条件传至底层生成 | 检查实际请求的时长、参考资产及续接参数；先验证一个普通对话场景的少量相邻镜头 |
| 3 | `lib/index.js` 的 approveGeneratedAsset/deliver-drama、对应审核策略 | 区分技术检查与内容审核；人物、动作接点、对白及全剧顺序未验收时不能声称内容合格 | 查看/听审真实相邻镜头与拼接结果，记录不合格镜头并定点返工 |

第一项优先级最高：至少先让正式剧本按正确时间线讲完一遍，再投入图片和视频生成。
