# 任务与步骤状态简化调研

## 结论
- AC-1 — 已确认：任务状态统一由 deriveTaskStatus 推导，记录 status 是缓存；trace.status 另按后台任务数量赋值且无人读取，应删除。
- AC-2 — 已确认：latestVerdicts 与 reviewFailures 重复归并最新审核；runner.localStep 与 task-store.planStep 重复初始化；snapshot 重复计算状态，current 又覆盖克隆后的 steps。
- AC-3 — 未验收：需验证状态优先级、复审覆盖旧结论、取消、内存任务和快照隔离。

## 规格
- 目标：合并状态处理中的重复逻辑，让步骤成为任务状态的唯一来源。
- 非目标：不改变已有状态枚举、存储格式、优先级、后台等待、队列和节点状态；不处理上一轮以外的既有失败。
- AC-1：任务最终状态及查询只从步骤推导，无无用的第二套状态。
- AC-2：步骤初始化、最新审核选择各只有一份实现；快照不重复计算/覆盖数据。
- AC-3：正常完成、审核失败/复审通过、排队和执行取消、当前任务快照均保持正确；全量不新增失败或取消。

## 调用链
- runner.start → createTaskRecord/beginTask → runOperation → runStep → endExecution/finalizeSteps → runner.settle → snapshot。
- 内存任务：localStep → running → settleLocal → finalizeSteps；其步骤形状与持久化任务重复。
- 步骤结论 → latestVerdicts/reviewFailures（分别归并）→ deriveTaskStatus/reviewPassed/finalizeSteps。
- 查询：snapshot → summary 内 deriveTaskStatus，再单独 deriveTaskStatus 判断 queued；current 在展开 snapshot 后又用 stepsOf 覆盖克隆。
- 前端 current-task/execution-history 使用 API task.status；task-steps 的分组状态使用同一 deriveTaskStatus。
- trace 只用于日志和 result；run.js 的 trace.status 不被路由、runner、会话工具或嵌套操作读取。
- finished 是执行函数 finally 是否完成的内存标记；preparing 区分真实执行与出队准备；保留，不能和业务状态混为一谈。
