# 平台适配器可替换调研

日期：2026-09-15。职责：补齐已有 Runpod 实现的依赖取证及平台可替换验收标准。

## 结论

- AC-1 — 已确认不满足：平台名仅进入 JSON，执行链未加载 provider。
- AC-2 — 已确认不满足：Runpod 目录只有占位，服务生命周期与工作流来源仍在外部脚本。
- AC-3 — 已确认不满足：没有模块发现和契约校验，客户端平台选项写死。
- AC-4 — 已确认部分满足：任务/批次保存后端快照，但未检查所属适配器是否仍存在。
- AC-5 — 未验收：现有测试只覆盖地址切换，没有物理删除 Runpod 后的构建和完整任务测试。
- AC-6 — 已确认约束可继续沿用：安装与真实平台租赁分离，其他平台只保留目录；不新增平台 API。

上述为实施前基线，不把文档中的“已完成”作为代码证据。

## 规格

目标：业务通过统一平台接口调用现有 Runpod 完整服务流程；其他平台实现同一契约后可独立替换，删除 Runpod 模块不会破坏使用其他平台的业务。

非目标：
1. 不实现其他三家平台 API、自动租机、计费或资源销毁。
2. 不把项目、批量编排、ComfyUI HTTP 协议、H3 模型工作流复制到每个平台。
3. 不迁移在途任务或媒体，不修改真实服务器配置、凭据或存储，不执行远端启停。
4. 不把仓库从未实现的云实例创建、镜像安装承诺为“现有完整流程”。本次 Runpod 完整范围为已有服务配置、连接、就绪检查、工作流构建与执行、查询/恢复/取消、结果 URL、现有镜像中的进程启停及工作流同步来源。

验收标准：
- AC-1：选择 provider → 新任务、恢复、原子工具、批次、参考帧、媒体连接、检查和 LLM 启动均通过公共调度接口；业务文件不直接导入具体 provider。
- AC-2：Runpod 目录 → 提供版本化入口、配置与能力定义、公共协议组合、服务管理实现、使用说明、配置样例；现有外部运维入口只做兼容转发。
- AC-3：仅新增符合契约的 provider 目录 → 系统发现、登记、选择和执行，无须修改核心或前端枚举；仅有占位的目录不可调用；缺失或损坏适配器明确报错，不回退到其他平台。
- AC-4：切换或移除 provider → 新任务使用新选择，原任务/批次保留原 provider 和服务快照；原 provider 缺失时该任务明确不可恢复，但项目与其他平台仍可用。
- AC-5：隔离副本物理删除 `providers/runpod/`，仅加入 AutoDL 测试实现 → 构建、包导入、HTTP 项目接口、检查/切换、真实本地 worker 生成/恢复、原子查询/取消、批次/参考帧、历史媒体和 LLM 配置路径通过；另对真实 Runpod 模块运行相同公共契约及生命周期模拟测试。
- AC-6：目录/差异检查 → 其他三家正式目录仍仅占位；测试适配器只存在于临时副本，不冒充 AutoDL 已接入；安装不连接云服务；冻结制作案例不改动。

## 调用链

```text
聊天生成 → video/service → createJob(backend.json) → launcher → worker → video/execution
  → ensureConnection + new ComfyClient + buildVideoGraph → ComfyUI 提交/历史/结果
批次 → runner → executeVideoShot / ComfyClient → reference-frame
服务器设置 → server-routes → resolveServer → checkServer → writeRegistry
本机启动 → tunnel / server-startup → 通用 SSH / settings
远端运维 → runpod/scripts/comfyui.mjs → 固定镜像路径与进程命令
工作流同步 → scripts/workflow-sync.mjs → 固定 Runpod 公网 URL
```

问题发生点：这些链路都没有调用 `providers/<provider>/index.js`。平台标记未成为执行依赖。
