# 持久化任务驱动调研

## 结论

- AC-1 — 已确认 — Job 存储仍由 `projectJobRoot(projectId, jobId)` 定位到项目内，与已迁移的 `projects/jobs/` 不一致。
- AC-2 — 已确认 — `submitTask` 目前在一次调用中路由、建档并立即 `launch`，没有持久化队列。
- AC-3 — 已确认 — 状态机只有 `queued/running/succeeded/failed`，不支持受理后待派发和取消。
- AC-4 — 已确认 — 当前没有驱动循环、对账、结算和按泳道选择派发的实现。
- AC-5 — 已确认 — Session 单次生成由工具内 `waitJob` 阻塞；安装的 `ctx.jobs.start` 支持绑定 `exec.agent` 和完成通知。
- AC-6 — 已确认 — 项目 Store 能按镜头 ID 幂等更新，但尚未注册任务结算回写处理器。
- AC-7 — 已确认 — 基线插件测试 199/199 通过，可用于阶段回归对比。

## 规格

- 目标：按 `docs/design/设计-持久化任务驱动.md` 建立可恢复、全局单并发、按泳道有序的生成任务驱动闭环。
- 非目标：
  1. 上传、下载、状态查询、ffmpeg、媒体探测和校验不进入任务驱动。
  2. 不实现自动重试、重排、插队或修改已提交任务。
  3. 不把 Harness `ctx.jobs` 当作持久化队列。
- 验收标准：
  - AC-1：新旧 Job 都从 `projects/jobs/` 读写，137 个现存 Job 可读，迁移后诊断路径为相对路径。
  - AC-2：Job 原子建档，支持 `pending/cancelled`，不会暴露无状态目录。
  - AC-3：批量提交全或全无、幂等，引用约束、结算和管理命令符合设计。
  - AC-4：驱动可对账、重建、结算和轮转派发；全局最多运行 1 个任务，失败不阻塞后续。
  - AC-5：单次媒体工具输出不变；导演批量提交由 `ctx.jobs` 完成通知。
  - AC-6：Service 通过幂等 Sink 回写项目镜头/锚点，删除项目能找到其全局 Job/Task。
  - AC-7：新增专项测试、插件全量测试、构建、Registry 打包和差异检查通过。

## 调用链

```text
Session/Service -> worker.submit -> routeTask -> tasks + pending Job + driver index
                                                   |
driver loop -> reconcile -> settle terminals -> choose lane -> launch -> Worker
                                                   |
Worker -> status.json -> driver settle -> registered sink / ctx.jobs waiter
```
