# Harness 项目存储双入口一致性调研

日期：2026-09-14

状态：待审核；本文仅提出设计，不代表功能已实现。

## 0. 问题本质

AI 短剧创作有两个操作入口：右侧面板（手动编辑）和聊天（AI 辅助创作）。两者需要操作同一份项目数据，且修改后双方都能看到最新状态。

这是一个**单用户、单机、单进程**的场景。不存在多用户并发、网络分区、分布式一致性等问题。方案应当匹配这个实际复杂度。

## 1. 结论

采用"统一项目工具 + 保存后刷新"的最小方案：

1. **聊天侧增加项目读写工具**——复用现有 `store.js` 的能力，让 AI 能通过工具调用创建/修改项目数据
2. **右侧面板改为对象级操作**——不再提交整个数组，而是按对象 ID 增删改
3. **保存后通知刷新**——任何一方保存成功后，通知另一方重新加载数据
4. **创作编辑 Skill**——规范 AI 的创作行为（先读后改、展示差异、按授权保存）

不引入：版本号/乐观并发、操作去重/幂等 ID、恢复日志/WAL、操作记录持久化、多会话协同。这些是分布式系统的解法，不匹配当前场景。

## 2. 现状代码依据

以下路径均相对于仓库根目录 `/Users/mac/ai/llm-dsh-plugins`。

| 位置 | 现状 | 影响 |
| --- | --- | --- |
| `../../dsh-elysium/src/projects/store.js` | 项目按元数据、素材、锚点、分镜、交付物拆成 JSON；Promise 队列串行写入；临时文件+rename 原子写 | 已有可靠的单进程写入保障 |
| `../../dsh-elysium/src/projects/schema.js` | 基础字段校验；分镜序号保存时重新计算 | 序号不能作为长期身份，需要稳定 ID |
| `../../dsh-elysium/src/client/workbench/anchors.js` | 添加/编辑后提交整个锚点数组 | 需改为对象级操作 |
| `../../dsh-elysium/src/client/workbench/storyboard.js` | 用数组位置定位镜头，提交整个分镜数组 | 需改为对象级操作 |
| `../../dsh-elysium/src/tools/index.js`、`src/index.js` | 注册生成/查询工具，未注册项目编辑工具 | 需新增项目读写工具 |

实际数据位于 `/Users/mac/.dsh/storages/elysium`。仓库中的 `../../harness/.dsh/storages/elysium` 是安装模板。

## 3. 数据职责

正式项目数据由 `store.js` 管理。右侧表单和聊天上下文都不是独立副本。

区分三种内容：
- **正式数据**：已提交的项目字段，双方共读
- **待保存提案**：AI 整理的修改建议，用户未确认前不影响正式数据
- **讨论内容**：聊天中的探讨，不写入项目

## 4. 两入口的统一链路

```text
右侧面板 → HTTP 路由 ─┐
                      ├─ store.js 校验并写入 → 正式数据 → 通知刷新
聊天 → 项目工具 ──────┘
```

两入口共享同一个 store 实例。HTTP 路由和聊天工具只是不同的调用适配层。

## 5. 需要做的三件事

### 5.1 给聊天增加项目工具

在 `tools/index.js` 注册项目读写工具，与 HTTP 路由共用同一个 store 实例：

- `read_project`：读取项目完整数据
- `update_anchor`：增删改单个锚点（按 ID）
- `update_shot`：增删改单个镜头（按 ID）
- `update_project_info`：修改项目元数据
- `create_project`：创建新项目

工具调用 store.js 的现有方法，不新增独立的写入逻辑。

### 5.2 右侧面板改为对象级操作

当前问题：`anchors.js` 和 `storyboard.js` 提交整个数组，如果右侧持有旧数据，会覆盖 AI 刚保存的内容。

改动：
- 角色/锚点使用稳定 ID（现有 `role` 字段可作为标识，新增的用 UUID）
- 镜头使用稳定 ID（不再依赖数组下标）
- 前端改为发送"修改某个对象的某些字段"，而非"替换整个列表"
- store.js 增加对象级的增删改方法

这是唯一真正需要的"一致性保障"——消除整数组覆盖的风险。

### 5.3 保存后通知刷新

任何一方保存成功后，右侧面板刷新对应数据：

- 优先复用宿主已有的事件机制（待核验）
- 如无现成机制，store 写入成功后通过简单回调通知前端重新加载
- 前端收到通知后，刷新已保存区域；如果用户有未提交的编辑，提示"数据已更新，是否加载最新版本"

不需要实时 WebSocket 推送。保存是低频操作，回调通知足够。

## 6. 创作编辑 Skill

一个 Skill 覆盖"完整创建"和"中途修改"两种场景，规范 AI 的行为：

**Skill 规则：**
1. 通过项目工具读写数据，不直接修改 JSON 文件
2. 修改前先读取最新项目数据
3. 展示具体变更内容，按用户授权决定是否保存
4. 不确定的内容保留为提案，不当作已确认事实写入
5. 只提交明确修改的字段，未提及的保持原值
6. 保存结果以工具返回为准

**用户意图判断：**

| 用户说 | AI 做 |
| --- | --- |
| "把小林改成红色外套并保存" | 直接保存 |
| "帮我修改小林的服装" | 给出建议，询问是否保存 |
| "红色外套会不会更好？" | 讨论，不改数据 |

Skill 是行为指引。若 Agent 有通用文件工具可直接写存储目录，需核验权限配置能否限制。

## 7. 项目约束（继承自 standards.md）

| 约束 | 落实 |
| --- | --- |
| 只在 `dsh-elysium` 插件内实现 | 不新建插件或服务 |
| `projects/` 负责领域逻辑，`tools/` 负责工具，`http/` 负责路由 | 各层职责不混 |
| 客户端无 JSX、无 bundler | 保持现有技术栈 |
| 临时文件+rename 原子写入 | 继续沿用 |
| 媒体使用服务器 URL，不新增文件上传下载 | 本功能不涉及媒体文件 |

## 8. 实施顺序

1. **store.js 增加对象级操作方法**（稳定 ID + 单对象增删改）
2. **注册聊天项目工具**（复用 store 方法）
3. **前端改为对象级提交**（anchors.js、storyboard.js）
4. **保存后刷新通知**（核验宿主事件机制后决定方案）
5. **创作编辑 Skill**

每步可独立验证，不存在大爆炸式改动。

## 9. 验收场景

| 场景 | 预期 |
| --- | --- |
| 右侧新增角色 | 数据保存成功 |
| 聊天通过工具新增镜头 | 右侧刷新后可见 |
| 右侧改角色 → 聊天改字幕 | 两次修改都保留 |
| 讨论"是否更好" | 正式数据不变 |
| 聊天创建完整项目 | 结构和引用通过校验 |

## 10. 不做的事及理由

| 不做 | 理由 |
| --- | --- |
| 版本号 + 乐观并发控制 | 单用户单进程，store 队列已保证串行，不存在真正的并发冲突 |
| 操作去重 / 幂等 ID | 本地工具调用不存在网络重试，调用即执行 |
| 恢复日志 / WAL | 单文件 temp+rename 已是原子写入；跨文件场景极少且可通过写入顺序控制 |
| 聊天操作记录持久化 + 重连补发 | 右侧刷新即可看到最新状态，不需要在聊天中完整回放历史 |
| 会话-项目绑定协议 | 用户一次用一个聊天窗口，项目上下文由 Skill 管理 |
| 自动合并算法 | 对象级操作后不存在字段级冲突 |
| 历史版本浏览 | 可用 git 管理，不需要应用层实现 |
