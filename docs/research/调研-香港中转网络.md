# 香港中转网络调研

## 结论
- AC-1 — 未确认 — GPU → 香港出站 22 已实测可达且 0% 丢包；反向隧道与自动重连尚未部署。
- AC-2 — 未确认 — 服务器不可重启；容器无 systemd，容器内看不到 `/init/supervisor` 且无 `supervisorctl`，改用 `~/.bashrc` 登录钩子 + `flock`，以模拟方式验证。
- AC-3 — 部分确认 — 2026-09-21 香港管理入口 `veo-hk`（ubuntu + sudo 免密）已打通；GPU 别名经中转待实施。
- AC-4 — 未确认 — 基线已测：现有 16016 隧道 5 次中 1 次失败、1 次 10.6s；中转后的数据待实施后测。
- AC-5 — 未确认 — 香港公网仅 22；Ubuntu 24.04 / OpenSSH 9.6 支持 `permitlisten`；当前允许密码与 root 登录，需在阶段 1 收紧。
- AC-6 — 已确认（前提） — 现有直连别名可用，保留为 `-direct` 即可回退。
- AC-7 — 未确认 — `veo-comfyui` 代理变量指向 `127.0.0.1:7890`，该端口无监听，出站全部失败；是否纳入本次由用户决定。

## 规格
- 目标：两台 AutoDL GPU 机经香港 43.154.247.11 中转访问，消除本机 → seetacloud 网关跨境链路丢包造成的卡顿和超时，且对项目代码透明。
- 非目标：
  1. 不修改 `dsh-elysium` 隧道实现（`transport.js`）及端口定义（16016/18000）。
  2. 不追求降低往返延迟下限（日本 ↔ 大陆物理距离决定）。
  3. 不引入 WireGuard/Tailscale（容器无 `/dev/net/tun`）。
  4. 不在香港机开放除 22 以外的公网端口。
  5. 不重启任何服务器（香港、两台 GPU 容器），不中断 ComfyUI 与 llama-server。
- 验收标准：
  - AC-1：两台 GPU 机向香港建立反向隧道；杀掉 GPU 端隧道进程或断开香港端 `tunnel` 会话后，60 秒内无人工介入自动恢复。
  - AC-2：隧道进程全部停止后，经任一入口（直连 SSH、AutoDL 网页终端）登录一次即自动拉起且只运行一份；不重启服务器，以模拟方式验证。
  - AC-3：本机 `ssh veo-comfyui` / `ssh veo-qwen38` 经 `veo-hk` 跳转登录成功，`ssh -G` 显示 `proxyjump veo-hk`，主机密钥校验不降级。
  - AC-4：不改代码，项目按需建立的 18000（`/v1/models`）与 16016（`/system_stats`）隧道可用；各连续 100 次请求 0 失败，p95 < 1s。
  - AC-5：香港公网端口不新增；反向监听只绑定 `127.0.0.1`；GPU 端密钥在香港不能取得 shell，只能监听各自端口。
  - AC-6：`veo-comfyui-direct` / `veo-qwen38-direct` 直连可用；恢复 `~/.ssh/config.bak` 即回退。
  - AC-7（可选）：`veo-comfyui` 经香港代理访问 GitHub、HuggingFace 返回 200。

## 调用链
```text
项目连接隧道 → transport.js:ensureConnection
  → ssh -M -S <control> -f -N -L 127.0.0.1:<local>:127.0.0.1:<remote> <ssh_alias>
  ├─ 现状：alias → connect.west{b,d}.seetacloud.com（日本 → 大陆公网，丢包 23%）
  │   └─ 丢包 → TCP 重传 → 请求 10s 级卡顿 / 失败          [问题发生点]
  └─ 目标：alias → ProxyJump veo-hk → 127.0.0.1:2200x（香港）
        → GPU 主动建立的 -R 反向隧道 → GPU sshd:22 → 127.0.0.1:<remote>
        ├─ 反向隧道断开 → GPU 守护循环重连；香港 ClientAlive 清理旧监听
        └─ 香港不可达 → 手动切回 -direct 别名
sshIdentity 把 hostname/port/proxyjump/hostkeyalias 计入哈希 → 切换后旧控制连接自动失效，不会错误复用
```
