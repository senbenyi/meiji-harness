# 短剧创作闭环调研

调研时间：2026-09-22；代码：`/Users/mac/ai/llm-dsh-plugins/dsh-elysium`（行号以当前工作区为准，含未提交的剧本页改动）；运行数据：`~/.dsh/storages/elysium`。本轮只调研与设计，不修改代码、Skill 或项目数据。

## 已确认的产品口径

| # | 决定 | 对设计的约束 |
|---|---|---|
| 1 | 剧本与分镜**分开** | 分开后不能出现两处维护同一内容：分镜只引用剧本，不复制剧本 |
| 2 | 前期**全部人工审核**，系统不做任何审核 | 去掉“需复核”、自动定稿、审校、质检、级联暂停；每一步都能人工编辑，另提供“自动生成”入口 |
| 3 | **不区分版本**，一次通过 | 每个产物只有一份当前内容，保存即生效；去掉 versions / finalize / based_on |
| 4 | 闭环由**人工验证**，系统少干预 | 系统只负责生成、保存、提交任务、合成成片；是否满意、是否重做都由人判断 |
| 5 | 集数由 **Skill 维护** | 集数只由导演 Skill 规定，其他 Skill 和代码不另行决定；先修复 Skill 失效的问题（见第一节） |

## 结论

当前流程没有闭合，原因不是缺少功能，而是**多了三样东西**：

1. **重复内容**：情节、对白、场景被时间线、分镜、提示词、字幕各写一遍。
2. **版本机制**：内容要先产生版本，再“定稿”，定稿后还要级联标记“需复核”。
3. **系统代替人做判断**：自动定稿、自动暂停、“完成”和“需复核”两种状态同时成立。

闭环的做法是把这三样都去掉，只保留一条人能看懂、能随时插手的直线：

```text
立项 → 剧情总览 → 单集剧本 → 分镜 → 镜头提示词 → 角色定妆 → 镜头 → 成片 → 人看
  ▲       ▲          ▲         ▲        ▲            ▲         ▲              │
  └───────┴──────────┴─────────┴────────┴────────────┴─────────┴── 不满意：回到任一步编辑 / 重新生成 / 重拍
```

- **数据闭环**：每个事实只存一处，下游引用上游，不复制。改剧本的一句台词，分镜、提示词和字幕看到的都是同一句。
- **流程闭环**：每一步都是“一份当前内容 + [自动生成] + [编辑保存]”。自动生成只是替人写初稿，人保存后即生效。
- **产品闭环**：人看成片 → 定位到某一步修改 → 重拍受影响的镜头 → 重新合成。系统不判断对错，只保证改动能走到成片。

## 一、集数 Skill 为什么失效

**结论：Skill 没有失效，它被正确加载，模型也照着执行了，只是执行的是 Skill 里另一条互相矛盾的规则。** 同时，立项草稿和通用规划 Skill 都在鼓励模型自己决定集数。

| 事实 | 证据 |
|---|---|
| Skill 已生效并被注入 | 导演 `director-cad24a59/references/script.md` 最后修改于 2026-09-21 20:31（本地时间）；《雨夜未寄出的信》立项于 21:21，总览 v1 生成于 21:21:52。立项（`planning.js:44`）和总览（`planning.js:74`）都注入了 `script.md` |
| 同一行里有三条互斥规则 | “集数：**通常 2 集**……按**关系阶段数量**判断：相遇、误会、分离、真相、重逢，**每阶段至少 4–8 集**。”第三条算下来是 20～40 集 |
| 模型执行的是“按阶段数量判断” | 项目详情的故事走向正好 5 集，并逐集标注（相遇·甜）（误会·虐）（分离·虐）（真相·甜）（重逢·甜），与 5 个关系阶段一一对应 |
| 立项就定死了集数 | 立项草稿要求写“## 故事走向”（`planning.js:46`），模型据此写出了第 1～5 集。总览这一步又把项目详情作为用户输入（`planning.js:78`），于是 5 集变成了“项目事实”，压过了“通常 2 集”这句软建议 |
| 通用 Skill 明确授权模型自定 | `drama-planning/SKILL.md`：“集数、单集时长由故事规模和节奏决定，不机械固定”；`steps/series.md`：“根据……导演 Skill 及故事容量**决定适合的集数**” |
| 没有稳定性 | 项目《雨夜来电》连续生成三次总览，得到 40 / 30 / 40 集（当时导演 Skill 还没有“通常 2 集”这句） |

修复只动 Skill 文本，不加代码校验：

1. 导演 `script.md` 的集数写成**一条确定规则**，例如“集数：2 集；单集 60–150 秒”。关系阶段改写成“单集或全剧的结构”，不再和集数挂钩。
2. `drama-planning` 与 `steps/series.md` 改为“集数与单集秒数**严格采用导演 Skill 的规定**，不得自行决定”。
3. 立项草稿不再写逐集的“故事走向”，只写梗概、主角与冲突；逐集内容只由剧情总览负责。这样也消除了项目详情和总览之间的重复。

修复后，列表显示的集数就是总览的集数，而总览的集数就是导演 Skill 规定的集数，来源只有一个。

## 二、现状的重复与多余机制

### 2.1 同一内容被写多遍

以运行项目第 3 集第 1 镜为例：

| 位置 | 内容 |
|---|---|
| 项目详情 `synopsis` | 第 3 集走向：“林晚搬回母亲家……咖啡馆……” |
| 总览 `episodes[2].summary` | 同一集的梗概，再写一遍 |
| 时间线 beat 0 `plot` | “林晚坐在靠窗座位，面前放着一杯冷掉的咖啡。她望着窗外雨滴滑落玻璃，眼神疲惫。桌上摊开一本素描本……” |
| 分镜 shot 0 `action` | 与上一行几乎逐字相同 |
| 镜头 `prompt` | 场景、人物、动作第三次展开 |
| 提交视频时 | `service.js:26` 在 prompt 前面再拼一次场景描述 |
| 对白 | 同时存在于时间线、分镜、提示词（校验要求逐字包含，`planning-schema.js:79`）和字幕来源 `shot.dialogue`（`film.js:32-46`） |

结果是改一句台词要改四处。系统用“整层需复核 + 重新生成”来追平，而重新生成又会改掉人工修改过的其他内容。

### 2.2 版本和复核机制制造了矛盾状态

- 每一步都有 `versions / finalized / based_on / needs_review`（`managers/projects.js:187-214`）。上游一旦重新定稿，下游整层都会被标记为需复核；换导演时全部被标记（同文件 `281-289`）。
- 运行项目第 3 集：8 个镜头和成片都已完成，但分镜仍基于时间线 v2（当前为 v4），8 条提示词全部标为“需复核”。流水线对已完成的集直接跳过这些标记（`pipeline.js:18-29`），于是“完成”和“需复核”同时成立。
- 自动模式在生成后立即定稿（`pipeline.js:43-54`、`planning.js:86-110`），所谓“审核”只是形式。
- 提示词重新定稿后，旧任务 ID 会被清空（`planning.js:150-154`），改稿就会触发重拍。

这些机制都是“系统替人判断”。按口径 2～4，应当整体删除，而不是继续修补。

### 2.3 Skill 职责混杂

| Skill | 越界之处 | 调整 |
|---|---|---|
| 导演 `script.md` | 集数规则自相矛盾 | 只保留一条确定的集数规则 + 叙事节奏 |

## 三、目标设计

### 3.1 每步一份当前内容，事实只存一处

| 步骤 | 存储（不再有版本） | 只维护 | 引用而不复制 |
|---|---|---|---|
| 立项 | `project.json` | 名称、导演、题材、梗概（Markdown，不写逐集走向） | — |
| 剧情总览 | `series.json` | 一句话故事、世界观、角色（含外观、音色、定妆图提示词）、场景、分集条目（标题 / 梗概 / 钩子）、单集秒数 | 集数 = 分集条目数，不再单独存 `episode_count` |
| 单集剧本 | `episodes/N/script.json` | 按场景分组的行：动作行 / 对白行（角色、语气、台词），每行有稳定的短 ID；**不含时间码** | 场景、角色引用总览 ID |
| 分镜 | `episodes/N/storyboard.json` | 每镜：引用的剧本行 ID、出镜角色、景别、运镜、画面补充、时长 | 台词和动作从剧本行读取显示；时间线由镜头时长累加得出 |
| 镜头提示词 | 分镜里每镜的 `prompt` / `keyframe_prompt` | 画面、运镜、光线、分秒节奏 | 台词写成占位符 `{L12}`，提交时由代码替换为剧本原文，并带上角色音色 |
| 镜头与成片 | 现有 `job_id / status / deliverables` | 不变 | 字幕取自剧本行 |

剧本与分镜分开后避免重复维护，靠的是这四条规则：

1. **台词只在剧本里改。** 分镜页把引用的台词以只读方式显示在镜头旁边，点击后跳到剧本对应行。
2. **分镜只写“怎么拍”**，包括景别、运镜、时长和画面补充，不重述剧情。分镜 Skill 的说明写明这一点。
3. **提示词不抄台词。** 占位符在提交时替换，所以改台词后不需要改提示词，重拍就能用上新台词。
4. **引用失效时只提示，不拦截。** 剧本删掉某行后，引用它的镜头显示“引用的第 L12 行已删除”，由人决定怎么处理。这只是显示，不算审核。

### 3.2 每一步的交互都一样

```text
┌ 第 3 集 · 剧本 ───────────────────────────── [自动生成] [编辑] ┐
│  一份可读正文；编辑时就是同一份文本，保存即生效                  │
└──────────────────────────────────────────────────────────────┘
```

- **[自动生成]**：把上游内容和对应的 Skill 交给 LLM，结果直接写入这一步。如果这一步已有内容，先确认再覆盖。
- **[编辑]**：人工修改后保存，保存即生效，不需要定稿。
- **批量入口**“自动生成本集 / 全部剩余”：**只填空白的步骤，不覆盖已有内容**。系统在这里唯一的规则就是“不覆盖人写的东西”。
- **保存某一步时不会动下游**，不打标记，不清任务，不触发重拍。要不要重新生成下游、要不要重拍，都由人点按钮决定。

### 3.3 后台自动化只做机械工作

保留“自动生产”，但只负责不需要判断的事情：

| 保留 | 删除 |
|---|---|
| 为缺图的角色出定妆图 | 自动生成规划、自动定稿 |
| 按分镜提交还没有任务的镜头 | 需复核标记、级联暂停、`cascade_confirmed` |
| 失败自动重拍一次，仍失败则暂停，并写明哪集哪镜、错误信息 | 按“上游已变化”阻止提交（`episodeReviewIssue` 的复核部分） |
| 一集镜头全部完成后合成成片 | — |

### 3.4 Skill 分工

| Skill | 负责 | 不负责 |
|---|---|---|
| 导演 `director-*` | 风格、题材、人物塑造、声音、禁忌、**集数与单集时长**、镜头语言 | 视频模型的提示词格式 |
| `drama-planning` | `steps/series.md` 剧情总览；`steps/script.md` 单集剧本（场景 + 行，无时间码） | 集数（取自导演 Skill）、分镜 |
| `shot-planning` | `steps/storyboard.md` 分镜（引用行，只写怎么拍）；`steps/shot-prompt.md` 提示词（台词用占位符，附模型格式范例） | 改写剧情和台词 |

生成时，代码只负责把“上游内容 + 本步说明 + 导演 Skill”拼接起来，并做结构解析，确保 ID 能对应上、格式能读取。解析失败时，把错误原文返回给人，不做内容判断。

### 3.5 项目列表

| 字段 | 来源 |
|---|---|
| 名称、导演、题材 | `project.json` |
| 集数 N | 剧情总览的分集条目数，即导演 Skill 规定的集数 |
| 成片 M/N | 各集是否已有 film 交付物 |
| 状态 | 未开始 / 进行中 / 已暂停（附原因）/ 已完成，只根据生产事实计算 |
| 主演 | 总览中角色的“主角”标记（新增一个布尔字段，由人勾选或生成时给出） |

## 五、迁移路径

1. **修 Skill**（无代码改动）：按第一节修改导演 `script.md`、`drama-planning`、立项指令。验证 AC-1。
2. **去版本、去复核**：每一步只保留当前内容，迁移时取原来的定稿版本（没有定稿则取最新版本）。删除 `finalize`、`needs_review`、`based_on`、级联暂停，后台只保留机械生产；加上“自动生成只填空”的规则。迁移前备份 `planning.json`。验证 AC-3、AC-4、AC-6。
3. **剧本与分镜解耦**：时间线转为剧本行，去掉时间码，每行分配 ID。分镜对白按文本匹配到行 ID（现有校验已保证分镜对白逐字来自时间线，可以无损匹配）。提示词和字幕改为从剧本行取台词；已有提示词里的原文台词保持原样，新生成的使用占位符。删除 `service.js:26` 重复拼接的场景描述。验证 AC-2、AC-5、AC-6。
4. **列表与主演**：总览角色增加主角标记，列表按第 3.5 节显示。

注意：未提交的“剧本页布局”改动建立在版本和定稿机制之上（按版本保存、定稿、`auto_finalize`）。第 2 步会让其中与版本相关的部分失效，建议先合入它的布局部分，再开始第 2 步。
