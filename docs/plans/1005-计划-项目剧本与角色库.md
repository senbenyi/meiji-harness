## 2. 方案

### 2.1 剧本作为参考

- 剧集摘要的生成、修订、审核统一按「参考」处理，资料优先级为：
  1. 用户本次要求（`requirements` / 修改意见）
  2. 已发生的剧情（前集摘要，以及本集修订时的基稿）
  3. 项目剧本（当前版本）：决定具体情节
  4. 故事基调（2.2c）：决定题材、风格、人物基调和整体走向；与剧本冲突时，情节按剧本，风格按基调
  5. 项目摘要（AI 维护的全剧概要）
- **生成**：有剧本时优先沿用剧本的情节顺序推进，本集篇幅按时长控制；已发生的剧情与剧本冲突时以已发生的为准，再把剧本后续内容调整到与之衔接，不强行回到原剧本走向。
- **审核**：
  - 不判失败：剧本里没有的事件、与剧本不同的走向。
  - 判失败：与前集事实矛盾、违背本次要求、本集时长明显装不下、没有取得剧情进展。
- 涉及：`server/prompts/models/episode-summary-model.js`（任务文案与资料用途说明）、`skills/task/generate-episode-summary-skill.md`、`skills/review/review-episode-summary-skill.md`。改 skill 正文要按 `meiji-dev.md` 第 12 节做提示词前后对比。
- 大纲 Model 已把剧本作为背景、以本集摘要为准（`story-model.js:25`），只需核对用语是否一致。

### 2.2 剧本是全剧总稿（版本、同步与改剧情）

**原则**：剧本是全剧唯一的总稿，剧集、剧本、项目摘要三者以剧本为准保持同步：
- 剧集从剧本来；剧集变化回写剧本。
- 剧本每次变化都生成新版本；项目摘要只在剧本版本增加时更新。
- 要改后续剧情，先改剧本，再按剧本生成剧集。

**两种剧本**（`scriptKind`，取决于项目有没有导入剧本）：

| | 导入的剧本 `imported` | 拼接的剧本 `assembled` |
|---|---|---|
| 来源 | 创建时导入或从素材库选择，复制进项目成为第 1 版 | 没有导入剧本的项目自动使用；初始为空 |
| 结构 | 一整篇正文 | 按集分节：`sections: [{ episodeId, text }]`，再加末尾的「后续剧情」`future`（选填，写还没拍的方向）；正文由程序按「第 N 集 … 后续剧情 …」拼出 |
| 新增剧集后 | AI 生成修改方案回写（剧集超出剧本时等于追加） | 程序把该集摘要作为新的一节接到末尾，不调用模型 |
| 修改剧集后 | AI 生成修改方案回写 | 程序替换该集小节；之后再由 AI 核对「后续剧情」是否与之冲突，有冲突才生成修改方案 |
| 删除剧集后 | 不改剧本（只提示） | 程序删除该集小节 |

拼接剧本的小节由程序维护，不靠在正文里找标记，所以替换不会出错。

**版本与修改记录**：
- 项目上保存当前剧本：`script`（拼出的正文）、`scriptKind`、`scriptSections`（拼接剧本）、`scriptRevision`、`scriptSource: { assetId, name }`（导入剧本）。素材库原文件永不改动。
- 每个版本存一份记录 `history/script-revisions/<revision>.json`：
  ```json
  {
    "revision": 3, "content": "完整剧本正文", "sections": [ "拼接剧本的分节快照，导入剧本为空" ],
    "createdAt": "ISO 时间", "actor": "human | model | program",
    "source": "import | edit | ai-edit | episode-append | episode-sync | episode-delete | restore",
    "episodeId": "触发的剧集，可空", "operationId": "…", "taskId": "…",
    "note": "修改说明", "changes": [{ "before": "原段落", "after": "新段落" }],
    "stats": { "added": 320, "removed": 180 }, "restoredFrom": "可空"
  }
  ```
- 每个版本存完整正文，恢复和对比直接读取。导入剧本建第 1 版；拼接剧本在第一集保存时建第 1 版。
- 剧集记录生成时依据的版本：`episode.summary.basis = { scriptRevision }`。

**修改剧本的方式**（都生成新版本）：
1. **人工编辑**：
   - 导入剧本整篇编辑；拼接剧本按小节编辑：某一集的小节，或「后续剧情」。
   - 保存时必须填写修改说明。
   - 改某一集的小节等于改这一集的摘要：保存后同步到剧集摘要，该集下游按现有规则标为过期。
2. **按要求修改（AI，小范围）**：
   - 输入修改要求，AI 生成修改方案 `{ note, changes: [{ before, after }] }`。
   - 要求只改必要的段落；审核检查有没有改动无关内容。
   - 确认前，方案里的每条修改都可以单独取消，只写入保留的部分。
3. **剧集回写**：见上表和下文。
4. **恢复旧版本**：把某个历史版本复制为新版本，不删除任何版本。

**剧集回写与核对**：
- **触发**：新增、人工编辑、按意见修改、重新生成剧集摘要并保存后。按第八轮决定，回写总是执行，不再提供「不同步」选项。
- **拼接剧本**：程序直接追加、替换或删除小节。改的不是最后一集、或者有「后续剧情」时，再执行一次 AI 核对。
- **导入剧本**：执行 AI 核对与回写。
- **AI 核对**：同一操作里的第二个任务 `script-sync`，与「按要求修改」共用剧本修改 Model（`script-revision-model.js`）。
  - 输入：当前剧本、这一集修改前后的摘要、前后集摘要。
  - 输出：`{ consistent, note, changes }`。与剧本走向一致且不需要修改时，`consistent: true`，`changes` 为空，不生成版本。
  - 需要修改时，`changes` 中的每个 `before` 必须逐字取自剧本，并能唯一定位；只改本集对应段落，以及后续必须跟着调整的冲突段落。
- **人工编辑剧集摘要的核对结果**会显示在剧集弹窗里（U4）：
  - 一致 → 直接完成。
  - 不一致 → 列出冲突，并给出三个选择：「按方案修改剧本」「把本集改回符合剧本」（按冲突说明修订本集）、「先保留，稍后处理」。选「先保留」时，剧集标「与剧本不一致」。
- **写入**：
  - 程序对拼接剧本的追加、替换、删除直接写入，不需要确认。
  - AI 生成的修改方案在面板对比、逐条确认后写入（决定 16）。
  - 同步失败不回退已保存的剧集。

**改后续剧情的入口**（用户问题：剧情发展到一定程度想改走向）：
1. 在项目概要的剧本卡片或剧本页点「修改后续剧情」。
2. 选择从第几集之后开始改（默认最后一集之后）。可以手写，拼接剧本写进「后续剧情」，导入剧本直接编辑对应段落；也可以输入要求，让 AI 生成小范围修改方案。
3. 对比确认后写入新版本，项目摘要变为待更新。
4. 之后新生成的剧集按新剧本发展。改动点之后已经生成的剧集标「剧本已更新」；剧集详情提供「按当前剧本重新生成本集摘要」。批量重新生成放第二期，会话可以逐集执行。

### 2.2b 项目摘要由 AI 维护

**定义**：项目摘要是 AI 从**当前版本的剧本**浓缩的「全剧概要」，最多 1000 个非空白字符（原为 500）。它概括主线、主要人物、已发生的进展和后续走向。用户不手动编辑，只能要求重新生成（可附意见）。
- 拼接的剧本由各集组成，所以概要自然包含「剧情至今」。

**只在剧本版本增加时更新**：
- `summary.basis = { scriptRevision }`。剧本版本号大于依据的版本时，项目摘要显示「待更新」。
- 需要项目摘要的生成操作（剧集摘要、剧情）开始时，如果项目摘要待更新，先在同一操作里插入「更新项目摘要」任务，再执行原任务。面板也提供「立即更新」。连续多次改动只更新一次。
- 更新任务复用 `project-summary` 任务、Model 与 skill。输入为当前剧本和故事基调；剧本为空时不执行（没有导入剧本的项目在第一集之前没有项目摘要）。
- 长度上限改为 1000：修改 `shared/script-content.js` 的 `projectSummaryFailures`，同步修改生成与审核 skill。

**创建项目**：
- 只填标题、风格、画幅，剧本可选，没有摘要输入框。
- 没有导入剧本时，第一集需要用户给出方向：第一次生成时填写的「本次要求」会保存为「故事基调」（2.2c）。也可以直接手写第一集摘要。
- 创建页「剧本摘要预生成」（现状 6b）不再需要，相关代码删除：弹窗里的草稿生成、没有项目的草稿操作分支、`project-drafts` 记录与发布逻辑。这会撤回今天刚完成的「1005-计划-创建页剧本摘要预生成」的大部分改动，但创建页显示「剧本」标题与文件名的部分保留。

**不再连锁过期**：项目摘要更新、剧本出新版本都不让剧集过期。修改 `overviewPatch`（现状 14）：只有画幅、风格变化时，才保留「所有剧集图片、视频过期」的规则。

**提示词**：【项目摘要】说明为「全剧概要」，为空时省略。生成剧集摘要时同时提供剧本：导入剧本为全文；拼接剧本为各集小节加「后续剧情」。

### 2.2c 故事基调（第一次的要求）

- **问题**：没有剧本时，只有第一集需要「本次要求」来定方向。但「本次要求」只作用于本次任务；如果不保存，第一集之后就只剩 AI 写的概要，题材、风格和想要的结局容易逐集走偏。
- **做法**：项目新增 `premise`（故事基调，最多 1000 字），是用户的创作意图，不是剧情概要，所以由用户填写，AI 不改写。
  - 没有剧本、没有基调、还没有剧集时，生成第一集必须填写「本次要求」，并默认勾选「保存为故事基调」。
  - 之后各集的「本次要求」都是选填，只作用于该次生成。
  - 基调可以在项目概要里随时编辑；有剧本时选填（例如补充「整体偏喜剧」）。
  - 修改基调后，项目摘要显示待更新，已有剧集不过期。
- **用途**：作为【故事基调】进入剧集摘要、剧情和项目摘要更新的提示词，优先级见 2.1。会话查询返回它；会话在用户第一次要求生成且没有剧本、没有基调时，先用 ask_user 问清基调。

### 2.3 项目角色库与造型

结论：同一角色 + 新造型（评估见附录 A）。剧情里确实是另一个人（双胞胎、替身等）时，才新建角色。

**JSON 结构**：角色层只放不随时间变化的字段（name、aliases、nationality、gender）。随年龄、经历变化的字段都放造型层，其中 `role`（身份）也放造型层，因为身份会随剧情变化（学生 → 医生）。

```json
"characters": {
  "items": [
    {
      "id": "R01", "name": "旅人", "aliases": [],
      "nationality": "中国", "gender": "男性",
      "required": false,
      "looks": [
        {
          "id": "R01-1", "label": "三十岁",
          "role": "赶路的旅人", "era": "古代", "age": "三十岁", "costume": "深灰长衣",
          "height": "一米八", "build": "结实", "features": "方脸，浓眉",
          "appearance": "三十岁男性，结实，方脸浓眉", "prop": "铜灯",
          "identity": "赶路的旅人，右手提铜灯",
          "look": "国籍：中国\n姓名：旅人\n身份：赶路的旅人\n…（十行，由程序按角色与造型字段组装）",
          "image": { "localPath": "…", "assetId": "…", "source": "ai" },
          "createdFrom": { "episodeId": "…", "cardId": "C01" }
        }
      ],
      "defaultLookId": "R01-1"
    }
  ]
}
```

- **剧集角色卡**：保留现有全部字段，外加 `ref: { characterId, lookId, linkedBy: 'name' | 'model' | 'human' }`。卡片 ID（C01…）不变，下游不用改（现状 11）。
- **人物输出协议**（模型返回）：每个角色在现有字段之外增加三个字段：
  - `characterId`：库中已有角色填它的 ID，新角色为 null。
  - `lookId`：沿用已有造型填它的 ID，否则为 null。
  - `lookLabel`：新造型的名称，`lookId` 为 null 时必填。

  模型照常输出完整字段，卡片结构和现有解析不变。
- **程序规则**：
  1. `characterId` 与 `lookId` 都有效 → 卡片的造型字段以角色库为准，图片取自造型，`linkedBy: 'model'`。
  2. `characterId` 有效、`lookId` 为 null → 用卡片字段在该角色下新增造型。
  3. `characterId` 为 null，但名字或别名与库中角色完全一致 → 自动关联到该角色的默认造型，`linkedBy: 'name'`。
  4. 都不满足 → 新建角色（R 编号）和第一个造型。

  并入角色库的时机：人物资料通过审核并最终保存时。
- **自动关联依据「名字 + 剧情」**（用户决定）：资料中增加【项目角色库】，列出各角色的名字、别名、各造型的身份与外貌。审核时检查关联到的是不是同一个人、选的造型是否符合本集剧情。
- **人工修改**：面板可以关联到其他角色、改用其他造型、解除关联、合并重复角色。改动后同步卡片字段与图片，下游按现有规则标为过期，留有历史记录。
- **图片**：
  - 关联造型已有图片的卡片 → 直接使用，不生成也不用确认；批量图片和基座计划的 `images.missing` 都不包含这些卡片。
  - 为关联卡片确认的图片写回造型，同一造型的其他剧集卡片同步更新，受影响的视频标为过期，并提示受影响的集数。
- **附属素材**：`clothes、props、hairstyles` 和 `parts` 槽位本期仍留在剧集卡片上。

### 2.4 指定照片

- 角色库支持手动新建角色，并为造型导入照片或从素材库选图。照片造型 `image.source: 'photo'`，不经生成，不用确认。
- 标为 `required: true` 的角色作为【指定角色】写入剧集摘要和大纲的资料，要求按名字和身份写进剧情；人物提取按名字或别名直接关联。
- 想让剧本里的某个角色用照片时，在该角色的 `aliases` 里填剧本中的名字即可。

### 2.5 场景库说明（第二期）

- **作用**：同一个地点会在多集出现（比如「林家客厅」在第 1、3、7 集）。现在每集都重新提取场景卡、重新生成场景图（现状 12），带来两个问题：
  - 同一个客厅每集长得不一样，画面不连贯。
  - 每集重复生成，浪费费用，还要重复确认。
- 场景库就是把角色库的机制用在地点上：同一地点跨集复用描述和图片；地点的不同状态（白天/夜晚/被砸之后）对应造型。
- 本期只做角色。关联、并入、图片回写写成通用规则（`shared/library-rules.js`），第二期场景库直接复用。

### 2.6 界面与交互（UI/UX）

整体原则：
- 只有基调由用户手写；项目摘要由 AI 维护，界面不提供手动编辑。
- 所有「已更新、需核对、待更新」都只是提示，不拦操作。
- 需要模型的按钮遵守项目互斥（基座计划 6.2），有生成在跑时禁用并显示原因。

**U1 创建项目弹窗**（`client/project-session-view.js`）
- 字段：短剧标题、画幅、风格、剧本（导入 / 从素材库选择 / 移除，显示「剧本」标题与文件名）。
- 删除：摘要输入框，以及剧本摘要预生成的状态、重试与回填。
- 提示文字：「没有剧本也可以创建；生成第一集时告诉 AI 你想要的故事。」
- 创建成功后进入项目概要页。

**U2 项目概要页**（`client/project-overview-view.js`），卡片顺序：
1. **标题行**：编辑按钮打开「编辑项目」，可改标题、画幅、风格，不再有摘要。
2. **故事基调**：
   - 显示 `premise`，带编辑按钮。
   - 为空时显示「还没有基调。没有剧本时，生成第一集填写的要求会保存在这里」。
3. **项目摘要（AI 维护）**：
   - 正文与状态标签：最新 / 待更新（列出原因，如「第 2 集已修改」「剧本更新到第 4 版」）/ 更新中 / 失败（显示原因）。
   - 按钮：「立即更新」「按意见重新生成」（弹出意见框）、「查看任务历史」「查看 skill」。
   - 为空时显示「生成第一集后，AI 会在这里维护全剧概要」。
4. **剧本**（每个项目都有）：
   - 显示「第 N 版 · 更新时间」、类型（导入：显示来源文件名；拼接：显示「由各集自动拼接」）、正文预览、「待确认方案 N 个」标记。
   - 按钮：「打开剧本页」「修改后续剧情」。
   - 没有导入剧本的项目在第一集之前显示「还没有剧本，第一集保存后会自动生成」。
5. **角色库**（P4 起替代现在的「人物角色」栏）：
   - 横向列表：默认造型的头像、名字、造型数量；缺图的造型标「需要图片」。
   - 点击进入角色详情页（U6）。
   - P5 增加「新建角色」按钮。
6. **剧集**：
   - 剧集卡片上的提示标记：「剧本已更新」（依据的版本低于当前版本）、「前集已修改」。
   - 「＋ 新增剧集」沿用现有入口。

**U3 剧本页**（新增 `client/script-view.js`，从剧本卡片进入，返回到概要页）
- **页头**：「剧本 · 第 N 版」，以及来源（导入的文件名，或「由各集自动拼接」）。
- **正文**：
  - 导入剧本：整篇只读显示，带「编辑」按钮。
  - 拼接剧本：按小节显示（第 1 集、第 2 集……、后续剧情），每节有「编辑」按钮；编辑某一集的小节会同步改该集摘要。
  - 保存时必须填写修改说明，显示字数（上限 200000）。
- **修改后续剧情**：
  1. 选择从第几集之后开始改。
  2. 手写（拼接剧本写入「后续剧情」）或输入要求让 AI 生成方案。
  3. 进入方案确认。
- **方案确认**（按要求修改、剧集回写、修改后续剧情共用）：
  - 修改说明，以及逐条「原文 / 新段落」对照，每条带复选框，默认全选。
  - 操作：「写入选中的修改」「放弃」「按意见重新生成」。
- **待确认的方案**：列出来自剧集回写的方案，显示关联剧集（可点击跳转），进入方案确认。
- **版本记录**：
  - 表格列：版本、时间、来源（导入 / 人工编辑 / 按要求修改 / 新增剧集 / 剧集回写 / 删除剧集 / 恢复）、修改说明、关联剧集、增删字数。
  - 每行可「查看」「与当前对比」「恢复为新版本」（二次确认）。
- **版本对比**：任意两版，按段落显示新增与删除。
- **忙碌状态**：项目有生成在跑时，AI 相关按钮禁用；人工编辑按互斥规则处理。

**U4 剧集弹窗**（新增 / 编辑剧集，`episodeDialog`）
- 字段：本集时长、本集剧情摘要，新增「本次要求」（AI 生成时使用）。
  - 没有剧本、没有基调、还没有剧集时，「本次要求」必填，标签显示「故事设想（必填）」，提示示例：题材、风格、主角、核心冲突、想要的结局。
  - 其他情况选填。
- 复选框「保存为故事基调」：只在上述第一集场景出现，默认勾选。
- 「AI 生成」依据当前剧本、故事基调、前后集和本次要求。
- 保存后：
  - 弹窗显示回写与核对的进度（「保存剧集 → 回写剧本」）。
  - 一致或程序直接回写成功：显示「剧本已更新到第 N 版」，然后关闭。
  - 不一致：弹窗内列出冲突，提供「按方案修改剧本」（进入 U3 方案确认）、「把本集改回符合剧本」「先保留，稍后处理」。

**U5 剧集详情页的摘要区**（`client/generation-stage-views.js`）
- 显示「本集基于剧本第 2 版，当前第 4 版」「前集已修改，可能需要核对」，并提供「按当前剧本重新生成本集摘要」。
- 显示「与剧本不一致」标记（来自 U4 的「先保留」），并提供「按方案修改剧本」「把本集改回符合剧本」。
- 「按意见修改」保存后，同样执行回写与核对，结果显示方式同 U4。

**U6 角色详情页（角色库）**（P4、P5，新增 `client/character-library-view.js`）
- **基本信息**：名字、别名（可编辑，用于匹配剧本里的名字）、国籍、性别、「必须出场」开关。
- **造型列表**：每个造型显示名称、外貌字段、图片与来源标记（AI / 照片），可以：
  - 导入照片、从素材库选图、AI 生成（候选图需确认）；
  - 编辑外貌；
  - 设为默认造型。

  另有「新增造型」。
- **出场记录**：列出关联的剧集与卡片，每行显示所用造型，点击跳到对应剧集的角色卡。
- **操作**：「合并到其他角色」（选择目标角色，确认后迁移造型与关联）、「删除角色」（只有没有关联时可用）。

**U7 剧集角色卡**（`client/asset-cards.js` 的角色详情）
- 顶部显示关联标签「角色库：林晓 · 少年」，点击进入 U6。
- 操作：「改关联」（从角色库选择）、「改造型」、「解除关联」（作为新角色）。
- 所关联造型已有图片时，隐藏「生成图片」，改为显示「来自角色库造型」；需要不同外貌时，引导到 U6 新增造型。

**U8 新建角色弹窗**（P5）
- 字段：名字、别名、国籍、性别、第一个造型的名称与外貌、照片（可选）、「必须出场」。

**U9 会话**（P6，依赖基座计划）
- 第一次生成、且没有剧本也没有基调时，先用 ask_user 问基调。
- 改剧本可以发起人工文本修改或按要求修改。
- 同步方案和按要求修改的方案需要面板确认时，登记等待 job，提示用户到剧本页处理（同基座计划的图片确认）。

## 5. 用户决定与评估结论（2026-10-05）

| # | 问题 | 结论 |
|---|---|---|
| 1 | 年龄或外貌变化 | 同一角色 + 新造型（附录 A）；人物 JSON 按 2.3 修改 |
| 2 | 判断是否同一角色 | 按「名字 + 剧情」自动关联，人可以修改 |

## 7. 风险

| # | 风险 | 应对 |
|---|---|---|
| R1 | 模型把不同的人判为同一角色，或把同一个人判为新角色 | 名字或别名一致时优先关联；模型判定经审核；面板可以修改与合并 |
| R2 | 剧本改为参考后，模型可能过度偏离剧本 | 生成时要求优先沿用剧本的情节顺序，只在与已发生剧情冲突时调整；提示词对比时检查 |
| R3 | 长剧本每次整份传入，可能超过请求容量（现状 5） | 本期先记录；第二期做长剧本浓缩 |
| R4 | 只带上一集摘要，更早的改动可能在多集后丢失（现状 4） | 剧集同步会把改动写进剧本，后续剧集从剧本获得长期方向；第二期再评估「剧情至今」 |
| R8 | 同步方案的 `before` 与剧本原文不一致或不唯一 | 程序校验唯一匹配，失败进入自审修订；仍失败时同步任务记为失败，剧集保留，用户可以手动编辑剧本 |
| R10 | 项目摘要更新和剧集生成都要读剧本全文；拼接剧本会随集数增长 | 按需更新（只在需要时执行一次）；第二期的长剧本浓缩同样适用 |
| R12 | 每次人工编辑剧集都要做一次 AI 核对（导入剧本或有后续剧情时），增加调用次数 | 核对输出很小；拼接剧本没有后续剧情时由程序直接回写，不调用模型 |
| R11 | 撤回刚完成的创建页预生成功能，可能与另一个工具的工作冲突 | 先确认那边已提交，再在 P3 中删除；删除范围以本计划列出的文件为准 |
| R9 | 同步把剧本改得过多，或漏改后续冲突段落 | 审核检查无关改动与后续连贯性；写入前用户在面板逐条对比确认；可以随时恢复旧版本 |
| R5 | 图片回写到造型会让多集视频变为过期 | 写回前提示受影响的集数；只同步关联同一造型的卡片 |
| R6 | 项目数据结构变化 | 旧项目删除，实施前停服清空 |
| R7 | 与基座能力接入计划改动的文件重叠 | 在基座计划 J4 之后实施；开始前确认工作区没有其他进行中的改动 |

## 附录 A：年龄或外貌变化的方案评估
