# 修复链路四项优化

- 类型：完整流程，功能与Bug修复。
- 目标：停止对上游矛盾的下游空修、识别无进展、检查明确原对白、支持安全局部镜头修订。
- 非目标：按字数推算时长、增加修订额度、自动修改上游原文、重新生成现有生产内容、修改Harness源码。

## 验收标准与调研结论
| AC | 输入 → 可观测结果 | 调研状态 | 依据 |
|---|---|---|---|
| AC-1 | 审核明确定位上游矛盾 → 当前任务以未通过结束，原因指向上游及位置，不继续改下游、不覆盖正式内容 | 未验收 | task-manager.js原只有boolean/reason判断，任何拒绝统一修订 |
| AC-2 | 同一候选重复出现 → 记录无进展；重复同一确定性程序错误时提前结束，AI拒绝不因原因文字相同直接停止 | 未验收 | 原只按round与retryRounds判断 |
| AC-3 | 明确引号原对白跨拍保存 → 逐字、顺序、标点与重复检查；不明确的来源仍交AI，不猜测补写 | 未验收 | seconds程序只验证时轴，删句号仍通过 |
| AC-4 | 按镜头ID更新字段 → 程序合并完整候选并全表审核，未改镜头保持；错误/重复ID拒绝，无mode的片段不能隐式删镜 | 未验收 | regenerate要求返回全表，replaceShots整表替换 |
| AC-5 | 错误、取消、耗尽与历史兼容 → 原状态/凭据/旧正式内容不被意外覆盖，所有新通路有隔离测试 | 未验收 | 文本候选与正式保存分开 |

## 调用链与证据
面板任务 → TaskService.run → createTextHandler → taskNodeInput → createAiRoutes(nodeAction/compose/validate) → prepareContent → 程序审核/AI审核 → commitOutput。局部修订必须在响应校验和prepareContent前合并为完整表，所有后续步骤继续消费完整候选；原patch保留请求响应历史。修复范围只由结构化审核问题判定，不用关键字猜测上游错误。
GitNexus meiji-harness索引为最新。impact：TaskService与nodeAction为HIGH、createTextHandler/taskNodeInput/validateNodeResult为MEDIUM，renderPrompt/nodeRules/replaceShots为LOW。高风险已告知。动态route对象调用按源码补查，不当作无影响。

## 待用户决定
无。上游只定位并停止，不自动改写。AI同文拒绝只给定向提示，不直接当作无解。

## 实施阶段
1. 新review-policy公共契约：可选结构化问题和明确来源；更新实际渲染/规则查看及校验，拒绝非法来源与自相矛盾的通过结果 → AC-1/5。
2. repair-policy与TaskService：上游停止、确定性无进展提前终止、AI无进展定向反馈，沿用已有rejected状态、记录步骤诊断；taskNodeInput带反馈 → AC-1/2/5。
3. 明确原对白程序检查：仅能确定来源的引号台词，按时间线顺序拼接逐字核对，不用字数推时长；未明确的旁白不作机械假设 → AC-3。
4. shots局部patch契约、程序安全合并、完整候选审核；明确全表替换，修订提示改成局部优先 → AC-4。
5. 回归测试和业务文档，检查完整diff、detect_changes，最后集中刷新GitNexus → AC-5。
