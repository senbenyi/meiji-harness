## 2. 规格决策与缺口

### 2.1 子代理形态（未确认，已询问）

总工作流新增“剧本重要角色和定妆照放在同一个子代理里”，但任务组章节和定妆照 dots 仍规定“提取只写资料，不派生图片；人物卡单独提交”。需要确定：

- 是独立业务执行器，还是实际 Harness 子代理会话。
- 是否继续由人物卡明确发起图片任务，还是新增自动生成全部人物图片的入口。
- 图中的分支是职责划分还是要求实际并行。未确认前保留同项目串行写入，不假定两个代理可直接并发改项目。

本计划的确定部分：不论采取哪种形态，子代理都提交现有任务服务，不能自行写 Model、直接结算任务或在缺少明确入口时自动扩展生产任务。

### 2.2 缺定妆照时的视频类型（已确定并实施）

按用户后续“执行”指令采用：有角色必为多模态；缺定妆照不阻断逐镜文本，但视频等待补图，不自动降级。无角色的首镜文生，后镜首尾帧。

确定部分：每秒分镜和文生提示词不能因图片缺失阻断；首镜不能使用上一镜尾帧；同一请求不能混用三种类型字段。

### 2.3 素材引用口径（已确认需修正文档）

总工作流、定妆照 dots 和现行角色 Model 已采用“首套定妆照作为默认角色图”，不再有独立 character_image。旧逐镜 dots 仍要求 character_image 加 costume_image。按最新总工作流统一：明确服装使用对应定妆照；无服装使用 costume_id 为空的图片；按实际图片去重。同步移除逐镜文档中的独立角色图要求，不恢复已删除节点。

### 2.4 镜头身份绑定和其他旧计划内容

旧镜头计划明确记录独立识别节点已获选择，当前总工作流与 dots 尚未将其列出。阶段 0 将补齐规格入口，不将空 on_screen_characters 当成“已确认无人”。已识别但服装未决与确无服装分别处理，不使用数组第一套掩盖未决。

当前每秒分镜 dots 同时写“从0连续覆盖”和“钩子追加亚秒格”，有重叠歧义；沿用旧计划的非重叠拆分方案作为拟议细化，在实施前同步 dots。旧计划额外时间轴缩放、标签命名扩展未经本轮工作流明确要求，不在此引入。

## 3. 目标执行流程

```text
剧本 → 提取剧集 → 故事大纲 → 镜头表 ─────┐
             └→ 角色分支：角色提取 → 定妆照 │
                             角色资料必需 ──┤
                                            ↓
                  镜头角色/服装识别（既有已记录决策）
                    → 每秒分镜 → 文生视频三段
                    → 程序判定视频类型
                        文生：不创建提示词编排任务
                        首尾帧：程序编排首帧请求
                        多模态：程序编排图片引用请求
                    → 视频生成
                    → 同任务视频校验/实测/截帧/尾帧校验
                    → 程序审核，必要时同任务修订
                    → 成对提交视频、实测时长、尾帧
                    → 满足整集条件时唯一合片
```

项目摘要、剧集摘要保留独立旁路，不新增主线前置。定妆照是否阻断视频由 2.2 的结论确定，不阻断逐镜文本。角色分支是否自动运行及并行由 2.1 确定。

## 4. 节点路由、输入、输出与审核

继续采用“一套节点接口、模型来源内部选择”，输出格式只在路由契约定义。表中输入为业务字段集合，正式英文字段在实施时沿用当前命名；生成不传无关历史、图片或整份 project。

| 节点 | 最小业务输入 | 输出 | 执行/审核 |
|---|---|---|---|
| 项目摘要 | 剧本、语言、规则、补充需求 | 摘要正文 | 文本 AI；AI 审核 |
| 提取剧集 | 剧本、参考单集时长、语言、规则、补充需求 | 分集切点；程序按原文拼接 | 文本 AI；程序审核 |
| 剧本重要角色 | 剧本、现有角色目录、语言、规则、补充需求 | 人物和服装资料 | 文本 AI；AI 审核 |
| 定妆照 | 人物描述、服装描述、可选唯一参考图、画幅、规则、补充需求 | 图片候选 | 图片 AI；无审核 |
| 剧集摘要 | 本集剧情、语言、规则、补充需求 | 摘要正文 | 文本 AI；AI 审核 |
| 故事大纲 | 本集剧情、参考时长、本集要求、语言、规则 | 故事小段 | 文本 AI；程序→AI 审核 |
| 镜头表 | 小段、参考时长、角色服装文字、已有镜头编号、语言、规则、补充需求 | 镜头九字段 | 文本 AI；程序→AI 审核 |
| 镜头角色/服装识别 | 本镜内容、有效角色服装目录、实际使用的前镜穿着依据、规则 | 已有角色/服装的编号绑定，程序映射 ID | 文本 AI；程序→AI 审核；补写当前工作流 |
| 每秒分镜 | 本镜九字段、已确认绑定、对白身份目录、语言、规则、补充需求 | storyboard[] | 文本 AI；程序→AI 审核，±5秒，共用两次修订 |
| 文生视频提示词 | 已通过每秒分镜、参考时长、必要说话人文字资料、规则、补充需求 | 固定三段文本 | 文本 AI；AI 审核，不读图片/前尾帧 |
| 首尾帧编排 | 三段、计划时长、画幅、上一镜有效尾帧 | 带 input_reference 的请求数据 | 程序，不调用文本模型 |
| 多模态编排 | 三段、计划时长、画幅、本镜绑定的有效定妆照 | 带 reference_images 的请求数据 | 程序，不调用文本模型 |
| 视频 | 程序确定的类型和该类型所需的业务资料；修订另带本轮意见 | 媒体候选；任务后处理形成视频/时长/尾帧配对结果 | 视频 AI；程序审核，±5秒且4–15秒，最多两次修订 |
| 合片 | 按镜头顺序的有效视频列表 | 合片地址 | 程序，无 AI 审核 |

审核路由：业务依据 + 待审核候选；修订路由：业务依据 + 当前候选 + 对应意见。生成/审核/修订使用同一个节点输出契约体系，不允许请求覆盖输出格式。审核输入按实际需要携带本轮意见，不能混入未来轮次或其他任务。

程序节点注册在任务执行目录，使用明确输入/输出契约；不为它创建 PromptModel 或虚假的 AI review，也不通过 `/ai/` 调用文本模型。既有 AI HTTP 路由返回候选，正式项目写入、文件后处理、审核结算仍经 TaskService；视频 HTTP 媒体返回与视频任务产物应在契约中明确区分，不能把“下载到字节”当作正式生成成功。

### 阶段 1：角色分支及逐镜入口

### 阶段 2：文本输入与程序审核

- `http/nodes/{seconds,storyboard}.js`、对应 `prompts/models/` 和 `composers/`、`handlers/node-inputs.js`：收窄输入，移除图片状态和无关前镜资料；按路由输出生成和校验。

- 提供提示输入与依赖计算共用的实际资料投影，避免修改了模型看到的资料却不更新依赖。

验证：±5边界、连续/重叠时间格、程序与AI共用两轮；中文项目仍输出英文画面描述并保留原对白；提示词不含图片/尾帧编排指令。→ AC-3/5/6

### 阶段 3：类型判定与程序编排

- 新增具体 `server/handlers/video-prompt-handler.js`，注册两个固定程序业务，复用已有 first_last_frame_prompt/multimodal_prompt Model。
- 类型在成片实际执行入口写入；文生即使不创建编排任务，也必须有写入 video_generation_type 的入口。
- `TaskService` 按运行时已确认绑定和素材状态物化唯一适用分支；提交时不依据未生成的空数组固定类型。事务内处理顺序、重复提交与潜在分支占用。
- `http/nodes/video.js`、视频编排器、`ai-routes.js`、`gateway/model-gateway.js`：按类型白名单组装请求。文生只三段与时长画幅；首尾帧只加前尾帧及规定对齐行；多模态只加实际定妆照数组。初次发送保留三段原文，不再次套完整角色/系统正文。
- 生成视频的修订只附加本轮意见，不改已通过三段，不额外调用文本模型，不发网关未支持的参数。

验证：文生不创建 pack；程序编排零模型调用；三个 HTTP 请求字段严格互斥；首镜、镜头重排、缺图/缺尾帧、9张边界按确认策略处理。→ AC-7/8

### 阶段 4：视频、尾帧与审核原子结果

- `media-handler.js`、`shared/task-plan.js`、步骤 Model/标签：视频 generate/revise 后都执行文件校验、最终时长测量、截帧和尾帧校验；同一任务中记录可见后处理步骤。
- `handler-registry.js`、`node-state.js`：视频程序审核实测值，启用最多两次修订。网络/文件/截帧失败不当作时长 rejected 自动重复付费调用。
- `handlers/content.js`、Model 事务：全部校验通过才成对提交新视频和尾帧；审核耗尽保存最后配对候选为 rejected、保留原成功 hash；失败/取消不覆盖旧配对。
- 手工导入视频也执行同样的文件/实测/尾帧处理，不要求先生成 AI 文本节点。
- 从新任务目录、命令、编组和界面操作中移除独立 tail；保留 last_frame 产物字段及历史只读识别。

验证：真实 FFmpeg 临时短片验证边界、配对、损坏、截帧失败、取消和晚到响应；不得出现新视频搭配旧有效尾帧；实测累计正确。→ AC-9/10/11

- `shared/node-dependencies.js`：按实际类型计算依赖与传播；前尾帧仅影响下一镜首尾帧编排/视频，图片仅影响引用它的多模态链。

- `server/data/sqlite-store.js`、`schema.sql`、`shared/models/migrate_project_model.js`：当前代码版本为 v8；如需持久化变更则提供 v8→新版本显式事务迁移，不能复用旧计划的 v6 编号。保留媒体、已完成历史和旧请求；旧 tail 历史只读，未完成旧队列显式作废，不继续执行旧工作流。
- 绑定迁移不把旧空数组宣称为已审核无人；旧请求数据不能按新资料重建；错误回滚且有备份。

验证：图片/尾帧条件过期、排队快照恢复、单镜组与整集唯一合片、分支切换继续、DOM按钮、迁移回滚/重开/历史完整性。→ AC-8/11/12/13
