# 基座能力接入：后台任务、交互日志、工具图谱

- 类型：方案评估与计划（完整流程，实施前需用户确认第 6 节）
- 目标：会话发起的生成改用 Harness 后台任务（jobs）接收完成通知；Harness 与模型、工具之间的交互可追溯；会话按需获得 meiji 的能力说明，不被无关工具干扰。
- 非目标：不改 meiji 的操作/任务/步骤模型（见计划-操作任务节点三层模型）；不改提示词 Model 与网关。
- 依据：本机 deepseek-harness（0.1.7-rc.2）源码与文档、meiji 当前代码。

## 1. 方向评估

| # | 用户方向 | 判断 | 关键依据 |
|---|---|---|---|
| 1 | 使用基座 jobs；同一项目面板与会话同一时间只允许一个任务 | 部分正确：jobs 适合做等待与唤醒，不承担互斥（仍由 meiji 占用负责）；面板生成经会话命令登记后同样由 jobs 管理（第 9.1 节） | jobs 按发起它的 agent 会话归属，进程内存储；不提供跨会话、跨面板的互斥（packages/jobs/jobs/README） |
| 2 | Harness 与模型交互、tool 调用都要有日志 | 方向正确，但基座已覆盖大部分；缺口在 meiji 自己的网关调用和「串起来看」 | 会话 JSONL 已记录 request/header（含工具 schema）、各类 message、assistant/attempt（失败与重试）、tool/call、tool/result |
| 3 | 建 tool 图谱，由模型决定加载哪些 tools 和 skill | skill 部分已是基座现成机制；tool 动态加载与基座设计取向相反，建议改为「meiji 专用 agent preset 固定工具集 + skill 按需加载」，图谱作为维护与校验依据 | 基座按 preset 固定工具目录以保持请求缓存稳定；skill 由模型经技能目录 + `skill` 工具加载；会话中途增减工具虽有支持（developer/message 记录增减），但会改变请求前缀 |

## 2. 方向 1：后台任务（jobs）

### 现状
- 会话：`meiji_content_generate` 返回 operationId → 模型反复调用 `meiji_task_control.wait`（每次最多 25 秒，operation-manager.js `waitFor`）。
- 互斥：meiji 的剧集占用（operation-occupancy.js），面板与会话共用；同一集同一时间一个操作。

### 基座 jobs 的事实
- 工具在执行中用 `ctx.jobs.start()` 登记长任务，立即返回 `<kind>-N` id；模型用 `job_output`（可带超时等待）、`job_list`、`job_kill` 管理。
- 任务结束时：agent 忙则在下一步收到注入通知；agent 空闲则被一个 follow-up 轮次唤醒（`completionDelivery: wakeup`，`maxConsecutiveWakes` 可封顶）。
- 归属：只属于发起它的 agent 会话；无主任务对任何调用方开放。进程内存储，服务重启即消失。
- 前提：该 agent 的组合里加载了 `tool-jobs`（web 的 standard 预设已加载）。

### 方案
- jobs 只包在「会话发起的操作」外面：`meiji_content_generate` 仍经 operation-manager 发起，同时登记一个 kind=`meiji` 的 job，job 的结束跟随操作结束；job 输出写入阶段进度，结束结果只给续跑所需的状态、审核结论、失败原因。
- 取消：`job_kill` → 调用 operation-cancel 停止该操作。
- 占用（busy）：会话发起时本集被面板占用 → 登记一个「等待占用结束」的 job（不发起生成），结束时唤醒会话，由模型重新发起本步骤。
- 面板发起的操作不进 jobs，仍由 operation-manager 与面板任务视图管理。
- 互斥仍由 meiji 占用负责，是面板与会话共同的唯一判断依据。
- `meiji_task_control` 删除（wait/cancel 由 job_* 工具取代）；会话说明与工具描述同步改写。

### 需要补充
- 互斥范围：现行规则是「同一剧集」，本次表述为「同一视频项目」（更严，同项目不同集也不能并行）。需确认（第 6 节）。
- 唤醒与目标续跑叠加：job 完成唤醒 + goal 续跑会各自开启轮次，需在会话说明中约定，并评估设置 `maxConsecutiveWakes`。
- 重启：jobs 随进程消失，meiji 操作在重启时也被取消，两者一致；会话恢复后通过 `meiji_context_query` 读取状态。
- 会话目前无法生成图片和成片（生成工具只开放 summary/story/shots/seconds/storyboard 五个阶段），「生成视频」在会话里走不到底。建议同期补上图片、成片阶段（第 6 节）。

### 面板是否也改为「走会话」（2026-10-05 评估与决定）
- 纯「点击发消息给模型」：每次点击一轮模型请求、延迟、结果不确定、参数经模型转述、人工专属操作不能交给模型。不采用。
- 采用「面板生成操作作为会话命令执行」（ctx.commands，不经模型）：以会话 agent 名义登记 job，面板与会话两种来源统一由 jobs 等待与唤醒，模型知道面板发生的生成；直接操作仍由面板直接执行。详见第 9.1 节。
- 停止权限：面板命令登记的 job 与会话自己的 job 属于同一会话 agent。meiji 用 `ctx.tools.guard()` 注册工具守卫，模型对面板发起的 meiji job 调用 `job_kill` 时直接拒绝并返回原因（「面板发起的操作只能在面板停止」）；会话说明同步写明。面板停止按钮不受影响，仍可停止项目内任何操作（含会话发起的）。

### 验收
| AC | 输入/状态 → 结果 |
|---|---|
| AC-J1 | 会话发起生成 → 立即返回 job id 与 operationId；本轮可结束；操作结束时会话被唤醒并收到结果 |
| AC-J2 | 会话执行中，面板按钮置灰；面板执行中，会话发起返回「等待占用」job，结束后唤醒并可重新发起 |
| AC-J3 | `job_kill` → 对应操作取消，占用释放，面板恢复 |
| AC-J4 | 会话中不再出现 `meiji_task_control`；模型不再轮询 |

## 3. 方向 2：交互日志

### 现状
- Harness：每个会话一份只追加 JSONL（默认 Zstandard 压缩），记录 request/header（模型配置与完整工具 schema）、system/user/assistant/developer message、assistant/attempt（失败、重试、取消）、tool/call（工具名与参数）、tool/result；Web 会话界面渲染，可 `/export` 导出，会话查询工具可检索；规则「模型可见即已记录」由运行时不变量检查。
- meiji：自己的网关调用（文本、图片、视频）不在 Harness 模型请求日志里；meiji 另存提示词快照（history/prompts），并把操作日志写成 Harness 会话里的 command/run + command/done 卡片（只显示，不进模型上下文）。

### 缺口
1. 链路无法一眼串起：会话 tool/call → meiji operationId → 任务 → 步骤 → 网关请求快照，目前各存各的，没有统一关联 id 的视图。
2. Harness 会话日志是压缩 JSONL，排查时不便直接阅读。
3. meiji 网关的原始响应、耗时、重试与 token 用量记录不统一（文本有快照，图片/视频只有部分）。

### 方案
- 关联 id：tool/call 的 callId 写入 meiji 操作记录；操作 → 任务 → 步骤 → promptId 已有关联，补齐 callId 一环。
- meiji 网关统一请求日志：每次请求记录请求快照引用、模型、耗时、状态码、重试次数、用量、错误；不记录密钥、请求头与参考图 Base64（沿用现有规则）。
- 查看：面板任务详情可从步骤跳到请求快照与响应摘要；提供一个导出脚本，把指定会话的 Harness 日志与 meiji 操作记录按时间合并为可读文本。
- 不改 Harness 会话格式。

### 验收
| AC | 输入/状态 → 结果 |
|---|---|
| AC-L1 | 任一会话工具调用可查到对应 meiji 操作、任务、步骤与网关请求 |
| AC-L2 | 文本、图片、视频网关请求都有统一字段的记录，且不含密钥与 Base64 |
| AC-L3 | 导出脚本输出按时间排序的可读日志，覆盖模型请求、工具调用与 meiji 网关请求 |

## 4. 方向 3：工具图谱

### 现状
- web 的 standard 预设给每个会话加载大量通用工具（bash、文件、网页、subagent、workflow 等），人设为「coding agent」；meiji 的 4 个会话工具注册在主机层，所有预设可见。
- meiji 的会话说明是 skill：模型在技能目录看到名称与简介，按需调用 `skill` 加载正文；消息首行 `/skill-gongyong-panel-generate` 可强制加载。

### 判断
- 「模型决定加载哪些 skill」基座已支持，无需新建。
- 「模型决定加载哪些 tools」：基座刻意让工具目录在会话内稳定（请求缓存）；中途增减工具虽可行，但会改变请求前缀，且增加不确定性。meiji 只有 4 个会话工具，动态加载收益有限。

### 方案
- 新增 meiji 专用 agent preset（如 `preset-meiji`）：视频制作人设；只包含 meiji 工具、todo、skill、ask_user、jobs、压缩；不含 bash/文件写入等无关工具。新建会话时选择该预设。
- 工具图谱作为维护资产：一份数据文件描述「会话工具 → 阶段 → meiji 操作 → 任务类型 → skill」及阶段依赖（摘要 → 剧情 → 图片 → 镜头表 → 每秒指令 → 成片），用于：生成会话说明中的阶段顺序、生成工具描述、测试校验（每个阶段都有工具入口、每个 skill 都被引用）。
- 可选（不建议默认）：按图谱分组的动态工具加载，基于作用域注册在调用 agent 上增减工具。

### 验收
| AC | 输入/状态 → 结果 |
|---|---|
| AC-T1 | 选择 meiji 预设的会话只看到 meiji 相关工具，人设为视频制作 |
| AC-T2 | 图谱数据与实际工具、操作、skill 一致，测试校验 |
| AC-T3 | 会话说明中的阶段顺序与工具描述由图谱生成或校验，不再手写不一致（如「剧情整包」漏写道具） |

## 6. 用户决定（2026-10-05）

1. 互斥按项目：同一视频项目同一时间只允许一个生成操作，面板与会话共用；不同项目可并行。

## 7. 决定带出的设计（2026-10-05）

### 7.1 按项目互斥
- operation-occupancy 由「剧集」改为「项目」为单位：生成类操作从入队起占用整个项目；面板在该项目所有剧集置灰生成按钮并显示占用提示；会话发起时同项目被占用返回 busy（经「等待占用」job 唤醒后重新发起）。
- 影响：长时间的成片会锁住整个项目的生成；同项目不同集不能再并行生成。
- 待定：编辑类直接操作（改大纲、改人物文字、导入图片等）是否也按项目锁（见第 8 节）。

### 7.2 完整原始返回
- meiji 网关每次请求保存原始响应：文本模型保存完整响应正文（含流式拼接后的结果与用量），图片、视频保存网关返回的 JSON（不重复存二进制，二进制已在项目文件中）。
- 位置：`history/responses/<responseId>.json`，与提示词快照 `history/prompts` 对应，步骤记录引用；删除项目/剧集时一并清理。
- 不保存密钥、请求头与参考图 Base64；大响应按现有快照方式整体保存，不截断。
- Harness 侧模型请求与工具调用沿用会话 JSONL（已含完整 assistant 流），导出脚本合并两边。

### 7.3 会话开放图片与成片
- `meiji_content_generate` 新增阶段：`images`（为指定或全部缺图的角色、场景、道具卡生成图片，一个操作、每张卡一个任务）与 `film`（成片：每镜分镜提示词 → 视频）。现有 `storyboard` 阶段保留（成片只做分镜）。
- 新增批量图片操作 `generate/operation-images.js`，任务复用 task-character-image / task-scene-image / task-prop-image。
- 图片确认：候选图需人确认（confirm-image / discard-image 为人工专属）。会话生成图片后如何处理确认见第 8 节。
- 成片依赖：镜头表通过、每秒指令通过；分镜引用已确认的图片。会话说明与工具图谱写明阶段顺序：摘要 → 剧情 → 图片（确认） → 镜头表 → 每秒指令 → 成片。

## 8. 用户决定（第二轮，2026-10-05）

1. 面板生成操作作为会话命令执行：不经模型，以面板所属会话的 agent 名义登记 job，完成时唤醒模型告知结果。
2. 按项目互斥只约束生成操作；编辑类直接操作只锁正在生成的剧集，其他剧集可编辑。
3. 会话生成的候选图由用户在面板确认：会话登记「等待确认」job，确认或放弃后被唤醒继续。

## 9. 方案细化

### 9.1 面板生成走会话命令
- meiji 在 `ctx.commands` 注册命令 `meiji-run`（参数为操作 JSON：action、episodeId、track、itemId、mode、review、requirements 等），执行记录写入会话（command/run、command/done）。
- 面板生成请求：后端取面板所属会话的 agent（运行中则直接取，否则恢复），调用 `ctx.commands.execute(agent, '/meiji-run …')`；命令处理器经 operation-manager 发起操作（origin=panel），并以该 agent 名义 `ctx.jobs.start` 登记 kind=`meiji` 的 job，立即返回。
- 编辑、删除、导入、确认/放弃候选图、忽略自审等直接操作不变，仍由面板直接执行（不登记 job）。
- 会话发起（meiji_content_generate）同样登记 job；两种来源的 job 结束都跟随操作结束。
- 完成通知：job 结束唤醒会话模型（tool-jobs 默认 wakeup）。会话说明约定：面板发起的操作完成后只简要告知结果，不自行发起新生成，除非属于用户已要求的计划。
- 停止：
  | 谁 | 能停止什么 | 方式 |
  |---|---|---|
  | 面板停止按钮 | 项目内任何操作（面板或会话发起） | operation-cancel → 操作取消 → job 随之结束，会话被唤醒并收到「已取消」 |
  | 会话模型 | 只能停止本会话发起的操作 | `job_kill` → 操作取消；对面板发起的 job 由工具守卫拒绝（job 登记时记录来源 initiator） |
  | 其他会话 | 不能停止 | job 按会话 agent 归属，其他会话看不到 |
- 被面板停止的会话操作：会话按说明停止依赖步骤并报告，不自行重做。
- 前提：会话所用预设加载 tool-jobs（meiji 专用预设包含）；面板所属会话缺少活体 agent 时先恢复。实施时核对 `ctx.agents` 恢复接口与命令执行的取消信号。
- `meiji_task_control` 删除；会话等待改用 job 通知与 `job_output`。

### 9.2 互斥
- 生成操作：按项目占用（从入队到结束）。面板在整个项目置灰生成按钮并显示「本项目正在执行：…（发起方）」；会话发起被占用时登记「等待占用」job，结束后唤醒重新发起。
- 编辑类直接操作：只在目标剧集正被生成占用时拒绝；其他剧集照常编辑。
- 运行中输入的审核意见等草稿不受影响（沿用现规则）。

### 9.3 会话图片阶段与确认
- `images` 阶段生成候选图后，操作完成；若有待确认候选图，工具返回待确认列表并登记「等待确认」job（kind=`meiji-confirm`），面板确认或放弃全部候选后结束，唤醒会话。
- 会话说明约定：提示用户到面板确认；全部确认后再进入镜头表与成片；有放弃的卡片时报告并按用户要求重新生成。
