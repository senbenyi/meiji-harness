## 3. 状态维护（重点）

### 3.1 两类状态与三把锁

| 类别 | 内容 | 写入规则 | 证据 |
|---|---|---|---|
| **执行状态** | 步骤状态 StepStatus（pending/running/waiting/completed/failed/cancelled/skipped）→ 任务状态（`deriveTaskStatus`）→ 操作状态（`deriveOperationStatus`） | 只写步骤，任务与操作状态一律推导，任何代码不直接赋值；运行中的步骤在内存 `liveTasks`，结束写入 `history/tasks`、`history/operations` | `shared/task-nodes.js:25-95`；`server/runtime/task-state.js:23-48`；`operation-manager.js:51-66` |
| **内容状态** | 内容节点的 `status/check/error/operation/revision`（阶段 1 删除 `stale` 与 `dependencies`） | 只经 `drama-model.js` 的 `setContent/begin/finish/modelPatch` 与 `shared/content-state.js`；B4 测试静态扫描 server 目录 | `shared/content-state.js:1-12`；`shared/drama-model.js:66-80`；`tests/status-stability.test.js:87-92` |

三把锁：
1. **内存占用**（`operation-occupancy.js`）：操作级，`occupy` 早于建立任何记录（`operation-manager.js:77` 早于 `:88`），冲突时不留记录；重启后消失。
2. **内容节点 `operation` 字段**：节点级，持久化，`begin` 时已有则 409；结束时释放；重启时由 `interruptRunning` 释放。
3. **队列名额**：只限流。

本次新增的**后台任务（job）只是观察者**，不写任何状态；新增的**阻断检查（3.6）只在规划任务时判断**，不写状态。

### 3.6 剧本阻断规则（D3）

- **何时阻断**：存在 pending 的剧本修改方案，或存在「待回写」的剧集。
- **阻断哪些操作**（D8）：剧本只作用于剧集的剧情层，所以只阻断剧情层的生成，在 `planTasks` 的 precheck 中拒绝（409，`code: 'SCRIPT_PENDING'`，列出待处理的方案或剧集）：
  - 剧集摘要的生成（含草稿）；
  - 剧情；
  - 项目摘要更新；
  - `script-revise`。
- **不阻断**：
  - 镜头表、每秒指令、图片、成片：它们依赖已通过的剧情，不读剧本，剧本改动传不到这一层；剧情真被改了以后，下游按 3.7 删除；
  - 处理问题本身的操作：方案确认或放弃、重新回写（`script-sync`）、对方案所关联剧集的摘要修改或重新生成（用来「把本集改回符合剧本」）；
  - 剧集级的人工编辑。
- **解除**：方案全部处理、回写全部完成后自动解除。会话通过 `meiji-script` 等待 job 得到通知后继续（6.1）。

### 3.7 流水线下游删除规则（D9）

**原则**：上游一改，下游直接删除，不标过期，不做新鲜度比对。删除后为未生成，需要重新生成。删除只清项目数据：任务历史（含当时的提示词、产物快照）与素材库文件保留。

**单集流水线**（L0 → L7）：

| 层 | 内容 | 依赖 |
|---|---|---|
| L0 | 剧集摘要、本集时长 | 剧本、项目摘要、基调、前后集（只作参考，不构成删除依赖） |
| L1 | 大纲 | L0 |
| L2 | 人物卡、场景卡 → 道具卡（含本集候选图） | L1；道具依赖人物、场景目录 |
| L3 | 镜头表 | L1、L2（实体清单） |
| L4 | 每秒指令（按镜，后镜依赖前镜的结束状态） | L3 |
| L5 | 分镜提示词（按镜） | 本镜 L4、引用实体的外观与图片、上一镜尾帧 |
| L6 | 视频与尾帧（按镜） | 本镜 L5 |
| L7 | 合成 | 全部 L6 |

「尾帧链」：第 j 镜的分镜记录了第 j−1 镜的尾帧（`tailReference`），所以第 j−1 镜的视频变化会让第 j 镜的分镜和视频失效，并依次向后传递，直到遇到不使用上一镜尾帧的镜头。

**删除规则**：

| # | 上游变化 | 删除（本集，除非另有说明） |
|---|---|---|
| R1 | 剧集摘要或本集时长变化（人工编辑、按意见修改、重新生成后保存） | L1–L7。其他剧集不删除，下一集只提示「前集已修改」 |
| R2 | 大纲变化 | L2–L7。卡片删除不影响库条目，重新提取时自动关联 |
| R3 | 人物、场景或道具任务整体重新生成或按意见修改 | L3–L7；人物或场景重新生成时，同时删除道具卡 |
| R4 | 单张卡片改名（剧集里编辑，或库条目改名） | 沿用现有的名称替换（镜头表、每秒指令中的标记）；删除引用该实体的镜头的 L5–L6（含尾帧链）与 L7 |
| R5 | 单张卡片外观文字变化（不改名） | 引用该实体的镜头的 L5–L6（含尾帧链）与 L7；图片不自动删除 |
| R6 | 卡片图片变化（导入、从素材库选、确认候选、删除图片；库条目变体图片变化） | 引用该实体的镜头的 L5–L6（含尾帧链）与 L7 |
| R7 | 删除一张卡片（如删除道具） | 被镜头表或每秒指令引用时删除 L3–L7；没被引用时只删卡片与它的候选图 |
| R8 | 镜头表整表重新生成或修改 | L4–L7（全部镜头） |
| R9 | 镜头表单镜修订（第 k 镜） | 第 k 镜及之后各镜的 L4–L6，L7 |
| R10 | 第 k 镜每秒指令变化 | 第 k+1 镜起的 L4；第 k 镜起的 L5–L6；L7 |
| R11 | 第 k 镜分镜提示词变化 | 第 k 镜 L6，沿尾帧链向后删除 L5–L6；L7 |
| R12 | 第 k 镜视频重新生成（尾帧随之变化） | 沿尾帧链删除第 k+1 镜起的 L5–L6；L7 |
| R13 | 剧本出新版本、项目摘要更新、基调变化、指导素材或补充 skill 变化 | 不删除（只影响之后的生成） |
| R14 | 画幅变化 | 全部剧集的 L5–L7；图片保留，由用户决定是否重做 |
| R15 | 风格变化 | 全部剧集的 L5–L7；图片保留 |
| R16 | 库条目在库页或剧集里被编辑 | 对每个关联剧集，分别按 R4、R5、R6 执行 |
| R17 | 合并库条目 | 改为指向目标条目的卡片，对其所在剧集按 R4、R5、R6 执行 |
| R18 | 删除剧集 | 该剧集全部数据（沿用现有规则）；其他剧集不删除，下一集只提示 |

「引用该实体的镜头」：镜头表条目或每秒指令中带有该实体 ID 标记，或分镜 `referenceSnapshot` 里含该实体的镜头。没有分镜、视频的镜头不受 R4–R6 影响。

**执行方式**：
- 新增 `shared/pipeline-cascade.js`，统一提供两个函数：
  - `cascade(project, change)`：返回删除后的补丁，以及删除清单；
  - `cascadePreview(project, change)`：只返回删除清单，用于确认提示。

  `change` 的类型对应 R1–R18。
- 现有 `replaceFrom`、`clearShotDownstream`、`staleMedia`、`seconds-results.js` 的后镜处理、`refreshReferences` 的过期标记，全部改为调用 `cascade`；`guidance-assets.js` 的过期标记删除（R13）。
- 删除与上游变化在同一次 `projectStore.save` 中完成（S14）；被删除卡片和镜头的候选图同时移除。
- 删除 `stale` 字段与 `dependencies` 字段，以及所有对它们的判断：`generation-gates.js`、`story-content.js`、`operation-story.js` 的 `completed`、`operation-seconds.js`、`generationFeedback`、`film-freshness.js` 的 `storyboardReady/videoReady/tailReady`（改为「有内容且已通过」）、`tail-frame.js`、client 中的过期显示、查询工具返回的 `stale`。

**确认提示**：
- 面板：任何会删除已生成内容的操作，开始前先用 `cascadePreview` 显示删除清单（如「将删除本集：镜头表、12 条每秒指令、3 个视频；同步影响第 2、5 集」），确认后才执行；没有内容要删时不提示。
- 会话：生成工具增加 `confirmDelete` 参数。会删除已生成内容、但没有 `confirmDelete: true` 时，工具不启动操作，只返回 `{ status: 'needs_confirmation', deletes: [...] }`；会话说明要求先用 ask_user 征得同意，再带 `confirmDelete: true` 重新调用。

## 6. 设计约定与阶段改动

### 6.1 后台任务规格

| kind | 何时登记 | 结束条件 | 结果 `result` |
|---|---|---|---|
| `meiji` | 会话发起的生成；面板发起的生成（`draft: true` 与面板发起的 `script-sync` 除外）；会话发起的剧集摘要触发的 `script-sync` 也登记给该会话 | 操作结束 | `{operationId, projectId, episodeId, action, status, reviewPassed, failures, error?, retryable?, scriptRevision?, pendingConfirm?, pendingProposal?}` |
| `meiji-wait` | 会话发起时项目被占用 | 占用操作结束 | `{occupantOperationId, occupantStatus, message}` |
| `meiji-images` | 图片操作结束且有候选图；或 `meiji_wait_images` | 目标卡片都有图（含关联条目的图），且没有候选图 | `{items:[{itemId, name, ready}]}` |
| `meiji-script` | 产生待确认方案；或会话发起时遇到剧本阻断 | 阻断解除（方案全部处理、回写全部完成） | `{scriptRevision, resolved:[…], message}` |

- 状态映射：completed → completed；cancelled → killed；failed、review_failed → failed。项目摘要更新失败时 `retryable: true`。
- 进度：每次 `notifyProject` 更新「已结束任务数/任务总数 当前任务」，每个任务结束时追加一行；`outputLimitBytes: 16384`。
- 取消：原因为 `'owner disposed'`、`'jobs service disposed'` 时只脱离，以 killed 结束且不停止操作；其他原因调用 `tasks.cancel`；等待类 job 被取消时只结束等待。
- 已完成短路：alreadyCompleted 时先 `registry.wait(jobId, 5000, sessionId)`，再 `registry.remove(jobId)`。

### 6.2 锁规则

操作定义增加 `lock`：生成操作按 `kind: 'generate'` 处理；直接操作写 `'project'` 或 `'episode'`，不写时有 episodeId 为 `'episode'`，否则为 `'project'`。

冲突判断：同一项目内满足以下任一条件即冲突：
- 双方都是生成；
- 任一方是项目级直接操作；
- 剧集重叠：任一方没有 episodeId，或双方是同一集。

| 已占用 ＼ 新发起 | 生成·第 N 集 | 生成·第 M 集 | 生成·项目级 | 剧集级编辑·第 N 集 | 剧集级编辑·第 M 集 | 项目级编辑 |
|---|---|---|---|---|---|---|
| 生成·第 N 集 | 拒 | 拒 | 拒 | 拒 | 允许 | 拒 |

### 6.8 剧本与三类库的数据结构

剧本的字段、规则与界面以剧本计划 2.1–2.2c、2.6 为准，并做以下修改：

**剧本（D2）**：
- `scriptKind`：`imported`（一整篇正文）或 `assembled`（按集分节 `sections: [{ episodeId, text }]` 加「后续剧情」`future`）。
- 两种剧本都由 `script-sync` 用 AI 回写：
  - 输入当前剧本、本集修改前后的摘要、前后集摘要、基调。
  - 输出 `{ needsChange, note, changes: [{ before, after }], appendOnly }`。
- 没有导入剧本时，AI 负责写出本集小节，并在必要时调整相邻小节的衔接，避免重复、保持连贯。
- `appendOnly` 由程序判定，不信任模型自报：所有 `before` 都只锚定剧本末尾、或只新增本集小节，且不改动任何已有文字。判定为 `appendOnly` 时自动写入新版本（D10）；否则生成方案，等待面板确认。
- 剧集删除：AI 生成删除该集内容并修补衔接的方案（改动已有内容，需要确认）。

**新增状态字段**：
- 剧本修改方案：`{ id, kind: 'script-proposal', source: 'episode-sync' | 'ai-edit' | 'edit', baseRevision, episodeId?, requirements?, note, changes, status }`。
- 剧集摘要：`basis = { scriptRevision, prevSummaryRevision, scriptSyncedRevision }`。
- 项目摘要：`basis = { scriptRevision }`。

**三类库**（D5）：剧本计划 2.3 的角色库推广为通用结构，`looks` 统一改名为 `variants`（界面上角色叫「造型」，场景叫「状态」，道具叫「样式」）：

```json
"library": {
  "characters": [{ "id": "R01", "name": "…", "aliases": [], "nationality": "…", "gender": "…", "required": false, "variants": [ { "id": "R01-1", "label": "三十岁", "fields": { "role": "…", "age": "…", "costume": "…", "…": "…" }, "image": { "localPath": "…", "assetId": "…", "source": "ai | photo" }, "createdFrom": { "episodeId": "…", "cardId": "C01" } } ], "defaultVariantId": "R01-1" }],
  "scenes":     [{ "id": "L01", "name": "林家客厅", "aliases": [], "variants": [ { "id": "L01-1", "label": "白天", "fields": { "landmark": "…", "light": "…", "space": "…", "look": "…" }, "image": { } } ], "defaultVariantId": "L01-1" }],
  "props":      [{ "id": "T01", "name": "铜灯", "aliases": [], "category": "prop", "ownerLibraryId": "R01", "variants": [ { "id": "T01-1", "label": "完好", "fields": { "description": "…" }, "image": { } } ], "defaultVariantId": "T01-1" }]

```

- 编号前缀 R / L / T，避开剧集卡片的 C / E / P 和镜头的 S。
- 剧集卡片保留现有全部字段，外加 `ref: { libraryId, variantId, linkedBy: 'name' | 'model' | 'human' }`。
- **输出协议**：人物、场景、道具三类都增加 `libraryId`、`variantId`、`variantLabel` 三个字段。
- **程序规则**（三类相同）：
  1. 两个 ID 都有效 → 卡片字段以库为准、用库的图。
  2. 只有 `libraryId` → 新增变体。
  3. 都没有，但名字或别名一致 → 关联到默认变体。
  4. 都不满足 → 新建条目。
- **自动关联**：依据「名字 + 剧情」，资料中提供该类库的目录，审核时检查关联是否正确。
- **剧集里编辑关联卡片**（D5、S13）：
  - 保存前弹窗提示「将同步到 N 集」。
  - 保存为项目级直接操作：写入条目变体，同步所有关联卡片，对各关联剧集按 3.7 的 R16 删除下游。
  - 想只改本集时，选择「为本集新增变体」。
- **图片**：关联变体有图的卡片直接使用；为关联卡片确认的图片写回变体，并同步所有关联卡片。
- **道具收紧**（D6），修改 `skills/task/extract-story-props-skill.md` 与 `skills/review/review-story-props-skill.md`。新道具必须同时满足：
  1. 属于主要人物经常随身使用的物件（武器、坐骑、标志性饰品等），或者是贯穿剧情的关键物件；
  2. 在本集大纲中反复出现，或道具库中已有（前集出现过，本集再次出现时直接关联）。

  另外：
  - 一般服装写入角色造型的 `costume`，不建道具，除非是反复出现、需要单独参考图的标志性服饰。
  - 一次性物件、场景陈设一律不建。
  - 审核把「一次性或只出现一次的新物件」判为不通过。
- 库的界面：概要页显示角色库、场景库、道具库三个横向列表；条目详情页与 U6 相同（场景、道具没有「必须出场」）；剧集卡片显示关联标签与「改关联、改变体、解除关联」。
- 领域 schemaVersion 由 2 升为 3；阶段 3 开始前停服，用 `scripts/reset-runtime-data.js` 清空旧项目。

## 附录 A：会话说明 `skills/session/panel.md` 目标文本（阶段 6）

```markdown
---
name: skill-gongyong-panel-generate
description: 短剧视频制作：在会话中创建或打开短剧项目，管理剧本，按集生成摘要、剧情、角色/场景/道具图片、镜头表、每秒指令和成片视频，并跟踪后台任务结果。
---

会话负责理解用户意图、规划业务步骤和调用 meiji 工具；内容由工具背后的生成流程产出并保存，不在聊天里代写或另存一份。

一、先查询：用 meiji_context_query 了解当前项目、剧本（版本、待确认的修改、阻断原因）、故事基调、项目摘要、剧集与各阶段状态。创建或打开项目用 meiji_project_manage；创建只需标题，剧本可选。

二、阶段顺序：摘要 → 剧情 → 镜头表 → 每秒指令 → 图片 → 成片。镜头表和每秒指令不依赖图片，先做完；图片在成片前处理（见第六条）。各阶段工具：
- meiji_generate_summary：本集摘要（新集只能是最后一集的下一集）
- meiji_generate_story：剧情（大纲、角色、场景、道具），only 只生成其中一项
- meiji_generate_shot_table：镜头表
- meiji_generate_seconds：每秒指令，track 指定镜头
- meiji_generate_images：图片，省略 itemIds 时为本集全部缺图卡片
- meiji_wait_images：登记等待，用户在面板处理完图片时通知你
- meiji_generate_film：成片，parts 可选 storyboard / video / tail，track 指定镜头
按查询结果跳过已通过的阶段。重新生成或修改上游阶段会删除下游已生成的内容：工具返回 needs_confirmation 时，先用 ask_user 列出将删除的内容并征得同意，再带 confirmDelete=true 重新调用。多步骤请求先用 todo_write 列出业务步骤，每次只调用一个工具，按顺序执行，不要合并。

三、剧本：剧本是全剧总稿。保存剧集摘要后，系统会自动用 AI 把这一集整合进剧本。
- 结果里有 pendingProposal，或工具返回 SCRIPT_PENDING 时，说明剧本有待确认的修改，后续的剧集摘要和剧情步骤会被暂停（镜头表、每秒指令、图片、成片不受影响）：请用户到面板剧本页逐条确认，工具已登记等待任务，收到通知后再继续。
- 用户想改后续剧情时，用 meiji_revise_script（写明要求，可指定从第几集之后改），或请用户在剧本页修改；修改同样要在面板确认。
- 没有导入剧本、没有故事基调、也还没有剧集时，第一次生成前先用 ask_user 问清用户想要的故事（题材、风格、主角、核心冲突、结局），作为第一集的 requirements。

四、模式：generate 首次生成；regenerate 用户明确要求重做，新要求放 requirements；modify 基于当前内容局部修改，意见放 review。本次要求只作用于本次任务。

五、后台任务：生成工具返回 jobId 后本轮可以结束，任务结束时你会收到通知；需要进度时用 job_output（可带 wait）。只有 status=completed 且 reviewPassed=true 才算完成。结果带 retryable=true（项目摘要更新失败）时，重新调用同一工具一次；仍失败则报告原因。其他 review_failed、failed、cancelled 时停止依赖步骤，报告 failures 中的原因，不自行重试。返回 busy 表示本项目正在执行其他操作，工具已登记等待任务，结束后再重新发起。

六、图片：每秒指令完成后、成片之前，用 meiji_context_query 查看本集缺图卡片（images.missing，已排除关联到库且有图的卡片）。有缺图且用户事先没说明处理方式时，用 ask_user 询问：自己在面板导入或从素材库选；AI 生成全部缺图；AI 只生成指定卡片；不要图片直接成片。
- 选自己处理：调用 meiji_wait_images，告诉用户去面板处理，收到就绪通知后再做成片；用户在会话里说「继续」时，用 job_kill 停止等待后继续。
- 选 AI 生成：调用 meiji_generate_images；结果含 pendingConfirm 时请用户到面板确认或放弃，收到通知后再做成片。
- 用户没有选「不要图片」时，不在缺图状态下发起成片。

七、停止：只能用 job_kill 停止本会话发起的任务；面板发起的任务只能在面板停止。被面板停止的任务记为 cancelled：停止依赖步骤并报告，不自行重做。

八、面板发起的任务结束时你也会收到通知：只用一两句话告知结果，不主动发起新的生成，除非它属于用户已要求的计划。

九、用户已要求的多个步骤连续执行，不在步骤之间重复请求确认（剧本修改与候选图的确认除外）。最后简要说明已完成的项目、集数和阶段，或未完成的原因；不复述参数、密钥和内部日志。任务与步骤详情在面板查看。
```
