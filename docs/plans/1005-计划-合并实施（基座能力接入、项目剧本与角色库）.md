## 2. 业务规则与数据结构

### 2.1 剧本、剧集与项目摘要

**资料用途**：剧集摘要的生成、修订、审核统一把剧本当作参考。资料优先级为本次要求 → 已发生剧情（前集及修订基稿）→ 当前剧本 → 故事基调 → 项目摘要。沿剧本情节顺序按时长推进；与已发生事实冲突时承接事实，不强行回到旧走向。审核只阻塞事实矛盾、违背本次要求、明显超出时长或没有剧情进展，不因「剧本外事件」或合理续写判失败。剧情大纲仍以本集摘要为核心。

**当前剧本与版本**：项目保存 `script/scriptKind/scriptSections/scriptRevision/scriptSource`；导入剧本复制为第 1 版，素材库原文件不变。没有导入剧本时，第一集回写成功后建立第 1 版。`scriptSections` 保存各集小节及后续方向，不靠搜索正文标记定位。
- 每版完整快照保存到 `history/script-revisions/<revision>.json`，字段为 `revision/content/sections/createdAt/actor/source/episodeId/operationId/taskId/note/changes/stats/restoredFrom`；`stats` 记录增删字数。
- 人工编辑须填写修改说明；导入剧本编辑整篇，分节剧本编辑小节或「后续剧情」。恢复旧版是生成新版本，保留所有历史；原子写入与孤立记录处理遵守 S9。
- 「按要求修改」和「修改后续剧情」共用小范围方案；每个非空 `before` 必须逐字取自当前版本且唯一定位。面板逐条选择后写入，确认前校验 `baseRevision`，方案按 3.4 管理生命周期。
- 修改后续方向可以指定从第几集之后开始，默认最后一集之后。单纯修改剧本不改写已有剧集数据；提示已受影响的剧集，用户重新生成本集摘要后才按 3.7 删除其下游。

**项目摘要与基调**：项目摘要是当前剧本加基调的全剧概要，最多 1000 个非空白字符；不提供人工正文编辑，只支持立即更新或附意见重新生成。剧本为空时跳过更新；待更新仅按剧本版本推导，生成摘要、剧情时在规划任务阶段按需加入更新任务，失败时取消后续任务，重试原操作后继续。
- `premise` 保存用户的创作意图，最多 1000 字，AI 不改写；进入剧集摘要、剧情、项目摘要的输入。没有剧本、基调和剧集时，第一次生成的要求必填，默认保存为基调；之后的本次要求选填，只影响当次任务。
- 剧本、基调、项目摘要为空时省略对应提示词资料；有剧本时提供当前全文或分节正文与后续方向。

**回写协议**：
- `scriptKind`：`imported`（一整篇正文）或 `assembled`（按集分节 `sections: [{ episodeId, text }]` 加「后续剧情」`future`）。
- 两种剧本都由 `script-sync` 用 AI 回写：
  - 输入当前剧本、本集修改前后的摘要（删除时取 `scriptPendingDeletes`）、前后集摘要、基调及可修改的目标目录。
  - 输出 `{ needsChange, note, changes: [{ target: { kind, episodeId? }, before, after }], appendOnly }`；`kind` 为 body（导入整篇）、episode（分集小节，必带稳定 episodeId）或 future（后续方向）。
  - 按 target 定位后，在该目标内校验非空 before 唯一匹配；跨小节的相同文字不构成歧义。未知或越出本次范围的目标拒绝，允许新增的小节也须属于已提供的目标目录。
  - before 为空只允许明确的新增：导入整篇末尾追加，或建立尚不存在的分集小节/后续方向；不能作为覆盖已有正文的捷径。多项修改先验证并应用到内存副本，全部通过才原子保存，不逐项落盘。
- 没有导入剧本时，AI 负责写出本集小节，并在必要时调整相邻小节的衔接，避免重复、保持连贯。
- `appendOnly` 由程序比较应用前后的结果判定，不信任模型自报：导入整篇完整保留原文前缀，或分节只新增本集小节且已有小节/后续方向完全不变；使用末尾锚点时也必须完整保留原文。只追加时自动写入新版本，否则生成方案等待确认。
- 剧集删除：AI 生成删除该集内容并修补衔接的方案（改动已有内容，需要确认）。

**数据字段**：
- 剧本修改方案：`{ id, kind: 'script-proposal', source: 'episode-sync' | 'ai-edit' | 'edit', baseRevision, episodeId?, summaryRevision?, requirements?, note, changes, status }`；存在剧集的回写方案必带本次核对的 summaryRevision，删除方案绑定对应删除事实。
- 剧集摘要：`basis = { scriptRevision, prevSummaryRevision, scriptSyncedRevision }`。
- 项目摘要：`basis = { scriptRevision }`。
- 项目待删除回写事实：`scriptPendingDeletes: [{ episodeId, summaryBefore, prevEpisodeId?, nextEpisodeId? }]`。与删除剧集在同次保存中写入，按 episodeId 唯一；只有对应回写完成才移除，清理剧集历史不删除它。不另建持久任务队列或重复保存执行状态。

**同步完成**：生成方案不更新 basis。自动追加写入、全部确认写入或判定无需修改时，记录本次实际核对的 summaryRevision；确认时同时核对剧本版本和摘要依据。部分确认的选中项正常写入、方案结束，未完成的回写仍阻断，可重新回写或修改本集；放弃回写方案同样保留依据。没有选中项按放弃处理，不生成空版本。删除方案全部确认或无需修改后，移除对应 `scriptPendingDeletes`。人工 AI 编辑方案放弃仅结束该方案，不制造新的回写记录。

### 2.2 人物、场景与道具库

共用条目与 `variants` 结构（界面上角色叫「造型」，场景叫「状态」，道具叫「样式」）：

```json
"library": {
  "characters": [{ "id": "R01", "name": "…", "aliases": [], "nationality": "…", "gender": "…", "required": false, "variants": [ { "id": "R01-1", "label": "三十岁", "fields": { "role": "…", "age": "…", "costume": "…", "…": "…" }, "image": { "localPath": "…", "assetId": "…", "source": "ai | photo" }, "createdFrom": { "episodeId": "…", "cardId": "C01" } } ], "defaultVariantId": "R01-1" }],
  "scenes":     [{ "id": "L01", "name": "林家客厅", "aliases": [], "variants": [ { "id": "L01-1", "label": "白天", "fields": { "landmark": "…", "light": "…", "space": "…", "look": "…" }, "image": { } } ], "defaultVariantId": "L01-1" }],
  "props":      [{ "id": "T01", "name": "铜灯", "aliases": [], "category": "prop", "ownerLibraryId": "R01", "variants": [ { "id": "T01-1", "label": "完好", "fields": { "description": "…" }, "image": { } } ], "defaultVariantId": "T01-1" }]
}
```

- 编号前缀 R / L / T，避开剧集卡片的 C / E / P 和镜头的 S。
- 同一身体身份的年龄、着装、身份变化属于新造型；双胞胎、替身等独立人物才新建角色。名字、别名、国籍、性别放条目层，身份、年龄、外貌、着装等可变字段放 `variants[].fields`。附属素材 `clothes/props/hairstyles/parts` 本期仍留在剧集卡片。
- 剧集卡片保留现有全部字段，外加 `ref: { libraryId, variantId, linkedBy: 'name' | 'model' | 'human' }`。
- **输出协议**：人物、场景、道具三类都增加 `libraryId`、`variantId`、`variantLabel` 三个字段。
- **程序规则**（三类相同）：
  1. 两个 ID 都有效 → 卡片字段以库为准、用库的图。
  2. 只有 `libraryId` → 新增变体。
  3. 都没有，但名字或别名一致 → 关联到默认变体。
  4. 都不满足 → 新建条目。
- **自动关联**：依据「名字 + 剧情」，资料中提供该类库的目录，审核时检查关联是否正确。
- **剧集里编辑关联卡片**（S13）：
  - 保存前弹窗提示「将同步到 N 集」。
  - 保存为项目级直接操作：写入条目变体，同步所有关联卡片，对各关联剧集按 3.7 的 R16 删除下游。
  - 想只改本集时，选择「为本集新增变体」。
- **图片**：关联变体有图的卡片直接使用；为关联卡片确认的图片写回变体，并同步所有关联卡片。
- **指定照片**：手动创建条目时可导入照片或从素材库选图，`image.source: 'photo'`，不调用生成、不需要候选确认。`required: true` 的角色作为指定人物进入剧集摘要和大纲，按名字或别名关联；场景、道具没有必须出场开关。
- **道具准入**，修改 `skills/task/extract-story-props-skill.md` 与 `skills/review/review-story-props-skill.md`。新道具必须同时满足：
  1. 属于主要人物经常随身使用的物件（武器、坐骑、标志性饰品等），或者是贯穿剧情的关键物件；
  2. 在本集大纲中反复出现，或道具库中已有（前集出现过，本集再次出现时直接关联）。

  另外：
  - 一般服装写入角色造型的 `costume`，不建道具，除非是反复出现、需要单独参考图的标志性服饰。
  - 一次性物件、场景陈设一律不建。
  - 审核把「一次性或只出现一次的新物件」判为不通过。
- 库的界面按第 7 节的 U6–U8；剧集卡片显示关联标签与「改关联、改变体、解除关联」。
- 领域 schemaVersion 由 2 升为 3；阶段 3 开始前停服，用 `scripts/reset-runtime-data.js` 清空旧项目。

## 3. 状态与数据一致性

### 3.1 两类状态与占用分工

| 类别 | 内容 | 写入规则 | 证据 |
|---|---|---|---|
| **执行状态** | 步骤状态 StepStatus（pending/running/waiting/completed/failed/cancelled/skipped）→ 任务状态（`deriveTaskStatus`）→ 操作状态（`deriveOperationStatus`） | 只写步骤，任务与操作状态一律推导，任何代码不直接赋值；运行中的步骤在内存 `liveTasks`，结束写入 `history/tasks`、`history/operations` | `shared/task-nodes.js:25-95`；`server/runtime/task-state.js:23-48`；`operation-manager.js:51-66` |
| **内容状态** | 内容节点的 `status/check/error/operation/revision`（阶段 1 删除 `stale` 与 `dependencies`） | 只经 `drama-model.js` 的 `setContent/begin/finish/modelPatch` 与 `shared/content-state.js`；B4 测试静态扫描 server 目录 | `shared/content-state.js:1-12`；`shared/drama-model.js:66-80`；`tests/status-stability.test.js:87-92` |

只复用现有机制，不新增锁管理器、分布式锁或通用事务框架：
1. **操作占用**（`operation-occupancy.js`）：由 manager 统一判断项目/剧集冲突，`occupy` 早于建立任何记录（`operation-manager.js:77` 早于 `:88`），冲突时不留记录；重启后消失。
2. **内容节点 `operation` 字段**：记录节点属于哪个执行中操作，用于状态与重启恢复；`begin` 时已有则 409，结束或 `interruptRunning` 时释放，不作为另一套操作调度器。
3. **队列名额**：只限流，不承担数据互斥。

保存沿用 `projectStore.save` 的串行、原子写入与现有版本校验；job 只观察，不能再维护占用或执行状态。

后台任务（job）只观察，不写状态；阻断检查只在规划任务时判断，不写状态。

### 3.2 状态规则

| # | 不变量 | 说明 |
|---|---|---|
| S1 | 执行状态只推导 | job 结果、会话返回、面板显示都从 `snapshot()` 或记录读取 |
| S2 | 内容状态只经统一入口 | 三类库图片、项目摘要等内容节点状态只经 `content-state.js` 或 `drama-model.js` 基础函数；B4 扫描新文件。回写 basis 与删除事实作为业务数据在项目保存入口更新，不另造执行节点或状态字段 |
| S3 | 开始即建立全部任务 | 「更新项目摘要」任务在 `planTasks` 规划时决定是否加入；回写剧本是另一个操作，不往已开始的操作里插任务 |
| S4 | 停止规则不加例外 | 任一任务失败、审核未通过或停止 → 后续任务取消，已完成结果保留；「失败后重试再继续」通过重新发起同一操作实现 |
| S5 | 锁先于记录 | 占用范围在开始前按 5.2 确定，期间不升级锁；阻断检查只改「能否开始」，保持先占用、后建记录，被拒不留记录 |
| S6 | 项目级写入持项目锁 | 写剧本、方案确认、项目摘要、基调、三类库、剧集列表的生成和直接操作都为 `lock: 'project'`；`summary/story` 即使有 episodeId 也按项目级占用 |
| S7 | 派生提示与阻断不存状态 | 提示和阻断由版本号、方案与 `scriptPendingDeletes` 记录推导；后者仅保存尚未回写的删除事实，不另存 busy/pending/synced 等布尔状态 |
| S8 | 人工待处理对象有完整生命周期 | 候选图、剧本修改方案都写清产生与消除条件并有测试（3.4） |
| S9 | 剧本写入原子 | 先写版本记录文件，再在同一次 `projectStore.save` 中更新 `script/scriptSections/scriptRevision`；读取时忽略编号大于 `scriptRevision` 的孤立记录；版本号只增不减 |
| S10 | 修改方案绑定版本 | 方案绑定 `baseRevision`，回写方案还绑定本次摘要 revision（或删除事实）；任一依据已变化则拒绝确认，放弃或重新生成，不把旧方案标记为最新摘要已同步 |
| S11 | 重启处理一致 | 执行中的操作取消；内容节点 `operation` 释放（范围扩展到项目摘要、三类库条目图片）；内存占用与 job 消失；候选图与待确认方案保持；未完成回写的剧集及删除记录继续派生阻断，可重新回写 |
| S12 | job 只观察 | job 完成跟随 manager 跟踪的操作结束；teardown 只脱离；`job_kill` 与面板停止统一调用 `manager.cancel`，不创建第二条执行通路 |
| S13 | 库同步可预见 | 剧集里编辑关联卡片会同步到库与所有关联剧集，保存前提示影响的集数与将被删除的内容；各关联剧集按 3.7 删除下游 |

### 3.6 剧本阻断规则

- **何时阻断**：存在 pending 的剧本修改方案、待回写剧集或 `scriptPendingDeletes` 中的待回写删除记录。
- **阻断哪些操作**：剧本只作用于剧集的剧情层，所以只阻断剧情层的生成，在 `planTasks` 的 precheck 中拒绝（409，`code: 'SCRIPT_PENDING'`，列出待处理的方案、剧集或删除记录）：
  - 剧集摘要的生成（含草稿）；
  - 剧情；
  - 项目摘要更新；
  - `script-revise`。
- **不阻断**：
  - 镜头表、每秒指令、图片、成片：它们依赖已通过的剧情，不读剧本，剧本改动传不到这一层；剧情真被改了以后，下游按 3.7 删除；
  - 处理问题本身的操作：方案确认或放弃、重新回写（`script-sync`）、对待回写或方案所关联剧集的摘要修改/重新生成（用来「把本集改回符合剧本」）；部分确认或放弃后仍可走该纠正入口；
  - 剧集级的人工编辑。
- **解除**：没有待确认方案、待回写剧集或待回写删除记录时自动解除。回写方案放弃或部分确认后仍可重新回写、把本集改回符合剧本；AI 编辑方案放弃且无其他待处理依据时可解除。会话通过 `meiji-script` 等待 job 得到通知后继续（5.1）。
- 纠正入口的例外在父操作 precheck 统一判断，必要的项目摘要前置任务不再次阻断这个已允许的操作；独立发起项目摘要更新仍受阻断，不另设逐任务审批。

### 3.7 流水线下游删除规则

**原则**：上游一改，下游直接删除，不标过期，不做新鲜度比对。删除后为未生成，需要重新生成。R1–R17 只清项目内容，保留任务历史（提示词、产物快照、原始返回）与素材库。R18 删除剧集时清理该集历史与生成文件；删除项目时清理该项目全部记录与生成文件，素材库和系统配置均保留。

**单集流水线**（L0 → L7）：

| 层 | 内容 | 依赖 |
|---|---|---|
| L0 | 剧集摘要、本集时长 | 剧本、项目摘要、基调、前后集（只作参考，不构成删除依赖） |
| L1 | 大纲 | L0 |
| L2 | 人物卡、场景卡 → 道具卡（含本集候选图） | L1；道具依赖人物、场景目录 |
| L3 | 镜头表 | L1、L2（实体清单） |
| L4 | 每秒指令（按镜，后镜依赖前镜的结束状态） | L3 |
| L5 | 分镜提示词（按镜） | 本镜 L4、引用实体的外观与图片、上一镜尾帧 |
| L6 | 视频与尾帧（按镜） | 本镜 L5 |
| L7 | 合成 | 全部 L6 |

「尾帧链」：第 j 镜的分镜记录了第 j−1 镜的尾帧（`tailReference`），所以第 j−1 镜的视频变化会让第 j 镜的分镜和视频失效，并依次向后传递，直到遇到不使用上一镜尾帧的镜头。

**删除规则**：

| # | 上游变化 | 删除（本集，除非另有说明） |
|---|---|---|
| R1 | 剧集摘要或本集时长变化（人工编辑、按意见修改、重新生成后保存） | L1–L7。其他剧集不删除，下一集只提示「前集已修改」 |
| R2 | 大纲变化 | L2–L7。卡片删除不影响库条目，重新提取时自动关联 |
| R3 | 人物、场景或道具任务整体重新生成或按意见修改 | L3–L7；人物或场景重新生成时，同时删除道具卡 |
| R4 | 单张卡片改名（剧集里编辑，或库条目改名） | 沿用现有的名称替换（镜头表、每秒指令中的标记）；删除引用该实体的镜头的 L5–L6（含尾帧链）与 L7 |
| R5 | 单张卡片外观文字变化（不改名） | 引用该实体的镜头的 L5–L6（含尾帧链）与 L7；图片不自动删除 |
| R6 | 卡片图片变化（导入、从素材库选、确认候选、删除图片；库条目变体图片变化） | 引用该实体的镜头的 L5–L6（含尾帧链）与 L7 |
| R7 | 删除一张卡片（如删除道具） | 被镜头表或每秒指令引用时删除 L3–L7；没被引用时只删卡片与它的候选图 |
| R8 | 镜头表整表重新生成或修改 | L4–L7（全部镜头） |
| R9 | 镜头表单镜修订（第 k 镜） | 第 k 镜及之后各镜的 L4–L6，L7 |
| R10 | 第 k 镜每秒指令变化 | 第 k+1 镜起的 L4；第 k 镜起的 L5–L6；L7 |
| R11 | 第 k 镜分镜提示词变化 | 第 k 镜 L6，沿尾帧链向后删除 L5–L6；L7 |
| R12 | 第 k 镜视频重新生成（尾帧随之变化） | 沿尾帧链删除第 k+1 镜起的 L5–L6；L7 |
| R13 | 剧本出新版本、项目摘要更新、基调变化、指导素材或补充 skill 变化 | 不删除（只影响之后的生成） |
| R14 | 画幅变化 | 全部剧集的 L5–L7；图片保留，由用户决定是否重做 |
| R15 | 风格变化 | 全部剧集的 L5–L7；图片保留 |
| R16 | 库条目在库页或剧集里被编辑 | 对每个关联剧集，分别按 R4、R5、R6 执行 |
| R17 | 合并库条目 | 改为指向目标条目的卡片，对其所在剧集按 R4、R5、R6 执行 |
| R18 | 删除剧集 | 该集内容、候选图、生成文件及所属操作/任务/提示词/产物快照/原始返回；保留项目剧本版本、库条目与素材库。在同次项目保存中先记录 `scriptPendingDeletes`；其他集不删除，下一集只提示 |

「引用该实体的镜头」：镜头表条目或每秒指令中带有该实体 ID 标记，或分镜 `referenceSnapshot` 里含该实体的镜头。没有分镜、视频的镜头不受 R4–R6 影响。

**执行方式**：
- 新增 `shared/pipeline-cascade.js`，统一提供两个函数：
  - `cascade(project, change)`：返回删除后的补丁，以及删除清单；
  - `cascadePreview(project, change)`：只返回删除清单，用于确认提示。

  `change` 的类型对应 R1–R18。
- 现有 `replaceFrom`、`clearShotDownstream`、`staleMedia`、`seconds-results.js` 的后镜处理、`refreshReferences` 的过期标记，全部改为调用 `cascade`；`guidance-assets.js` 的过期标记删除（R13）。
- 删除与上游变化在同一次 `projectStore.save` 中完成（S14）；被删除卡片和镜头的候选图同时移除。
- 删除 `stale` 字段与 `dependencies` 字段，以及所有对它们的判断：`generation-gates.js`、`story-content.js`、`operation-story.js` 的 `completed`、`operation-seconds.js`、`generationFeedback`、`film-freshness.js` 的 `storyboardReady/videoReady/tailReady`（改为「有内容且已通过」）、`tail-frame.js`、client 中的过期显示、查询工具返回的 `stale`。

**确认提示**：
- 面板：任何会删除已生成内容的操作，开始前先用 `cascadePreview` 显示删除清单（如「将删除本集：镜头表、12 条每秒指令、3 个视频；同步影响第 2、5 集」），确认后才执行；没有内容要删时不提示。
- 会话：生成工具增加 `confirmDelete` 参数。会删除已生成内容但没有 `confirmDelete: true` 时，不启动操作，只返回 `{ status: 'needs_confirmation', deletes: [...] }`。已有用户对该范围的明确授权时直接带参数；否则用 ask_user 确认一次后重新调用。
- 同一次操作只确认一份完整删除清单，库同步的影响范围合并在同一提示中；已经授权的删除不在各内部任务重复确认。自动回写另按 2.1 的方案确认与自动追加规则处理，不增加逐步骤审批。

## 5. 接口与集成

### 5.1 后台任务规格

| kind | 何时登记 | 结束条件 | 结果 `result` |
|---|---|---|---|
| `meiji` | 会话发起的生成；面板发起的生成（`draft: true` 与面板发起的 `script-sync` 除外）；会话发起的剧集摘要触发的 `script-sync` 也登记给该会话 | 操作结束 | `{operationId, projectId, episodeId, action, status, reviewPassed, failures, error?, retryable?, scriptRevision?, pendingConfirm?, pendingProposal?}` |
| `meiji-wait` | 会话发起时项目被占用 | 占用操作结束 | `{occupantOperationId, occupantStatus, message}` |
| `meiji-images` | 图片操作结束且有候选图；或 `meiji_wait_images` | 目标卡片都有图（含关联条目的图），且没有候选图 | `{items:[{itemId, name, ready}]}` |
| `meiji-script` | 产生待确认方案；或会话发起时遇到剧本阻断 | 无待确认方案、待回写剧集及待回写删除记录 | `{scriptRevision, resolved:[…], message}` |

- 状态映射：completed → completed；cancelled → killed；failed、review_failed → failed。项目摘要更新失败时 `retryable: true`。
- 进度：每次 `notifyProject` 更新「已结束任务数/任务总数 当前任务」，每个任务结束时追加一行；`outputLimitBytes: 16384`。
- 取消：原因为 `'owner disposed'`、`'jobs service disposed'` 时只脱离，以 killed 结束且不停止操作；其他原因调用 `manager.cancel`；等待类 job 被取消时只结束等待。
- 已完成短路：alreadyCompleted 时先 `registry.wait(jobId, 5000, sessionId)`，再 `registry.remove(jobId)`。
- 四种 kind 共用一个 jobs 适配器，以不同的结束条件观察 manager 或项目事件，不各建执行器。自动回写已由 manager 启动时，只按 operationId 绑定观察 job；登记失败不撤销回写、不重复启动。

### 5.2 锁规则

`kind` 区分生成/直接操作，`lock` 表示实际写入范围（`'project'` 或 `'episode'`），两者分开。生成和直接操作都遵守范围规则，由现有 `operation-occupancy.js` 统一判断。

- 写共享项目数据（剧本、项目摘要、基调、三类库、剧集列表）或影响多集的操作，定义为 `lock: 'project'`，即使携带 episodeId 也不例外。
- `summary/story` 固定为项目级：可能包含项目摘要前置任务、剧集保存或提取结果入库；草稿同样可能更新项目摘要，不在执行中临时升级占用。
- 只写单集的镜头表、每秒指令、分镜、视频及图片候选生成可为 `lock: 'episode'`。条目图片写回库、跨集卡片同步仍为项目级。
- 开始前解析实际范围，先占用再建立记录，持有到操作结束；不在任务间释放重抢。未显式声明时，有 episodeId 默认为 episode、否则为 project；写共享数据的定义必须显式声明 project，测试防止漏标。

冲突判断：同一项目内满足以下任一条件即冲突：
- 双方都是生成；
- 任一方为 `lock: 'project'`；
- 双方为剧集级且 episodeId 相同。

| 已占用 ＼ 新发起 | 生成·第 N 集 | 生成·第 M 集 | 生成·项目级 | 剧集级编辑·第 N 集 | 剧集级编辑·第 M 集 | 项目级编辑 |
|---|---|---|---|---|---|---|
| 生成·第 N 集 | 拒 | 拒 | 拒 | 拒 | 允许 | 拒 |
| 生成·项目级 | 拒 | 拒 | 拒 | 拒 | 拒 | 拒 |
| 剧集级编辑·第 N 集 | 拒 | 允许 | 拒 | 拒 | 允许 | 拒 |
| 项目级编辑 | 拒 | 拒 | 拒 | 拒 | 拒 | 拒 |

项目级直接操作（`lock: 'project'`）：

| 阶段 | 操作 |
|---|---|
| 1 | `episode-add`、`episode-edit`、`episode-delete`、`overview`（保存项目概要）、`source`（修改原始资料） |
| 3 | `script-edit`、`script-restore`、`script-proposal-confirm`、`script-proposal-discard`、`premise-edit` |
| 5 | 库的各操作；卡片有 `ref` 时，下列编辑按项目级处理：`character-text`、`scene-text`、新增的 `prop-text`（现在没有道具文字编辑操作），以及会写回条目图片的 `confirm-image`、`import-image`、`use-asset`、`clear-image`。`prop-delete` 只删除本集卡片与关联，不动库条目，仍为剧集级 |

`summary/story/script-sync/script-revise/project-summary` 均为项目级生成。回写目标放在任务资料/方案的 episodeId 中，不用它降低操作占用范围。没有 projectId 的操作（创建、打开）不占用。

保留跨集编辑能力，仅适用于只写单集的生成；不增加多把锁或嵌套占用。版本号防止旧方案覆盖，原子保存防止文件不完整，各自沿用现有入口。

### 5.3 停止权限

| 谁 | 能停止什么 | 方式 |
|---|---|---|
| 面板「停止」 | 项目内任何操作 | `operation-cancel` |
| 会话模型 | 本会话发起的 job 与等待类 job | `job_kill`；面板发起的 job 被守卫拒绝 |
| 其他会话 | 不能 | job 按 owner 隔离 |

安全沿用现有 HTTP 鉴权、记录归属校验及密钥/Base64 脱敏；不新增通用安全审批流程。删除清单、剧本方案和候选图确认属于业务交互，已授权操作的内部任务不重复请求批准。

## 附录 A：会话说明 `skills/session/panel.md` 目标文本（阶段 6）

```markdown
---
name: skill-gongyong-panel-generate
description: 短剧视频制作：在会话中创建或打开短剧项目，管理剧本，按集生成摘要、剧情、角色/场景/道具图片、镜头表、每秒指令和成片视频，并跟踪后台任务结果。
---

会话负责理解用户意图、规划业务步骤和调用 meiji 工具；内容由工具背后的生成流程产出并保存，不在聊天里代写或另存一份。

一、先查询：用 meiji_context_query 了解当前项目、剧本（版本、待确认的修改、阻断原因）、故事基调、项目摘要、剧集与各阶段状态。创建或打开项目用 meiji_project_manage；创建只需标题，剧本可选。

二、阶段顺序：摘要 → 剧情 → 镜头表 → 每秒指令 → 图片 → 成片。镜头表和每秒指令不依赖图片，先做完；图片在成片前处理（见第六条）。各阶段工具：
- meiji_generate_summary：本集摘要（新集只能是最后一集的下一集）
- meiji_generate_story：剧情（大纲、角色、场景、道具），only 只生成其中一项
- meiji_generate_shot_table：镜头表
- meiji_generate_seconds：每秒指令，track 指定镜头
- meiji_generate_images：图片，省略 itemIds 时为本集全部缺图卡片
- meiji_wait_images：登记等待，用户在面板处理完图片时通知你
- meiji_generate_film：成片，parts 可选 storyboard / video / tail，track 指定镜头
按查询结果跳过已通过的阶段。重新生成或修改上游会删除下游内容：工具返回 needs_confirmation 时，没有对该删除范围的明确授权才用 ask_user 列出清单确认一次，再带 confirmDelete=true 调用；已有授权不重复询问。多步骤请求先用 todo_write 列业务步骤，每次一个工具，按顺序执行。

三、剧本：剧本是全剧总稿。保存剧集摘要后，系统会自动用 AI 把这一集整合进剧本。
- 结果有 pendingProposal 或返回 SCRIPT_PENDING 时，说明有待确认方案、待回写剧集或待删除回写，剧集摘要和剧情被暂停（镜头表、每秒指令、图片、成片仍按自身门禁执行）。请用户到剧本页处理或重试回写，工具已登记等待；部分确认或放弃回写方案不代表解决，阻断解除后再继续。
- 用户想改后续剧情时，用 meiji_revise_script（写明要求，可指定从第几集之后改），或请用户在剧本页修改；修改同样要在面板确认。
- 没有导入剧本、没有故事基调、也还没有剧集时，第一次生成前先用 ask_user 问清用户想要的故事（题材、风格、主角、核心冲突、结局），作为第一集的 requirements。

四、模式：generate 首次生成；regenerate 用户明确要求重做，新要求放 requirements；modify 基于当前内容局部修改，意见放 review。本次要求只作用于本次任务。

五、后台任务：生成工具返回 jobId 后本轮可以结束，任务结束时你会收到通知；需要进度时用 job_output（可带 wait）。只有 status=completed 且 reviewPassed=true 才算完成。结果带 retryable=true（项目摘要更新失败）时，重新调用同一工具一次；仍失败则报告原因。其他 review_failed、failed、cancelled 时停止依赖步骤，报告 failures 中的原因，不自行重试。返回 busy 表示本项目正在执行其他操作，工具已登记等待任务，结束后再重新发起。

六、图片：每秒指令完成后、成片之前，用 meiji_context_query 查看本集缺图卡片（images.missing，已排除关联到库且有图的卡片）。有缺图且用户事先没说明处理方式时，用 ask_user 询问：自己在面板导入或从素材库选；AI 生成全部缺图；AI 只生成指定卡片；不要图片直接成片。
- 选自己处理：调用 meiji_wait_images，告诉用户去面板处理，收到就绪通知后再做成片；用户在会话里说「继续」时，用 job_kill 停止等待后继续。
- 选 AI 生成：调用 meiji_generate_images；结果含 pendingConfirm 时请用户到面板确认或放弃，收到通知后再做成片。
- 用户没有选「不要图片」时，不在缺图状态下发起成片。

七、停止：只能用 job_kill 停止本会话发起的任务；面板发起的任务只能在面板停止。被面板停止的任务记为 cancelled：停止依赖步骤并报告，不自行重做。
```
