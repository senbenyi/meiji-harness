# 大剧本分阶段生产与项目纯程序创建

后续资产与声音设计以[剧本到视频与共享图片库完整方案](1028-计划-剧本到视频与共享图片库.md)为准：共享图片表只有id/url，项目保存定义和引用；文字分镜识别需求后准备素材与组合定妆，再绑定回分镜。本文阶段1实施事实保留，其他旧目标示例供演进追溯。

- 类型：项目创建流程调整及后续架构规划。
- 目标：创建/导入不调用模型；长原稿先忠实解析建索引，再全篇规划与分段改编，最终交给制作节点。
- 本轮实施范围：阶段1，移除创建/导入后的自动摘要调用；阶段2～6为本轮用户要求的方案，不在本轮直接迁移业务字段、盒子语义和既有项目。
- 非目标：不自动重跑已有任务，不清空旧项目摘要/历史，不调整图片视频生成协议，不在本轮宣称已支持10MB原稿。

### 阶段2：原著解析，替代当前“优化剧本”的职责（待实施）

建议命名“原著解析”，不是“优化剧本”。先忠实分章节、分场景并建索引；原著没有标题时可以给描述性标题，但不重排事件、不改对白、不补因果，不把未知事项写成事实。

先建设文件读取基础：原文保存在外部，使用不可变source_revision_id及原文区间引用；原始文本不重写、不靠模型复述还原。提供目录/搜索/按范围读取工具，程序限定每次token或字符返回量、给输出留预算，单行超长也能继续分页。物理阅读块、原文章节、改编故事段及最终分集是四种不同单位，不强求一一对应；超长章节内部继续分页，跨读取块章节可以合并为一个索引条目。

每个章节建议包含：chapter_id、顺序、标题（注明原有/识别）、source_revision_id、一个或多个原文区间、忠实摘要、人物、主要事件、时间/地点与前后状态、伏笔及回收引用、不确定项。人物/事件/时间线/伏笔记录都应有原文证据位置，不将摘要当原文事实。区间引用比复制原文更适合长稿，按需读取可取回原著。

执行先按预算分批覆盖原稿，再归并识别出的章节边界；块间可重叠用于理解，程序按区间去重核对覆盖，不因重叠重复创建事件/章节。完成条件是当前原稿版本所有内容已覆盖且索引区间合法、有序、无遗漏/重复归属；阅读未完成只能标partial。索引审核检查忠实、边界、摘要与证据一致，不能用改编审美否决原著。取消保留已完成范围，续读从明确检查点接续；原稿换版后旧索引只作旧版本历史，不用于新稿提交。此版本归属不恢复现有被取消的内容hash驱动下游过期机制。

验收：无章节标题、超长单行、章边界跨块、重复读取、取消续读及换稿场景均无丢字/重复归属；10MB合成样本每次模型请求在预算内，任务/调用记录不反复复制全文；真实模型另验证忠实度。

### 阶段3：人物、场景与剧情联合改编规划（待实施）

先确认已读全原著，再按用户本次目标规划改编。用户明确锁定事项独立记录；区分原著事实、改编建议和已采用决定。主线、人物弧光、主要冲突、爽点、压抑与释放、铺垫兑现、悬念/反转、节奏和结局是一套关联方案，不能孤立抽取爽点后强行堆叠。没有证据的判断标不确定；不能仅凭章摘要决定需精确对白或细节的修改，必须回读原文。

规划采用分层阅读：先读取各章结构与摘要，再读取关联原文和事实记录；总体纲要过大也需分层。保留跨章依赖关系，为每个改编单元记录输入章节/区间、改编目标、保留点、允许更改范围及与其他单元的约束。允许合并/拆分/移动事件，但显式记录来源及改编理由。联合规划和分段定稿保留为两个明确阶段，前者输出改编计划，后者依据计划写成完整故事。核心要求冲突或超出既有授权才向用户提出具体选择；已授权范围内不为每个小调整重复确认。

人物规划在写定稿前完成：主次功能、目标/动机、行为逻辑、关系、能力与局限、成长弧和关键转变；角色合并/新增及原著依据/改编理由明确记录。场景规划同样前置：每场的目标、参与人物、冲突、关键信息、爽点/伏笔/反转功能、进入/离开状态，以及场景合并或转移的叙事理由。人物行动推动场景与剧情，不能等全文改完才被动提取。

这层人物/场景规划区别于原著事实清单，也区别于下游制作资产。人物外貌、服装状态、建筑空间及美术风格可以在改编阶段确定必要约束；具体可复用视觉资产在剧本和制作设计稳定后生成。共享稳定身份，原著实体与改编实体通过映射关联，避免同名误合并或为每次出场新建资产。

方案审核检查用户锁定要求、因果/人物一致、伏笔兑现及可执行性。规划建议不会自动成为原著事实。是否拆成独立盒子由实施时的任务、审核及持久化边界决定，不只是多做一次摘要调用。

### 阶段4：分段故事定稿（待实施）

现有story_segments负责叙事定稿的定位保留，但执行改为按改编单元生成/修订：读取目标原文、关联原文、整体改编方案、必要人物/状态记录及相邻已定稿段，返回本段完整结果或有明确目标的修改，程序组装集合；不要求单次输出整部剧本。

单段审核独立于作者，核对来源、授权与正文；跨段审核覆盖人物动机、因果、时间/空间、持物、伏笔和信息揭示。不能只看摘要就宣称全文审核通过，局部及跨段审核均记录实际覆盖范围，全篇完成需覆盖所有段及已知依赖。发现问题由主Agent规划受影响段，再局部修订，不把全篇重生成当默认修复。

原著索引chapter_id与改编segment_id分开，保留多对多来源映射；正文只有改编定稿层是下游权威剧情来源。项目级长期记录保存来源、事实、方案、决策和已定稿引用；Task级记录保存具体调用、工具结果、审核/修改和检查点。每次请求只带当前范围所需内容，旧全文留在外部可回读；摘要/状态压缩不能替代锁定原话、证据及全篇覆盖检查。

### 阶段5～6：下游制作（待实施）

人物/场景的叙事设定来自联合规划；分镜读取定稿、规划、已有资产目录及前后状态，产生实际资产需求。项目库查重登记ID后，按需完善场景/团队/人物/服装定义及图片，不把全量资产预生成为分镜硬前置；无统一制服群体不强建团队。图片、视频提示词、视频生成与片段编排沿既有职责演进。节点无生产执行器时不得宣称可执行。

可先完成一个制作单元再推进后续单元，但共享人物、场景及服装等先消解身份冲突；来源明确的后续叙事变更由主Agent检查实际影响并规划keep/update/regenerate/defer，不机械按章节全链重做、不恢复hash自动扩散过期。最终分集按叙事节奏及成片组织，原文章节不是天然集数，参考单集时长不变成原著解析的删戏约束。

以下是用户追加要求的端到端目标，涵盖现有能力及待建设环节；不代表程序已实现完整链路。主Agent按依赖编排，可并行或局部回退，盒子保留明确输入、保存、审核及失败边界。

| 5 视听与分镜设计 | 只实现定稿剧情，确定镜头目的、景别/机位/运动、表演、节拍、声画关系及剪接点；服装道具状态关联人物与场景规划 | 镜头表、镜头间状态、对白/动作/声音及粗估时长；引用正确且每镜可执行 | 分镜技术/表达错误；叙事问题回剧本 |

| 7 逐镜生成方案 | 将已审核镜头、资产、首尾状态和声音要求转换为具体生成任务；按模型能力选择首帧/参考图、动作、镜头、时长及负面约束 | 每镜生成包、资产引用、种子/参数（能力支持时）及明确声音策略；满足实际生成接口能力 | 生成包或缺失资产 |

### 全程共用的执行原则

- 一份原著事实、一套明确改编方案、一套已定稿剧情，视觉资产和视频不能反向偷改剧情；反馈可发起有依据的上游修改。
- 原著章节、改编故事段、剧集、镜头、媒体片段与剪辑时间线分别有稳定ID及来源/依赖引用；例如一章拆成多集，多个章节合成一段，多个take对应一个镜头，均可追溯。
- AI负责规划、内容生成及内容审核；程序负责范围读取、token/输出预算、引用/Schema/媒体技术校验、保存、进度、调用费用事实及导出。主Agent不直接绕过Service写项目JSON。
- 模型每次拿目标、当前动作完整skill、必要资料索引与当前范围；分批读取后压缩旧工作上下文，全文与执行记录外部持久化。不能把模型声称“已读完”当覆盖证据，也不把完整任务历史反复塞进请求。
- 每次修改/生成保存候选，独立审核后标可供下游使用；失败/取消保留已完成事实，继续/重试记录目标和范围。阶段内技术重试、内容修订及用户重新派发分别计数，不允许无界重试或无限付费生成。
- 文本阶段可高自动化；涉及核心改编决策超授权或重大歧义时请求明确选择。生图/视频的预算、并发和可接受重试次数须由项目设置/用户授权约束，程序控制停止。
- 当前story_segments、人物/团队/场景、分镜与图片能力可复用职责；原著解析、全篇联合规划、范围化执行、视频提示词/视频生成/声音/后期/成片验收仍需按实际执行器逐项建设，不能因已有definition就标为可执行。

### 字段归属与迁移

| 当前字段/职责 | 目标字段 | 调整 |
|---|---|---|
| basic_info.actual_script及原稿路径 | source、source_analysis | 原稿外部保存，按版本和区间读取；basic_info保留项目设置，不继续把10MB正文重复写进项目、任务快照和每次提示词 |
| basic_info.script_revision_node及优化盒子 | source_analysis | 新职责是忠实解析与索引，不可将旧改编稿直接标为原著解析结果 |
| 无独立联合规划产物 | adaptation_plan | 新增用户约束、剧情主线、人物/场景规划、爽点/伏笔及改编单元计划；有修订号及来源依据 |
| story_segments | story_segments | 保留稳定段ID，增加plan_item_id、来源区间、顺序、修订号；完整定稿可放body_ref；无episode_id |
| character_extraction、group_setting、scene_extraction及各自assets | asset_library | 统一保存人物、团队、场景、服装/造型、必要道具、声音及实际媒体；生产盒子改成向库的指定对象提交，不再各存一份权威资产 |
| shot_design.shots | shot_design | 继续引用故事段、人物、服装和场景ID，增加显式前镜ID及连续性状态；不内嵌定妆图或复制完整资产定义 |

| clip_arrangement | clip_arrangement | 继续表示技术生成分片编排：clip_id引用镜头/节拍范围，按实际生成接口容量安排；不承担提前分集或成片剪辑 |
| video_prompt、videos | video_prompt、videos | 按clip_id组织提示词及视频take，记录实际选用的不可变media_id，区分候选、审核结果和已选take |
| episodes | editing、delivery及episodes | 新增剪辑时间线和交付；episodes仅在后期分集时建立，引用时间线范围及导出文件，不参与前期故事/镜头归属 |
| change_plans及任务/调用记录 | 保留change_plans与既有records.sqlite | 内容影响决策和完整执行历史不复制进项目JSON；长任务进度保存检查点引用 |

上述是目标迁移结构，不能只改JSON字段名而不改Service、Schema、UI、校验与历史适配。旧项目保留原结构或经显式迁移；原ID尽量保留，重名ID建立映射；旧任务快照和HTTP记录不重写。现有字段不能与新库长期双写、形成两份权威数据。

### 分镜之后的资产闭环

1. 分镜读取当前定稿、联合规划及已有项目资产目录，优先引用已存在且符合要求的身份/造型/场景。
2. 缺失对象由模型提出需求，程序检索去重并分配稳定ID，在项目库登记待完善定义或待生成资源；镜头保存有效ID，不能虚构ID、把不存在资源写成已生成。
3. 同人物/同造型跨多个镜头汇总为一个需求；对比原著与改编授权确定是否真的换装，表情、动作、临时破损通常是镜头状态，不自动新建定妆套装。身份、时代、造型和关键状态不同则不可盲目合并。
4. 分镜内容审核与媒体齐备检查分开：缺图可以保留已通过的分镜与pending需求，进入视频生成前必须补齐本分片实际需要的资源。
5. 资产执行器复用已有合格图片/声音，或只生成缺项；结果写入asset_library，更新需求状态。库写入与镜头引用登记在项目写队列中保持一致，图片大文件保存外部，JSON只存引用。
6. 视频生成前把实际选择的media_id绑定到clip生成记录，保存引用快照；同一资产可被多个镜头/分片复用，新版本不覆写旧媒体事实。失败只影响缺项及依赖它的分片，不无条件重生成全剧资产。

### 长稿与持久化边界

项目JSON保存阶段索引、稳定ID、文件引用、所选版本及必要状态；原稿、章节索引/事实大表、完整定稿、长提示词、媒体和完整执行历史不重复内嵌。项目JSON及外部文件一起构成项目数据，必须一起备份和迁移。

外部产物先写不可变版本文件，再通过现有项目写队列原子更新JSON引用；失败时旧已提交引用仍有效，不出现JSON指向半写文件。新版本是否影响下游由主Agent按实际语义规划，不增加内容hash自动过期链。每个盒子仍保留独立node_state、规则及审核/任务记录；资产记录的生成/选用状态与规划/剧本/分镜的审核状态分开。

## 建议落地顺序

1. 本轮先落实纯程序创建/导入，消除无必要首轮模型调用。
2. 文件引用存储、预算化范围读取、检查点和忠实原著索引一同实现，先验证长稿可读全、可回查。
3. 改编方案与分段定稿共同接入，迁移旧“优化剧本”入口/规则/面板；不只改按钮名而沿用改编执行器。
4. 下游支持目标范围读取/保存及关联审核，最后接入主Agent自由编排。

现有项目不能把旧优化正文或旧故事大纲直接重命名成忠实原著索引；保留旧数据和历史，新增索引从原稿重新解析，用户选择后续采用的基稿。接口字段迁移、版本策略及各阶段实施AC在对应实施计划中细化。
