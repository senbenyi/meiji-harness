# 面板失败任务重试直接执行

- 类型：完整流程，任务队列行为修复。
- 目标：面板对失败节点再次生成/重新生成时，遵循文档约定直接启动新任务；不让本次重试继续停在暂停队列中。
- 非目标：不改变会话请求的排队行为，不跳过其他待执行任务，不自动开始与重试无关的排队任务，不调用真实模型。

## 验收标准与调研结论
| AC | 输入/状态 → 可观测结果 | 已确认/未确认/未验收 | 依据或缺口 |
|---|---|---|---|
| AC-1 | 面板节点任务解析/协议失败并暂停队列，随后对同一节点再次点击生成 → 失败历史保留，新任务按 regenerate 直接运行并可成功完成 | 已确认 | 生产库旧任务与审核步骤均为 failed；随后新任务 queued，queue_stopped=1；任务步骤契约规定面板重试直接开始新任务；generate 前置检查会拒绝已有内容 |

## 调用链与证据

- 面板 `task-panel.js:165-191` → `TaskService.command()`；文本节点的“AI生成”提交 action=generate，“重新生成”提交 action=regenerate。
- `createTextHandler` 解析模型响应失败 → `TaskService.#loop` catch → `#finish(..., failed)`；该结算将步骤/任务及节点标记失败并设置 `queue_stopped=true`。面板按钮仍发送 `action=generate`，已有内容时重试因此又会被 precheck 拒绝；重试需改走 regenerate 模板。
- 后续面板 submit 当前只对 `script-split` 清除暂停；其他业务增加 queued 任务后 `#pump` 因暂停返回。`meiji/dev_docs/任务步骤.md` 约定重新生成直接开始新任务。
- 当前真实 SQLite 只读证据：`episode-characters` 首次任务 `failed`，review 步骤记录 JSON parse 错误；同 target 的下一任务 `queued`，项目 `queue_stopped=1`，节点显示 queued。当前 SQLite 索引快照来自现有 Harness 数据，测试修改使用隔离数据库。
- GitNexus `TaskService.command` upstream MEDIUM：11 个直接调用方，涉及 app-runtime 的一个命令流程；索引标记 5 个 receiver 类型解析缺口，面板/会话入口通过实际源码补查。

## 问题
| AC | 预期 | 实际 | 根因 |
|---|---|---|---|
| AC-1 | 面板同节点重试直接开始并进入再生成 | 新任务 queued；若仅清除暂停会在 precheck 因已有内容再次 failed | 失败暂停队列；普通 submit 不解除暂停；旧 `action=generate` 未转换成 `regenerate` |
| AC-2 | 不误启动其他任务 | 需保持显式冲突 | 直启前需排除同 target 未完成任务并检查其他队列项 |

## 改动
### 阶段 1：面板重试直启
1. `meiji/server/flow/tasks/task-service.js:TaskService.command` — 仅在同一 target 的最新任务为失败/未通过/取消/作废时识别重试（兼容已排队重试），若无其他未完成任务则同事务解除暂停；generate 重试转为 regenerate；有其他任务返回冲突；会话和普通新任务不变 → AC-1/2/3。
2. `meiji/tests/stage04-task-queue.test.js` — 覆盖解析异常后同节点面板重试自动执行、旧终态保留、其他等待任务冲突、会话不自动恢复 → AC-1/2/3。
3. `.agents/meiji-dev.md` — 明确面板同节点重试直启及冲突边界，与业务数据说明统一 → AC-1/2/3。

验证：`node --test tests/stage04-task-queue.test.js tests/stage09-script-split.test.js` 与 `npm test --prefix meiji`；`git diff --check`、GitNexus detect-changes。
