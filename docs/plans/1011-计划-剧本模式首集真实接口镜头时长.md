# 剧本模式首集真实接口镜头时长

- 类型：根因已确认的业务流程 Bug
- 目标：让镜头生成和修订明确以本集参考时长为目标，并提供满足单镜 15 秒上限所需的最少镜头数；完成真实接口的第一集成片链路验收。
- 非目标：不改镜头总时长 ±30 秒程序校验、不强制各小段镜头时长逐段精确相等、不重跑或覆盖已经完成的剧本拆分、人物、第一集大纲和资产。

## 调研与根因
项目 `武松_兄长不死_六场约30分钟` 已导入同名 TXT，模式为 `剧本`。拆分、项目角色、第一集摘要/大纲/本集资产和角色图已有真实接口产物；第一集故事大纲四段时长为 40/80/90/90 秒，镜头表为空且有历史失败。为避免覆盖并重花已完成的接口费用，在此既有测试项目上建立新的续作组，保留所有历史任务。

调用链：Harness 镜头卡片 → `TaskService.#run` → `createTextHandler` → `promptValues` + shots YAML → 真实 chat 网关 → `prepareContent`/`assertOutput`。首次真实调用生成 14 镜/77 秒，证明此前模板只以程序校验兜底。第一轮修复加入 300 秒目标、270–330 秒容差和 20 镜下限；新任务确实调用真实接口，但生成 19 镜/150 秒，首轮修订 20 镜/165 秒，第二轮仍为 20 镜/165 秒。提示词已经把目标和下限传给模型，但没有要求生成前逐镜累计总秒数并把落在范围内作为输出硬条件；数量达标不等于总时长达标。因此提示词还缺输出前的时长预算分配与自检，而非网关未调用或程序未校验。

GitNexus 已绑定 `llm-dsh-plugins`，CLI 索引与 HEAD `69feb43` 一致。原 `promptValues` 上游影响风险为 CRITICAL（65 直接调用、16 个流程、6 个模块）；新一轮针对 `createTextHandler` 的检查为 HIGH（13 个符号、2 条流程、3 个模块）。本轮只改镜头专用 YAML 和模板断言，保留其它文本业务。

## 改动
1. `meiji/server/handlers/text-handler.js` `promptValues`：提供 `ceil(episode.时长秒 / 15)` 动态最少镜头数 → AC-1/2。
2. `meiji/dev_docs/in_puts/shots-generate.yaml`、`shots-regenerate.yaml`：明确输出前逐镜求和、区间是硬验收、数量达标不能代替总时长达标；继续按分段预算分配，不要求各小段精确相等 → AC-1/2/5。
3. `meiji/tests/stage05-shot-inputs.test.js`：验证 300 秒目标、20 镜、270–330 秒区间和两份模板中的硬求和指令 → AC-2。
4. 重启 Harness 后在现有剧本项目继续真实镜头任务，成功后发起第一集全量 `episode-film` → AC-3/4。

验证：基线相关测试 9 项通过；实施后重跑相关测试、`npm test`、`node scripts/prompt-diff.js shots`、`git diff --check`、GitNexus detect/index。真实验收检查新增任务状态、镜头总时长、每镜上限、生成提示词/HTTP 步骤，以及成片各步骤和文件有效性。
