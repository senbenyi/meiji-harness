# 操作 · 任务 · 节点三层模型（方案 v2）

- 类型：重构（完整流程）。取代 `计划-操作与任务文件拆分.md` 第 2～8 节的目标结构；该计划阶段 1 已完成的文件拆分作为本方案的起点保留。
- 目标：用「操作 → 任务 → 节点」三层统一面板按钮、执行记录与状态；状态逐层向上推导；自审不通过时动态追加「修订 + 复审」节点，次数可配置。
- 非目标：不改提示词 Model、skill、网关接口；内容节点（摘要、大纲、镜头…的 未生成/生成中/未通过/已通过）仍独立记录，只由任务结果写入。

## 1. 三层定义

| 层 | 是什么 | 状态来源 | 例子 |
|---|---|---|---|
| 操作 Operation | 用户一次点击（或会话工具一次调用）。只负责「创建哪些任务、按什么顺序」 | 由其任务状态推导 | 生成每秒指令、生成剧集摘要、单镜成片 |
| 任务 Task | 一个可独立排队、执行、停止的工作单元，产出一个内容节点 | 由其节点状态推导 | 单镜 S03 每秒指令、大纲、角色图 C01 |
| 节点 Node | 任务内的一步：生成、自审、修订、复审、图片请求、视频提交… | 自身执行结果 | generate、review、revise#1、re_review#1 |

- 只有一个任务的操作（如生成剧集摘要）：点击即创建并执行这一个任务，操作状态 = 任务状态，界面上不单独显示父级。
- 名称约定：本文的「节点」指任务里的执行节点（原「步骤」）；项目里的摘要、大纲等称「内容节点」，两者不混用。

## 2. 状态推导（自下而上）

节点状态：pending / running / completed / failed / cancelled / skipped；审核类节点另有结论 pass / fail。

任务状态（按优先级）：
| 节点情况 | 任务状态 |
|---|---|
| 全部 pending | queued |
| 有 running | running |
| 有 cancelled | cancelled |
| 有 failed（接口或程序错误） | failed |
| 最后一个审核节点 fail，且修订次数已用完 | review_failed |
| 最后一个审核节点 pass，或无审核节点且全部 completed | completed |

操作状态：
| 任务情况 | 操作状态 |
|---|---|
| 全部 queued | queued |
| 有 running | running |
| 有 failed | failed |
| 有 review_failed | review_failed |
| 有 cancelled | cancelled |
| 已开始但仍有 queued | running |
| 全部 completed | completed |

失败与审核未通过优先于取消：按停止规则其余任务是因根因任务而被取消的，操作状态反映根因；用户主动停止时为 cancelled。

执行模型（已确认）：同一剧集同一时间只运行一个生成操作（含排队中），操作内任务逐个执行，全部串行；不同剧集、不同项目之间可并行，受 text/image/video 队列上限约束。

停止规则（已确认）：任一任务 failed / review_failed / cancelled，同一操作下其余未结束任务全部取消；已完成的任务及其内容保留。

内容节点：任务结束时按现有规则写入（completed → 已通过；review_failed → 未通过并保留失败稿；接口失败且未保存草稿 → 恢复原内容）。操作和任务状态不写入内容节点。

## 3. 动态节点与重试次数

- 任务创建时只放基础节点。文本任务：`generate → review`；图片任务：`image_generate → image_download → image_save`；视频任务：`video_submit → video_generate → tail_frame`；人工保存：`save`（需要时加 `review`）。
- 审核节点结论为 fail（程序检查或模型自审），且已用修订次数 < 上限时，执行器在任务末尾追加 `revise#n → re_review#n`；结论 pass 或次数用完则不再追加。没有失败就没有修订节点，不再出现「跳过」的修订占位。
- 修订基于本轮最新失败稿和本轮审核意见；第 n 轮修订使用第 n 轮复审前的结果，与现在一次修订的规则一致。
- 修订上限 `maxRevisions`：每个任务文件里的独立属性，默认 2；0 表示审核不通过直接结束为 review_failed。
- 计划预估（排队时展示总节点数）只计基础节点，追加节点实时出现在任务里。

## 4. 操作与任务清单

> 文件名与目录以[文件清单](计划-操作任务节点三层模型-文件清单.md)第 4 节（v3）为准；单镜、单卡、按意见修改、成片部分步骤均为同一操作的参数。

| # | 操作（文件 `operations/`） | 任务（文件 `tasks/`） | 顺序 |
|---|---|---|---|
| 1 | operation-summary 生成剧集摘要（含弹框草稿模式） | summary ×1 | — |
| 2 | operation-story 生成剧集剧情 | outline → characters → scenes → props | 串行 |
| 3 | operation-character-image 生成角色图 | character-image ×1（按 itemId） | — |
| 4 | operation-scene-image 生成场景图 | scene-image ×1 | — |
| 5 | operation-prop-image 生成道具图 | prop-image ×1 | — |
| 6 | operation-shot-table 生成镜头表 | shot-table ×1 | — |
| 7 | operation-seconds 生成每秒指令 | shot-seconds × 镜头数（S01…Sn） | 串行（后镜引用前镜本轮结果） |
| 8 | operation-film 成片（整集） | 每镜 storyboard-prompt → video | 每镜内串行，镜与镜按顺序 |

同一任务被多个操作复用：
- 单镜重新生成每秒指令 = 操作 generate-shot-seconds，任务 shot-seconds ×1。
- 单镜成片 = 操作 produce-shot，任务 storyboard-prompt → video。
- 按意见修改人物卡/场景卡 = 操作 revise-characters / revise-scenes，任务 characters / scenes ×1（mode=modify）。
- 按意见重写单镜 = 操作 revise-shot，任务 shot-table ×1（单镜修改模式）。
- 重绘图片 = 3/4/5 的 modify 模式。

直接操作（不排队）：编辑大纲/人物/场景文字、编辑分镜、修改镜头素材、新增/编辑/删除剧集、删除项目、保存概要、导入/关联/删除图片、设置/移除参考图、确认/放弃候选图、忽略自审、合成（assemble，已确认归操作）。改动内容的直接操作仍写一条只含 `save`（必要时 `review`）的任务记录，用于历史与版本留痕；创建、打开、删除等无项目归属或删除目录的操作不留记录。

取消：`operations/cancel.js` 只调用取消接口，按操作 id 或任务 id 停止（任务 id 也会连带停止同操作其余任务），不创建任务、不留记录。

删除：铅笔分镜（pencil）操作、任务、前端入口与测试（已确认取消）。

## 6. 记录结构

- 操作记录 `history/operations/<operationId>.json`：action、mode、发起人、requirements/opinion、taskIds（按顺序）、状态缓存、时间、错误。
- 任务记录 `history/tasks/<taskId>.json`：新增 `operationId`、`type`、`target`、`maxRevisions`；`steps` 更名为 `nodes`（追加节点带 `round`）。
- 状态缓存均可由下层重新推导，推导函数集中在 `shared/task-steps.js`：`deriveTaskStatus(nodes)`、`deriveOperationStatus(tasks)`。
- 旧任务记录（无 operationId）在历史中按「单任务操作」只读展示；提供迁移脚本，不做运行时双写。

## 7. 用户决定（2026-10-03）

1. 修订次数是每个任务文件里的独立属性 `maxRevisions`，各任务单独配置，默认 2。没有自审或没有修订提示词的任务（分镜文本提示词为程序生成、图片、视频）写 0。注意：现有文本任务从「最多修订 1 次」变为默认 2 次，相关测试按新行为调整。
2. 接口出错不在任务层重试（属于网络层），节点直接 failed。
3. 成片同样适用「任一任务失败、审核不通过或停止 → 同操作其余未结束任务全部取消」。

## 13. 统一入口与 ID 生成（2026-10-03 核对）

现状：
| 发起方式 | 入口 | ID 在哪里生成 |
|---|---|---|
| 面板生成类按钮 | panel-routes → `tasks.start`（task-manager.js） | task-manager.js `start()` 的 randomUUID，即任务 id；同一个 id 作为 runOperation 的 `operationId` 传下去，接口返回字段也叫 operationId（命名混用） |
| 面板直接操作（directActions） | panel-routes → `runOperation` | run-operation.js:29 randomUUID，startExecution 用它建任务记录 |
| 会话生成（meiji_content_generate） | `tasks.start`，与面板生成相同 | 同面板生成 |
| 会话创建项目 | `runOperation` | 同面板直接操作（不留记录） |

结论：会话与面板的生成已经共用同一入口，差别只在会话校验 agent:true、工具内另有前置检查。问题是 ID 有两个生成点，且「操作 id」实际是任务 id。

目标：
- `operation-manager.start(op, session)` 是面板与会话、生成类与直接类的唯一入口，只在这里生成 operationId。生成类入队，直接类立即执行并等待结果返回。
- 任务 id 只在 operation-runner 展开任务时生成：操作开始即为全部任务建记录（queued），之后逐个执行。
- 运行时上下文中 operationId 与 taskId 分开命名，不再混用。
- panel-routes 去掉 directActions 分支，统一调用 operation-manager；会话 create 也改走 operation-manager。
- 会话工具里的前置检查（摘要未通过不能生成剧情、已有已通过内容直接返回）移到对应操作文件的 `precheck`，面板与会话共用。

## 14. 查看与控制入口（2026-10-03）

现状：只有任务一层。历史页 `GET /history?projectId&episodeId` 返回全部任务记录，前端按 action 名分组过滤（execution-history.js 的 scopes）；当前任务页 `GET /tasks/current`；提示词 `GET /history?taskId&stepId`；内容快照 `GET /history?artifactId`；生成按钮旁的「查看任务」打开整页当前任务，不定位到具体任务；会话 meiji_task_control 按 taskId。

目标：操作、任务、节点三层都能直接查看，历史按「内容 target」过滤而不是按 action 名。

| 入口 | 接口 | 返回 |
|---|---|---|
| 当前任务页 | `GET /operations/current?projectId&episodeId` | 进行中/排队中的操作 → 任务 → 节点，含排队位置 |
| 任务历史页（按阶段） | `GET /operations?projectId&episodeId&targets=outline,characters,…&status` | 涉及这些内容的操作列表；展开为任务 → 节点 |
| 操作详情 | `GET /operations/:operationId` | 操作 + 全部任务 + 节点 |
| 任务详情（子任务单独查看） | `GET /tasks/:taskId` | 单个任务的节点、产物、所属 operationId（可跳回操作） |
| 某项内容的历史 | `GET /tasks?projectId&episodeId&target=characters` | 写过该内容的所有任务（来自生成操作、单项修订、人工编辑），按时间倒序 |
| 节点提示词 | `GET /tasks/:taskId/nodes/:nodeId/prompts` | 该节点实际请求快照（替代 `/history?taskId&stepId`） |
| 内容快照 | `GET /artifacts/:artifactId` | 不变，仅改路径 |

## 17. 状态稳定性

### 17.1 现有问题（核对代码）

现在有三套状态并行写入：
| 状态 | 用途 | 写入位置 |
|---|---|---|
| 任务状态 | 当前任务、历史 | 由步骤推导（deriveTaskStatus），较稳定 |
| 内容节点状态 | 各阶段「已通过/未通过/生成中」 | 约 13 个文件直接赋值（drama-model、project-rules、review-checks、run-operation、task-execution、film-video、episode-save、image-candidate、review-override…） |
| 剧集 `activity` / `activityError` | 按钮禁用（generation-stage-views.js 28 处 `Boolean(project.activity)`）、「生成中」文案、页面错误提示 | 20 多处直接写入 |

疑似缺陷（需先写测试复现）：
- B1（已核对，降级）：面板上同一集实际是串行的——执行中所有生成按钮因 `project.activity` 禁用，会话只能发起剧集级阶段，成片「依次生成」本身串行。但代码层未禁止：task-manager.js:119 与 run-operation 的 running 键都允许不同镜头同时进行。唯一缝隙：前一个单镜操作还在排队时尚未写入 `activity`，此时其他镜头的按钮仍可点击，两个操作会先后执行到同一集。新方案按剧集加锁（含排队中）后此缝隙消失。
- B2 `activityError` 只有一个，任意操作的错误互相覆盖（图片部分已修，其他操作仍存在）。
- B3 两把锁并存：task-manager 的冲突检查与 run-operation 的 `running` 键，规则不完全一致。
- B4 内容节点状态多处赋值，同一转换（如停止）在不同操作中写法不同。

### 17.2 修正原则

1. 「是否在执行」只由进行中的操作推导（operation-manager 内存状态 + /operations/current），删除剧集 `activity`、`activeOperation` 字段；按钮禁用与「生成中」改为查询该按钮对应 scope 是否有进行中操作。
2. 错误只记录在任务与节点上；页面提示读取对应内容最近一次任务的错误，删除剧集 `activityError`。
3. 只保留一把锁：operation-manager 加锁——生成类按剧集（同一集一个，含排队中），项目级操作按项目；runner 不再另加锁。直接操作与进行中生成操作的冲突规则沿用现状。
4. 内容节点状态只经一个模块转换：`shared/content-state.js`（markGenerating / markFailed / markPassed / markPendingReview / statusFromCheck / settleByCheck / 聚合刷新），转换表写在一处，服务端其他文件不得直接给 status 赋值（测试检查）。放在 shared 而非 runtime：数据层（project-store、content-records）也要转换状态，按分层不能引用 runtime；转换本身是无 IO 的纯规则。
5. 状态均可重算：任务由节点推导、操作由任务推导；持久化的 status 只是缓存，读取时以推导结果为准。

### 17.3 验收

| AC | 输入/状态 → 可观测结果 |
|---|---|
| AC-S1 | 某集已有生成操作（含排队中）时，从面板或会话再发起该集任何生成操作 → 拒绝并提示上一项操作还在进行；另一集的操作可同时进行 |
| AC-S2 | 两个操作先后失败 → 各自内容显示各自的错误，不互相覆盖 |
| AC-S3 | 停止、接口失败、审核不通过、重启取消四种结束方式 → 内容节点转换结果与转换表一致（逐一测试） |
| AC-S4 | 服务端文件出现内容节点 status 赋值（不经 shared/content-state.js）→ 测试失败 |
| AC-S5 | 删除缓存 status 后重新读取 → 任务与操作状态推导结果不变 |

## 18. 面板与会话的互斥（2026-10-03）

### 18.1 现状（核对代码）
| 场景 | 现在的行为 | 问题 |
|---|---|---|
| 会话发起生成后，面板点生成 | 两边都走 tasks.start，冲突检查返回 409「上一项操作还在进行」 | 会话任务排队期间面板按钮仍可点（按钮只看 activity，排队时尚未写入），点了才报错 |
| 面板生成执行中，会话发起 | tasks.start 抛错，工具调用失败 | 会话只拿到一句报错，不知道被谁占用、何时可以重试；工具说明没有约定怎么处理 |
| 面板生成执行中，面板编辑 | runOperation 的 running 锁拒绝 | 与生成用的是两套锁 |
| 会话任务排队中，面板编辑 | 允许 | 排队中的操作稍后基于被改过的内容执行，结果不可预期 |
| 停止 | 面板可停止任何会话发起的任务；会话只能停止本会话的任务 | 合理，保留 |

### 18.2 方案：剧集占用
- operation-manager 为每集维护「占用」：当前操作（排队中或执行中）的 operationId、名称、状态、发起方（面板 / 会话）。这是面板与会话共用的唯一判断依据，取代 activity 与两套锁。
- 占用从操作入队开始，到操作结束（完成、失败、审核不通过、取消）释放。
- 面板：占用信息随 /events 推送；该集所有生成按钮和会改内容的直接操作按钮置灰，页面顶部显示「本集正在执行：生成剧情（会话发起）· 查看 · 停止」。若并发请求仍到达服务端，返回 409 并附占用信息。审核意见等草稿输入不受影响（沿用「运行中新输入不丢失」）。
- 会话：发起时该集被占用 → 不报错，返回结构化结果 `{ busy: true, operationId, label, initiator }`；工具说明约定：告知用户，并用 `wait(operationId)` 等待该操作结束后再发起。会话对非本会话发起的操作只能 wait，不能 cancel。
- 不同剧集、不同项目互不影响。

### 18.3 用户决定
选 A：会话遇到占用立即返回 busy，由会话 wait 该操作结束后重新发起；面板不排队，直接置灰。

### 18.4 验收
| AC | 输入/状态 → 可观测结果 |
|---|---|
| AC-M1 | 会话发起生成剧情（排队中或执行中）→ 面板该集生成与编辑按钮置灰，顶部显示占用信息；其他剧集按钮可用 |
| AC-M2 | 面板生成执行中，会话发起任一生成 → 返回 busy 与占用操作 id；wait 该 id 结束后再次发起成功 |
| AC-M3 | 绕过面板置灰直接请求接口 → 409 并返回占用信息，不产生操作记录 |
| AC-M4 | 占用操作以完成 / 失败 / 审核不通过 / 停止 / 重启取消结束 → 占用释放，面板按钮恢复 |
| AC-M5 | 会话对面板发起的操作调用 cancel → 拒绝；面板可停止会话发起的操作 |
