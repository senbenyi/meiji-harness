# Elysium 持久化任务驱动设计

日期：2026-09-19　状态：已实施（第六版）；验收证据见 `docs/implement/实施-持久化任务驱动.md`

## 1. 结论

任务驱动只由两个管理器组成，二者都不理解业务：

| 角色 | 只负责 | 不负责 |
| --- | --- | --- |
| **任务管理器**（`worker/manager`） | 异步接收任务 → 入队排队 → 加锁执行 → 回写状态 | 编排顺序、解析业务结构、版本、验收 |
| **驱动管理器**（`worker/driver`） | 持续循环：对账、观察、结算、派发 | 决定提交什么、修改任务内容 |
| **提交方**（Session、Service） | 提交完整、有序、结构正确的任务；处理结果；决定下一步 | 执行、排队、加锁 |

### 1.1 管理范围

**只管理和模型交互、需要占用生成算力的任务**：图片生成（`image`）和视频生成（`video`），无论后端是 ComfyUI GPU 还是三方模型 API。

**不属于本管理范围、单独处理**：上传、下载、状态查询、本地合成与剪辑（ffmpeg）、媒体探测、校验等不占生成算力的操作。它们继续由各自模块同步完成，或另行设计，不进入任务记录、驱动索引，也不占用并发名额。

### 1.2 三处存储

| 存储 | 路径 | 职责 | 可变性 |
| --- | --- | --- | --- |
| **任务记录** | `projects/tasks/<task_id>.json` | 提交了什么：原始请求、泳道、序号、归属、回写标识 | 写入后不可变 |
| **驱动索引** | `runtime/driver.json` | 按什么顺序执行：泳道配置、未闭环条目的顺序、序号计数器 | 可变；可由另外两处重建 |
| **执行记录** | `projects/jobs/<job_id>/` | 执行成什么样：路由后的输入、状态、结果、诊断、结算标记 | 状态只在这里 |

项目目录（`projects/<project_id>/`）的内容不归任务驱动管理；`project_id` 只作为任务的归属属性被记录。

### 1.3 已确认的决策

| 决策 | 内容 |
| --- | --- |
| 失败处理 | 任务失败时写入 `failed`，**继续执行下一个任务**；不停住泳道 |
| 重试 | **只能人工手动重试**；重试的任务回到原 `seq` 位置，不插队 |
| 并发 | **全局同时只执行 1 个任务**（`queue.max_running = 1`） |
| 索引重建 | `driver.json` 重建后，所有泳道**接着上一次的位置继续驱动** |
| Session 等待 | 单次生成保持现有的阻塞等待；导演批量提交用 Harness 后台任务通知（`ctx.jobs`） |
| 进程模型 | 同一台电脑**只有一个 Harness 进程**，但有**多个 Session 对话**同时提交 |

```text
Session A / Session B / …（Tools）      Service（Server / 项目服务）
   │  各自保证顺序与结构                   │  自己保证顺序与结构
   └──────────── submit(泳道, 有序任务[]) ──┘
                          │
                          ▼
┌──────────────── 任务管理器 worker/manager（进程内单例）────────────────┐
│ 接收：校验 → 路由 → tasks/ 记录 → jobs/ 建档(pending) → driver.json 追加 → 回执 │
│ 队列：泳道按 seq FIFO；interactive 优先；泳道间轮转；全局并发 1               │
│ 锁  ：进程内队列互斥 / 会话锁 / Job 启动锁                                   │
│ 执行：dispatch = launch(已建档 Job)                                           │
│ 回写：status.json、settled.json、调用提交方回写处理器                          │
└──────────────────────────────────────────────────────────────────────────────┘
                          ▲  每轮调用
┌──────────────── 驱动管理器 worker/driver（进程内单例）─────────────────┐
│ 对账 → 观察 → 结算 → 派发 → 休眠/被唤醒 → 循环                           │
└──────────────────────────────────────────────────────────────────────────┘
                          │ spawn detached（现有）
                          ▼
              Worker 子进程 → Provider / ComfyUI / 三方 API
```

### 2.2 代码缺口

| 现状 | 位置 | 问题 |
| --- | --- | --- |
| `submitTask` 同步完成复用、路由、建档、启动 | `worker/manager/manager.js` | 没有“接收”和“执行”之分，也就没有队列 |
| 每次提交立即 `launch` 一个 detached Worker | `worker/runner/launcher.js` | 多个 Session 同时提交时，所有任务同时压向后端 |
| Job 状态只有 `queued/running/succeeded/failed` | `worker/store/status.js` | 没有“已接收、待派发”和“已取消” |
| Job ID 随机；建档与首次写状态之间有空档 | `worker/store/records.js`、`runner/inspect.js` | 重复提交无法幂等；空档期崩溃后 `getJob` 返回 404 |
| 没有持续推进者 | — | 状态推进只能靠调用方等待（`waitJob`） |
| 完成后没有回写通道 | — | 提交方只能轮询 |
| `saveJson` 临时文件名固定 | `database/json.js` | 同一文件并发写会损坏 |
| `status.json` 中存在本机绝对路径 | `runner/context.js` 写入的 `debug.*_path` | 目录迁移后失效 |

### 2.3 Harness 已有能力核查（避免重复造轮子）

已检查本机安装的 `@deepseek-ai/dsh@0.1.2-rc.1` 全部包和 `harness/.dsh` 预设：

| 包 | 实际能力 | 能否替代任务管理器 / 驱动管理器 | 结论 |
| --- | --- | --- | --- |
| `dsh-jobs` + `dsh-jobs-local` | 后台任务注册表：`<kind>-N` ID、按会话隔离、`wait`、`kill`、完成监听；**进程内存，随 Harness 进程销毁** | 不能：不持久、没有泳道顺序和并发控制 | **复用于导演批量提交的等待与完成通知**（§7.2） |
| `dsh-tool-jobs` | 给模型提供 `job_output`、`job_list`、`job_kill`，完成时向会话注入通知；Elysium 预设已加载 | — | 与上面一起复用 |
| `dsh-schedule` | 会话内持久提醒，最短 5 分钟 | 不能 | 不用 |
| `dsh-workflow` | 模型脚本编排子 Agent，阻塞整个轮次 | 不能 | 不用 |
| `dsh-webhook` | 进程内触发，没有队列和重试 | 不能 | 不用 |
| `dsh-deque` | 内存双端队列 | 只是数据结构 | 可选 |
| `dsh-atomic-write` / `dsh-storage-json` | 原子写 / KV，没有自动恢复的锁 | 不能 | 不用 |

结论：Harness 中没有持久化、跨重启、有顺序保证的任务队列，任务管理器和驱动管理器需要自己实现；`dsh-jobs` 只用于 Session 侧的等待与通知。`ctx.jobs.start` 的具体参数需要在实施时对照包内 `lib/index.d.ts` 确认（**未确认**）。

### 2.4 本项目可直接复用

- `routeTask`：路由与计划校验。
- `launch`：启动或接管 Worker。
- Provider 自身的提交记录（ComfyUI `comfyui-submission.json`、BytePlus `byteplus-submission.json`）：响应丢失时不会重复提交。
- `getJob` 的失联判定、`assertRetryAllowed` 的授权规则、`withLaunchLock`。

## 3. 闭环规则

| # | 规则 | 保证什么 |
| --- | --- | --- |
| R1 | **状态只写在 `jobs/<id>/status.json`**；任务记录和驱动索引都不保存状态 | 不会出现多处状态互相矛盾 |
| R2 | **`task_id` 就是 `job_id`**，一个任务只对应一个 Job；重试沿用同一个 Job | 任务和执行一一对应 |
| R3 | **顺序以任务记录为准**：受理时写入 `lane` 和全局单调递增的 `seq`；`driver.json` 只是可重建的索引 | 索引丢失时顺序仍可恢复 |
| R4 | **写入顺序固定**：任务记录 → Job 建档（`pending`）→ 追加驱动索引 | 任何一步崩溃都能被对账补齐 |
| R5 | **驱动每轮对账**：有任务记录没有 Job → 补建；Job 为 `pending` 但不在索引中 → 按 `seq` 补回；已结束且已结算 → 从索引移除 | 三处存储最终一致 |
| R6 | **结算至少投递一次**：Job 结束后调用提交方回写处理器，成功后写 `settled.json` | 结果一定交回提交方 |
| R7 | **执行记录中不存本机绝对路径**：Job 内文件相对 Job 目录，项目媒体相对存储根目录 | 目录迁移不会让记录失效 |

```text
提交 ─► tasks/<id>.json ─► jobs/<id>/status.json = pending ─► driver.json 追加
                                                                 │
        ┌──────────────────── 驱动每轮 ◄──────────────────────────┘
        ▼
  对账（R5）→ 观察运行中的 Job → 结算（R6）→ 派发下一个（launch → queued）
                                                   │
                                     Worker 写 running → succeeded / failed
  succeeded / failed / cancelled 且已结算 → 移出 driver.json → 闭环
  failed 的任务等待人工重试 → 状态回到 pending → 按原 seq 重新入索引
```

## 4. 数据模型

### 4.1 任务记录 `projects/tasks/<task_id>.json`

```json
{
  "schema_version": 1,
  "task_id": "9f2c…(32 hex)",
  "submission_id": "wb-6f1c…",
  "index": 0,
  "seq": 1042,
  "lane": { "id": "project-1234abcd-main", "priority": "batch" },
  "project_id": "1234abcd",
  "kind": "video",
  "plan": { "mode": "i2va", "prompt": "…", "duration_seconds": 3, "first_frame": "job:0123…" },
  "binding": { "type": "shot", "shot_id": "a1b2c3d4" },
  "channel": "workbench",
  "request_hash": "sha256…",
  "submitted_at": 1789747200000
}
```

- 写入后不可变，是“提交了什么”的原始证据；路由后的计划保存在 Job 中。
- `kind` 只能是 `image` 或 `video`（§1.1）。
- 在本设计实施前直接提交、没有任务记录的 Job 称为**旧任务**。驱动不主动管理旧任务；人工重试旧任务时，按 §5.5 先补写任务记录。

### 4.2 执行记录 `projects/jobs/<job_id>/`

```text
projects/jobs/<job_id>/
├── input/request.json    # 已路由、已校验的计划（现有）
├── input/backend.json    # 后端快照（现有）
├── input/origin.json     # 新增：{task_id, submission_id, lane_id, seq, binding, project_id}
├── status.json           # 状态唯一真相（新增 pending / cancelled）
├── settled.json          # 新增：结算标记 {status, finished_at, settled_at}
├── launch.lock/          # 现有：Job 启动锁
└── ...                   # Worker 执行产物、Provider 提交记录、诊断（现有）
```

- `origin.json` 是任务记录的摘要，便于只看 Job 目录时找到来源。它不并入 `request.json`，因为 Provider 会拒绝计划中的未知键。
- `status.json` 中的 `debug.diagnostic_path`、`debug.log_path` 改为相对 Job 目录的文件名（R7）。

### 4.3 驱动索引 `runtime/driver.json`

```json
{
  "schema_version": 1,
  "next_seq": 1043,
  "lanes": {
    "project-1234abcd-main": { "priority": "batch", "paused": false },
    "session-4be1c0d27a9f3e11": { "priority": "interactive", "paused": false }
  },
  "entries": [
    { "seq": 1041, "task_id": "…", "lane_id": "project-1234abcd-main" },
    { "seq": 1042, "task_id": "…", "lane_id": "project-1234abcd-main" }
  ],
  "rebuilt_at": null,
  "updated_at": 1789747210000
}
```

- `entries` 只保留**未结束或未结算**的任务，按 `seq` 升序排列；闭环后移除，所以文件有大小上限。
- 已失败并已结算的任务移出索引，等待人工重试；重试时按原 `seq` 重新加入。
- **重建**（文件缺失或校验失败时）：
  1. 扫描 `tasks/`，找出 Job 为 `pending`、`queued`、`running`，或已结束但未结算的任务，按 `seq` 排序写入 `entries`；
  2. `next_seq = max(seq) + 1`；
  3. 泳道配置取各泳道最新任务记录中的 `lane`；`paused` 恢复为 `false`；
  4. 写入 `rebuilt_at`，然后**立即接着上一次的位置继续驱动**。

### 4.4 任务状态机（`store/status.js` 扩展）

```text
(none) ──受理──► pending ──派发──► queued ──► running ──► succeeded（终态）
                   │                                   │
                   └──取消──► cancelled（终态）           └──► failed ──人工重试──► pending
```

| 状态 | 写入者 | 含义 |
| --- | --- | --- |
| `pending` | 任务管理器（受理或人工重试） | 已建档，在队列中，未占用后端 |
| `queued` | `launch`（现有） | 已派发，Worker 已启动 |
| `running` | Worker（现有） | 执行中 |
| `succeeded` | Worker（现有） | 终态，结果受保护 |
| `failed` | Worker、`launch`（现有），或派发前检查（§5.3） | 不会自动重试，只等人工重试 |
| `cancelled` | 任务管理器 | 终态；只能从 `pending` 进入，因为已派发的任务无法保证远端真正停止 |

`NEXT` 表新增：`none → pending`、`pending → queued | failed | cancelled`、`failed → pending`（人工重试时重新排队，不直接启动）；`cancelled` 为终态。`waitJob` 和 `completedResult` 需要把 `cancelled` 视为终态。

### 4.5 标识与幂等

| 标识 | 规则 |
| --- | --- |
| `submission_id` | 提交方生成，`^[A-Za-z0-9_-]{8,128}$`。Session 为 `s-` + `sha256(session_id, call_id)` 前 32 位；Service 自行生成 |
| `task_id` = `job_id` | `sha256(submission_id + "/" + index)` 前 32 位 hex |
| `lane_id` | 提交方指定，`^[a-z0-9][a-z0-9:_-]{0,95}$`，例如 `session-<hash16>`、`project-1234abcd-main` |
| `seq` | 全局单调递增整数，受理时在队列互斥内分配 |

重复提交同一 `submission_id` 时，如果第 0 个任务记录已存在，就比较 `request_hash`：一致则返回原回执，并按 R5 补齐缺失部分；不一致则返回 `409 SUBMISSION_CONFLICT`。Session 标识不以明文进入任务记录或索引。

## 5. 任务管理器（`worker/manager`）

### 5.1 接收 `submit`

```js
submit({
  submission_id, lane: { id, priority },
  project_id,
  tasks: [{ kind, plan, binding }],   // 有序；顺序即执行顺序
}, invocation?) -> SubmitReceipt
```

接收是同步的，但**不执行任何任务**。一次提交中的任务要么全部接收，要么全部拒绝：

1. **格式**：`kind ∈ {image, video}`；`plan` 与对应工具参数一致；`binding` 是提交方定义的不透明对象（≤ 2 KB）；`project_id` 只校验格式，不检查项目内容。
2. **引用约束**（引擎唯一的结构检查）：`plan` 中的每个 `job:<id>` 引用，要么指向已 `succeeded` 的 Job，要么指向同一泳道中排在它前面的任务（包括本次提交中序号更小的任务）。
3. **路由与预检**：逐个调用 `routeTask(kind, plan)`；任一失败则整批返回 422，并附上每个任务的错误。
4. **在队列互斥内**：
   - 分配 `seq`；
   - 写入任务记录；
   - 建档 Job：在 `jobs/.tmp-<uuid>/` 中写 `input/*`、`origin.json`、`status.json(pending)`，再 `rename` 为 `jobs/<job_id>`；
   - 追加 `driver.json` 条目。
5. **唤醒**驱动，返回回执。

**提交回执：**

```json
{
  "submission_id": "s-…", "lane_id": "project-1234abcd-main", "accepted_at": 1789747200000,
  "tasks": [
    { "index": 0, "task_id": "…", "seq": 1041, "status": "pending", "position": 4 },
    { "index": 1, "task_id": "…", "seq": 1042, "status": "pending", "position": 5 }
  ]
}
```

`position` 是该任务在全局派发顺序中的预估位置。提交方拿到 `task_id` 后，可以立即在后续任务中用 `job:<task_id>` 引用它。

### 5.2 队列（`manager/queue.js`）

- **全局并发**：同一时刻最多 `queue.max_running` 个任务处于 `queued` 或 `running`，默认且当前只支持 **1**。
- **泳道内顺序**：按 `seq` 升序，前一个任务结束后才派发下一个；不提供重排或插队。
- **失败不阻塞**：任务失败后泳道继续派发下一个任务。
- **泳道间选择**：`interactive`（Session 单次生成）先于 `batch`；同一优先级的多条泳道轮转，每轮每条泳道最多派发 1 个。这样多个 Session 同时提交时，不会有一条长泳道独占执行机会。
- **暂停**：`paused` 的泳道不派发；已派发的任务不受影响。

### 5.3 执行 `dispatch`

在队列互斥内：

1. 确认任务仍是 `pending`，全局运行数未满；
2. **引用检查**：`plan` 中引用的 Job 已 `failed` 或 `cancelled` 时，直接把本任务写为 `failed`（`error_code = REFERENCE_FAILED`），不启动 Worker，也不占用算力，然后继续下一个任务；
3. 调用现有的 `launch(jobId, capability)`，由它在 Job 启动锁内写入 `queued` 并 spawn Worker。

之后执行过程与现在完全一致。`launch` 失败时会自己写入 `failed`，驱动继续下一个任务。

### 5.4 回写状态与结算 `settle`

- **状态回写**：`status.json` 由 Worker 和任务管理器写入（R1）。时间线从 `status.json` 的时间戳和 Provider 记录中读取，不另设事件日志。
- **结算**（任务进入 `succeeded`、`failed` 或 `cancelled` 后，由驱动逐个串行执行）：
  1. `settled.json` 已记录本次终态（`status + finished_at` 一致）时，直接跳过；
  2. 按 `binding.type` 调用提交方注册的回写处理器 `handler(job, task)`；
  3. 成功后写 `settled.json`，然后从索引中移除；失败则记录 `settle_error`，下一轮重试（至少投递一次，处理器必须幂等）；
  4. 没有 `binding` 或没有对应处理器的任务，直接写 `settled.json`。
- 人工重试后任务再次结束，`finished_at` 改变，结算会重新执行，提交方能收到最新结果。
- 回写处理器注册表位于 `manager/sinks.js`：`registerSink(type, async (job, task) => { … })`。引擎不理解 `binding` 的含义。

### 5.5 管理命令

| 命令 | 前提 | 效果 |
| --- | --- | --- |
| `retry(task_id, { consent })` | `failed`，且满足现有 `assertRetryAllowed`（Session 需要用户原话要求，工作台按钮即视为同意） | 需要重提 ComfyUI 工作流时写 `resume-request.json`；状态写回 `pending`，按原 `seq` 重新加入索引。排在原位置，不插队 |
| `retry` 旧任务 | 旧 Job 为 `failed` 且没有任务记录 | 先按 Job 的 `input/` 和 `project_id` 补写任务记录（`lane = legacy-<project_id>`，分配新 `seq`，`channel = legacy`），再按上一行处理 |
| `cancel(task_id)` | `pending` | 写 `cancelled`；已派发的任务返回 409 |
| `cancelLane(lane_id, { from_seq? })` | — | 把泳道中（或从某个 `seq` 起）所有 `pending` 任务写为 `cancelled` |
| `pause(lane_id)` / `resume(lane_id)` | — | 停止或恢复派发 |
| `getLane(lane_id)` | — | 按 `seq` 列出任务、状态（读 Job）、位置和结算情况 |

**不提供**自动重试、重排、插入或修改已提交任务的命令。需要不同的顺序或内容时，由提交方取消后重新提交。

### 5.6 锁

已确认同一台电脑只有一个 Harness 进程，所以任务管理器和驱动管理器都是**进程内单例**，不需要跨进程的主控租约：

| 锁 | 位置 | 保护对象 |
| --- | --- | --- |
| **队列互斥**（新增，进程内） | 任务管理器单例 | `driver.json` 的读改写、`seq` 分配、受理写入、派发、命令。多个 Session 的并发提交在这里串行 |
| **会话锁**（现有） | `runtime/sessions/<hash>/` | 同一 Session 内串行受理，保证 `reusableTask` 判断正确 |
| **Job 启动锁**（现有） | `projects/jobs/<id>/launch.lock/` | `launch`、取消、重试改状态；与 Worker 子进程之间互斥 |

规则：

- **获取顺序固定为：会话锁 → 队列互斥 → Job 启动锁**，不允许反向获取。
- 持有队列互斥期间只做文件读写和 `launch`（它只等待子进程 spawn），不等待模型、远端或回写处理器。
- 结算由驱动循环串行执行，不需要额外的锁。
- 所有写入都用随机临时名加 `rename`，同时修复 `saveJson` 固定临时名的问题。

## 6. 驱动管理器（`worker/driver`）

```text
loop（有未结束任务时每 2 秒一轮，空闲时每 15 秒一轮；submit、retry 等命令会立即唤醒）：
  1. 对账（R5）
     · driver.json 缺失或损坏 → 按 §4.3 重建，并接着继续
     · 有任务记录、没有 Job 目录 → 按任务记录重新路由建档（pending）；路由失败则写 failed
     · Job 为 pending，但不在索引中 → 按 seq 补回
  2. 观察：读取正在运行的 Job 的状态（getJob）
  3. 结算：已结束、未结算的任务 → manager.settle（在队列互斥之外执行）
  4. 派发：运行数未满时，按 §5.2 选出下一个任务 → manager.dispatch
  5. 清理：已结束且已结算的条目从索引移除
```

- 全量对账（扫描 `tasks/`）只在启动时和每 10 分钟做一次；平时只核对索引中的条目。
- 单个任务的错误只记录在该 Job（`settle_error`）或日志中，不影响其他任务；循环本身不退出。
- 驱动随 Web 生命周期在插件主进程中启动和停止（`createTaskDriver()`）。Worker 仍是 detached 子进程，插件重启不影响正在执行的任务；驱动恢复后从索引接着驱动。

## 7. 提交方职责

### 7.1 提交方必须保证

1. **结构完整**：每个任务的 `plan` 完整、可执行；引擎不补全，不完整就整批拒绝。
2. **顺序正确**：先提交被依赖的任务，依赖链放在同一泳道，用 `job:<task_id>` 引用前面的结果。
3. **失败处理**：任务失败不会阻塞泳道。依赖失败任务的后续任务会在派发前以 `REFERENCE_FAILED` 失败，提交方需要决定人工重试哪个任务、重新提交哪些任务。
4. **幂等**：同一意图重复提交时使用同一个 `submission_id`。
5. **回写处理器幂等**：结算可能重复投递。
6. **业务状态自管**：项目是否存在、版本、验收、采用哪个结果、合成等，都由提交方负责。
7. **非模型操作自理**：上传、下载、状态查询、本地合成等不走任务驱动。

### 7.2 Session（Tools）

多个 Session 可以同时提交。每个 Session 使用独立的泳道 `session-<hash16>`，由队列互斥串行受理，驱动在泳道之间轮转派发。

| 场景 | 提交方式 |
| --- | --- |
| 单次生成（`call_tools_image/video`） | 本 Session 泳道，`interactive`，1 个任务；**保持现有阻塞等待**：工具内 `waitJob` 后返回 `completedResult`，Agent 看到的结构不变 |
| 导演模式批量生产 | Agent 按顺序构造任务（先锚点图，再逐镜视频，用 `job:<锚点 task_id>` 引用），通过批量提交工具提交到项目泳道（`batch`）；**用 `ctx.jobs` 注册后台等待**，任务完成时由 `dsh-tool-jobs` 向会话注入通知，Agent 据此决定下一步 |
| 失败恢复（`*_recover`） | `retry(task_id, { consent })`；`consent` 沿用现有 `userRequestedRetry` |
| 会话复用 | 现有 `reusableTask` 保留在提交路径上，命中时返回原任务，不提交新任务 |

`ctx.jobs` 的记录只在内存里，Harness 重启后等待句柄会丢失，但任务本身由任务驱动继续执行；Agent 仍可以用 `call_tools_job_status` 查询结果。

### 7.3 Service（Server / 项目服务）

- 从项目数据构造任务，按顺序提交到项目泳道；
- 注册自己的回写处理器（例如镜头、锚点），在处理器中幂等地更新项目数据；
- 自己管理版本、采用；合成成片属于非算力操作，由 Service 单独处理，不进入任务驱动。

## 8. 崩溃一致性

| 崩溃发生在 | 残留状态 | 恢复方式 | 是否重复计费 |
| --- | --- | --- | --- |
| 写任务记录前 | 无 | 提交方重试 | 否 |
| 任务记录已写、Job 未建 | 只有任务记录 | 对账补建 Job（`pending`）并补回索引；或提交方重试时补齐 | 否 |
| Job 已建、未进索引 | 任务记录 + `pending` Job | 对账按 `seq` 补回索引 | 否 |
| 已进索引、未派发 | 正常 | 驱动接着派发 | 否 |
| `launch` 中途 | `queued` 或 `failed` | 现有启动锁 + `worker.lock` 判定；失败等待人工重试 | 否 |
| 平台已收到、本地响应丢失 | Provider 提交记录 | 现有机制找回原任务，禁止重发 | 否 |
| Worker 进程死亡 | `running` 但无进程 | `getJob` 投影为 `failed/WORKER_NOT_RUNNING`，驱动继续下一个任务，等待人工重试 | 重试前不会 |
| Harness 退出，任务仍在执行 | 正常 | Worker 继续运行，驱动重启后继续观察 | 否 |
| 已结束、未结算 | 无 `settled.json` | 下一轮结算 | 否 |
| 已结算、未移出索引 | 条目残留 | 下一轮清理 | 否 |
| `driver.json` 损坏或丢失 | — | 从 `tasks/` + `jobs/` 重建，接着上一次继续 | 否 |

## 11. 安全

- `task_id`、`lane_id`、`submission_id`、`project_id` 在拼接路径前按正则校验。
- `binding` 限制大小，只原样保存和回传。
- Session ID 和 call ID 只以哈希形式出现在泳道 ID 和 `submission_id` 中，原值只保存在 0600 的 `runtime/calls` 中。
- 任务记录、驱动索引和 `status.json` 中不保存凭据或本机绝对路径（R7）；后端快照仍只存在于 `input/backend.json`。
- `projects/tasks`、`projects/jobs`、`runtime/driver.json` 都是恢复状态，不是可以清空的缓存。
