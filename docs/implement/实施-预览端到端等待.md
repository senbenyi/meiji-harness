## 调用链与修复

`workflow_generate_video.execute → startVideoJob → createJob/launch → video-worker → executeComfyVideo → prepareComfyWorkflow → ComfyClient.validate → submitComfyPrompt → ComfyClient.wait → collectVideoArtifacts → status.json → waitJob → 工具返回`。

- 两次旧 T2VA 图均有18种节点。原 validate 按4个一批，共5批；每批最慢请求结束前，其他空闲通道不能处理下一批。现在仍限制最多4个并发请求，但完成一个就补下一个；失败后停止补位，等待已发出的请求结束后抛出原错误。没有节点 schema 缓存，也没有省略校验。用阻塞首个请求的测试验证后续节点仍能推进。
- 提交去重日志、原 prompt_id 恢复、提交响应丢失找回与失败重试授权规则保持原样。
- 远端仍为 history → 必要时 queue → 等待2秒。已完成的 history 立即返回，不会再请求 queue 或等待。没有证据支持新增 WebSocket、改变轮询频率或重构调度。
- 本机 waitJob 仍每2秒读取状态，成功即返回。独立记录读取和等待耗时。
- 这条 T2VA 路径没有媒体上传、下载或本机解码。产物处理只检查最终 history 节点、构造服务器 URL 并保存 JSON 诊断记录。

计时在 jobs/timing.js 使用 performance.now。后台 timings 记录图准备、校验、HTTP 请求（含响应 JSON 读取）、提交、等待、按最近队列状态分类的 sleep、退避、输出检查及验证记录保存。工具返回的 tool_timings 覆盖工具入口到构造返回值前，包含任务启动和本机结果发现；不包含 Harness 页面显示、模型解释或浏览器媒体加载。后台阶段在 status/diagnostics JSON 中保留；工具阶段随工具结果返回，本次另保存 receipt.json。

各进程只计算自己的持续时间；不对本机与服务器时刻相减。嵌套阶段、并发 HTTP 请求与 GPU 执行会重叠，不能相加当作额外等待。记录采用每阶段聚合，保留次数、失败次数、总时长、最长耗时及最近一次起止偏移，不随轮询次数无限增长。
