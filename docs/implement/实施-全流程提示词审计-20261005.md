# 全流程提示词审计结果

本轮为测试与只读审计，没有新增生产代码修改。保留上一轮修复及工作区已有改动。结论：提示词入口已覆盖，但不能判定全部合理；真实模型仍有漏审、误判和复审事实优先级错误。

## 验证范围与方法

- 检查 11 个注册技能及实际 Model、接口、编译器、审核规则与输出协议。
- 从已有 27 个快照场景扩展，保存 141 份请求快照，另保存 5 个补充规则传递探针。
- 使用内存项目“旅人在庭院收好钥匙，听到三下敲击，本集不开门”，不修改运行项目或现有素材。
- 调用当前配置的真实文字模型 60 次：18 次生成/自动修订，42 次审核请求。审核中 1 次请求或解析错误，未保留足够错误信息，原因未确认；其余 41 次返回可解析判定。
- 真实模型测试为逐阶段独立样例，固定正确上游；不是把未经检查的前一阶段产物串入下一阶段。图片、视频本轮检查实际组装文本与引用模式，没有重新渲染每种媒体组合。
- `cd meiji && npm test`：687 项通过，0 失败、取消、跳过。该结果只证明现有程序回归通过，不证明语义自审可靠。

## 已确认问题

### F01 / P1：人物覆盖审核不可靠

大纲明确唯一出镜人物“旅人”，待审内容为 `{"items":[]}`。首次请求异常后，4 次有效重试中 **3 次通过、1 次拒绝**。这只是当前固定样例的小样本结果，不能外推模型整体漏审率。

证据：`characters-empty-retry.json`、`empty-character-repeats.json`。当前人物审核规则已有覆盖要求，说明仅写入一句规则不足以保证执行。应把出镜人物覆盖作为独立可观察的验收项，加入正反语义回归；不能把返回 `passed:true` 当成提取完整的证据。

### F02 / P1：复审把错误基稿重新提升为事实

大纲错误稿写“握着刚放进口袋的钥匙并提前开门”，修订意见要求消除持物矛盾和提前开门。修订稿保持门关闭，却被复审要求恢复错误基稿的持物细节；同时将“看向门缝”推断为提前演出开门。

证据：`generation-results.json` 的 `outline/revision`。审核意见明确写“物件状态必须与基稿确定的结尾一致”。应明确上游事实优先、修订意见指定的错误内容必须被替换；基稿仅约束未涉及的部分。不要要求错误基稿整体保真。

### F03 / P1：审核把偏好或推测当作阻断

- 人物审核否定“旅人”这个稳定身份称谓，而规则明确允许未命名人物使用身份称谓；提出的修改建议又允许保持“旅人”。还要求身份字段包含结尾动作，超出字段职责。
- 镜头表生成稿自审承认 10 秒可行，却因为“可能紧张”判失败，并要求起始状态直接到门前，跳过上游明确的走近过程。
- 人工正常人物样例含空 clothes/props，相关字段完整性意见可能合理，因此不将该样例的所有失败都算误判；仅列举有明确规则冲突的意见。

证据：`live-results.json`、`generation-results.json` 的人物和镜头表审核。应区分明确违约与可选建议，要求阻断意见引用上游与待审的冲突证据。

### F04 / P1：人物图年龄选择代码与规则正文脱节

`character-image-interface.js` 能选择“成年人物”“未成年或年龄不明”分支，但 `skills/task/generate-character-image-skill.md` 没有对应条件段。16 岁、年龄不明、30 岁三份实际请求都得到同一套裸上身/泳装规则。

证据：`requests.json` 的 `static-only/character-age/*`。仅检查文本，未发送这些年龄测试图片请求。应为未成年及年龄不明人物使用正常完整着装，并让规则正文与选择器一致。

### F05 / P2：人物图、场景图漏传项目风格

同一项目设为“手绘水彩”：文字请求与道具图请求包含该风格，人物图、场景图请求没有。证据：`expanded/character-image/generate`、`expanded/scene-image/generate`、`expanded/prop-image/generate`。

人物图刻意不带剧情服装/道具是源码明确设计，不单独当成漏传缺陷；问题是项目视觉风格未传递。

### F06 / P2：最终分镜审核引用了未提供的前镜依据

`review-text-storyboard-skill.md` 要求对照“前一镜已通过的最终提示词”；`storyboard-context.js` 明确不引入该内容，`text-storyboard-model.js` 又要求不要重审前镜。实际组合请求包含相互冲突的审核职责。

本轮正常/错误分镜对照均正确判定，因此这里只确认规则冲突，不声称该冲突本轮已造成错误结果。应按当前编译职责统一验收边界。

### F07 / P2：可保存的节点补充规则在部分流程不进入生成

`node-skills.js` 接受每秒指令和分镜节点。标记探针显示：大纲节点补充进入生成；`seconds:S01` 补充未进入每秒指令生成；`storyboard:S01` 补充进入编辑审核，却未进入编译文本；项目级 video.generate 补充进入最终视频请求。

证据：`additional-checks.json`。这是可保存配置与请求构建之间的差异；当前 UI 将节点专用入口主要用于剧情节点，不能把所有这些探针都说成已从 UI 实际操作。应统一支持范围：可保存的规则应落实到生成，或明确禁止不支持的节点。

### F08 / P2：数值约束仍依赖程序校验，语义审核不能替代

每秒指令生成稿合计 9500ms，目标是 10000ms，模型自审通过；同一稿交给生产 `validateSeconds` 后被正确拒绝。修订稿通过该校验。

证据：`generation-results.json`、`additional-checks.json`。这不是“错误视频已放行”的证据，生产校验已起作用。应保留程序硬约束，并让自动修订直接消费其准确诊断。

### F09 / P3：旧图片改写入口缺少审核事实

字符串 instructions 能进入生成任务，审核却不自动把原提示词和修改要求转为 facts；现有预览样例使用这种形式。本轮采用结构化 facts 的实际正反对照均通过。当前图片编辑主流程直接编辑原图，不调用这个文字改写路径；因此不能描述为所有图片编辑都无法自审。

## 规则合理性待决项

- 摘要审核要求无后集时以危机、新发现或关键抉择结束；若用户指定完整收束结局，会有冲突风险。本轮未用闭合结局调用模型，标为静态风险。
- 10 秒镜头表允许总时长 1–20 秒，这是提示词与当前程序一致的容差设计，不是漏传时长；是否符合产品预期需要单独确定。
- 输出协议要求所有实体引用完整标注，程序只对 action/camera/space/endState 扫描裸名字；summary/sound 等仅校验已有标记。需统一契约，不应仅通过增加重复提示词解决。
- 本轮英文只检查请求构建，没有逐节点真实英文生成；多人物多人对白、多集长剧情、全部指导素材组合、每种图片/视频实际输出尚不能据本轮宣布全部通过。
