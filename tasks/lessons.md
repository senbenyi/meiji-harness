# Lessons

- Prompt Snapshot 的内容身份不能包含全局 Project revision。并发 Worker 的心跳、兄弟任务或画布写入都会推进 revision，却不代表目标提示词或素材依据改变；revision 只保留为诊断元数据，失效判断必须由提示词、生成依据、参考资产、参数和工作流指纹共同决定。
- 用户已点名文件、范围并明确要求自动完成时，创建 Todo 后再次询问“是否启动”不是谨慎，而是违反执行授权。入口约束应明确成可验证的唯一工具序列 `todo_write → studio_novel_create`，并显式禁止确认工具。

- Harness 原生 Workflow 已可视化不等于自主生产已通过；真实验收必须证明同一根会话只接受一次请求并自动到 deliverable。动态结构化 Schema 还必须覆盖运行时退化形态（尤其 `oneOf` 只有 0/1 个分支），否则 Workflow 会在 `agent-start` 前失败，表面只看到空 Run。

- 已承担业务编排并继续派生子 Agent 的后台协调器，不能为了 UI 可见性直接改成 Harness depth=1 的真实 subagent；默认 `maxDepth=1` 会让它原有的下一层业务 Agent 变成 depth=2 而被拒绝。此类修复只补 descriptor/catalog 可见投影，保持原运行所有权、深度、随机 Session 身份和重试语义不变。
- 全局 Run 状态不能无条件插入每个阶段 tab；正常制作进度应由各阶段自己的摘要表达，全局异常只应在项目总览集中呈现。未经用户或既有产品结构支持，不擅自在所有页面增加重复状态横幅。
- 基础流程尚未通过时，失败 Pilot 快照、未验证 workflow、上游工具快照和已完成历史验收不应继续常驻工作树；保留 Git 历史即可，当前树只放实际加载链路、根因材料和下一次人工验收所需资产。
- 主流程尚未通过时，不保留“以后也许有用”的质检、探针或迁移脚本；用户选择全人工操作后，`scripts/` 应整体删除，避免未验证工具制造额外维护面和虚假安全感。
- 用户明确要求全部删除自动测试时，不应继续替用户保留“核心测试”例外；项目验证策略以真实页面、真实 provider、恢复过程和最终产物的人工验收为准。
- Pipeline manifest 声明 `retryOn: timeout` 不等于运行时已经支持超时恢复；验收必须制造真实超时并证明重试分支被执行。Workflow 调用超时应先由节点重试策略处理，只有达到 `maxAttempts` 才能把 Root Run 判为失败，不能在外层 catch 直接终止整条流水线。
- 稳定 ID、顺序和 sourceSpans 属于确定性控制数据；但每个镜头对应哪些 beat 是语义判断，不能由领域层按数组位置自动补齐，否则会制造“字段通过、内容未覆盖”的假验收。正确做法是先让剧本满足时长/镜头预算，再由模型提交语义关联、Schema 限定结构、validator 检查精确覆盖。
- Harness Workflow 的 structured_output 只支持受限 JSON Schema 子集；`minItems/maxItems` 会在 Agent 启动前被拒绝。数组数量只能用受支持的 description 提示，并由领域 validator 做最终强校验；不能因为标准 JSON Schema 合法就假设 Harness 可执行。
- 自动测试数量不是价值指标，也不是耗时根因的可靠代理。先按单项墙钟定位慢点；本项目真实主流程、页面交互和成片质量以 `3080` 人工验收为准，自动化只保留并发、幂等、原子持久化、路径安全、重复提交、DAG/checkpoint 和入口门禁等难以手验的隐藏不变量。
- 用户要求“压缩、合并、归档、删除”时，不能用新增索引和移动目录代替实际减量。计划必须先给出可验证的文件数/字节数目标，逐主题把独有结论收敛到 canonical 文档，并实际删除已被吸收的源文件；归档只解决活跃区噪声，不等于合并或删除。
- “最终成片质量通过”只证明产物质量，不证明生产流程自主验收通过。若过程中由 Codex 反复调用入口、恢复状态、热修代码或补齐数据，该运行只能作为故障诊断样本；修复后必须以“运营单次 UI 发起、Codex 零运行时介入”的全新运行重新验收。
- “新聊天”不等于“新 Project”。小说入口的幂等键若只含 workspace、正文 hash 和生产参数，会让新会话静默复用旧的污染项目；入口幂等必须限定在同一运营会话，跨会话重做应创建独立 Project/Run。

- 端到端验收一旦出现节点失败或主 Agent脱离唯一入口，立即停止会话并把该次结果判为失败；不能继续探索后再把局部成功当成流程通过。
- `file:` 插件更新不能以 `Already up to date` 作为已重装证据；必须验证安装目录入口可 import，必要时先 remove 再 `add --force`，并以宿主重启日志无加载错误为准。
- 重新发起 Harness 会话前区分“会话干净”和“Project 持久状态复用”；验收报告必须明确当前验证的是全新任务还是恢复路径。
- Pipeline manifest 的角色、Schema、Prompt 或校验契约发生变化时必须提升 `version`；否则恢复会复用旧任务快照，形成新 Prompt 与旧角色/状态混跑。
- 能从稳定输入确定的数据（例如按 `beatIds` 推导的全文连续 `sourceSpans`）应由 Harness 计算并校验，不能继续依赖模型按 Prompt 精确计算坐标。
- 文本 Workflow 的“恢复状态”与“重新调度执行”必须是同一个后端动作。只把 failed/blocked 改回 ready、再期待新聊天遵循 Skill 调用入口，会留下 active 但无人消费的任务；画布重试必须能唤醒持久执行器，不能依赖 Prompt 纪律。
- 对可能触发模型无结构输出的正文节点，确定性降级只能复用正式领域中已知且在剧本中有精确名称证据的资产；不得用模板或猜测补齐。降级结果仍必须经过同一 Schema/业务校验和物化门禁。
- 用户要求增强 Harness Workflow 时，不能把问题泛化为自建通用调度平台。先围绕 AI 短剧固定阶段复用 Harness 编排，只补最小的阶段检查点、失败恢复和画布投影；Root/Attempt/Outbox/Fencing 等平台化概念只有出现明确故障证据且现有 Harness 无法承担时才引入。
- 完整流程验收必须在执行前冻结样本、阶段、机器断言、证据目录和修复上限。只允许有限的 Happy/Recovery 场景；同一根因达到两轮修复上限就交付 `BLOCKED` 报告，不能用持续补丁和局部进度替代最终交付。
- 用户明确要求通过 `http://127.0.0.1:3080/` 验证时，代码测试和 smoke 只能作为辅助，不能替代真实页面操作。必须在该页面创建/恢复流程、观察阶段状态并验证最终产物；页面连接中断本身就是 Gate 0 失败，先恢复服务再继续。
- 设计快速 Pilot 前先确认唯一入口能够表达 Pilot 范围。若入口只支持整书，就应准备一个独立的小源文件作为完整输入，不能要求“整书唯一入口”同时执行局部 1 集/2–3 镜头，否则会诱导模型走底层工具并使验收契约自相矛盾。
- Manifest 声明的 provider 上限必须在 graph compiler 和引用选择两侧同时执行；Prompt 中写“最多 8 张”不能阻止执行器实际注入 `ref_image_9`。真实 provider 验证是这类契约的完成门槛。
- 确定性的运输步骤（镜头顺序、taskId、hash、concat、deliver）不能要求 LLM 原样回显后再校验。模型只负责创作判断；机器不变量由 Worker/Schema/领域校验直接持有。
- 画布阶段总数必须来自当前完整生产 DAG 的 required set，不能简单统计所有已创作实体，也不能只统计未缓存的 render-reference 任务；否则离屏角色会制造 99%，缓存命中又会漏计。
- Deliverable 是否有效应由文件、hash、时间线和所引用的批准资产判断。无关资产 rework 改变 project.status 时，不应把仍然有效的正式成片降级为“待制作”。
- 业务阶段不能由某个同名文本 barrier 或 ProductionTask 完成数推断。`asset-commit` 只代表资产结构与提示词已物化；只有当前签名的必需参考图全部 approved，资产阶段才算完成。调度、领域门禁和画布必须共享同一阶段验收谓词，前序未完成时后续任务不得创建，不能只在 UI 隐藏。
- 分镜的角色／场景绑定应只保存稳定的语义键 `kind + entityId`；当前参考图属于实体状态，必须在校验、Prompt 编译和媒体执行时统一解析 `entity.referenceAssetId`。不能要求模型或分镜规划复制 `assetId`，否则“先完成资产、后创建分镜”必然产生已批准素材被误判缺失的时序缺陷。
- 资产变体会在最终可见引用中覆盖角色／场景本体，但不能因此从绑定完整性校验中消失。完整性必须检查原始语义绑定，媒体引用与图片有效性才检查本体/变体去重后的可见绑定；两种集合不能混用。
- “提示词尚未编写”“分镜图尚未生成”在对应阶段尚未失败时只是正常未完成状态，不能投影为红色错误。画布只应把实际处于 `blocked` 的业务阶段问题显示为错误。
- 用户反馈“字体整体不合理”时，要先确认问题是否仅指字号；若是，只建立清晰的字号层级并全页面统一，不能顺带改字体、字重、颜色或布局。
- 项目名称不能直接复用为内容卡片的类型标题；卡片标题应表达内容类型，具体文件名与计数应合并为次级信息，且避免再用同义区块标题制造重复层级。
- 卡片使用 CSS Grid 时必须显式定义内容区的网格位置；依赖自动排布会把后续正文落入图片窄列，制造大面积空白和异常纵向拉伸。状态、说明、媒体与操作应先按阅读顺序成组，再考虑状态配色。
- 首次生产与重新生成必须是不同语义；动态扩展 DAG 的 `completed/total` 只能用于内部诊断，不能直接当作运营进度。运营界面应展示稳定业务阶段、当前动作和可解释的制品子计数。
- 资产提示词任务已经推进时，画布不能等到 `asset-commit` 后才展示正式实体；当前文本 Run 的任务进度和已知实体骨架必须进入同一读模型，逐项说明提示词、参考图和当前动作，同时保持业务资产总数与内部任务进度分离。
- 修复后台生产的计划／Subagent 可见性时，默认只补会话目录和只读投影；不得为恢复 UI 而改变 Durable Worker 生命周期、前台阻塞等待、ProductionRun 所有权或重试语义。可观测性事件必须与业务命令解耦，并验证不会重复创建或执行任务。
- 校验失败后的模型重试若只传错误、不传失败候选，却要求“修正现有 JSON”，新 Agent 实际只能从零重写并可能修一处退一处。重试应携带上一版候选和精确错误，要求保留其余字段做局部修正；不能用增加尝试次数掩盖上下文丢失。
- Harness 结构化子 Agent 即使实际只开放 `structured_output`，继承的全局系统上下文仍可能诱导模型幻觉调用未开放工具；当 Workflow API 无法强制 `tool_choice` 时，正式剧本可用该集原文与已批准的 beat/sourceSpans 做无编造降级，但不能用模板补写事实。并行批次必须先持久化成功 sibling，再汇总失败并把整个 Run 收敛到终态，不能留下 `running/active` 残留。
- 分集资产提取返回的是增量，不是全量快照：衍生资产本体可来自本集或此前已通过的累计提取结果，但不能只来自故事分析临时设定；单集可以没有新场景，只有全集合并后才强制至少一个场景。确定性 fallback 只能复用有正式剧本证据的资产，或逐字采用明确场景标题，不能推断新的道具和衍生状态。
- 用户指出“子智能体、任务是黑盒”时，目标是对话层 Harness 编排可观测性，不是创作页业务阶段进度。必须优先让会话里的 Agent、Workflow、Todo、Tool Call 可点击、可追踪并显示依赖/耗时/重试/错误；业务 ProductionRun 只能作为关联信息，不能拿业务进度条替代编排执行可视化。
- Harness 已内置 Workflow Run / Subagent 的持久事件和会话 UI 时，不得在业务插件中另造 Execution Graph、轮询 API 或新视图。先检查业务编排是否因后台 Worker、自建协调会话或嵌套 tool 调用而绕过了 Harness 顶层 workflow 事件边界；修复应优先让内置能力获得真实执行事实。
- 用户要求提高整体空间利用率时，应只统一收紧布局容器、区块和卡片的 margin、padding、gap，并先排查正文默认 margin 与容器 padding 的叠加；不能顺带改字号、颜色、内容结构或业务逻辑。
- 用户要求"从架构角度重构"时，不能先给目录拆分或新增 DDD 概念层的方案，那样只会让代码更复杂。动手前必须先读 `tasks/lessons.md`、`tasks/todo.md` 的历史决策和 `docs/research` 的最新分析，再盘点已安装 Harness 的真实能力，先回答三件事：核心模块、真实流程、哪些能力在重造 Harness。重构方向优先做减法，把通用能力交还 Harness。不得推荐用户已明确删除的自动测试作为安全网。
# 参考图预算必须端到端使用同一规则（2026-10-07）

- 工作流 manifest 的 `refs.max` 不只是提交器参数；Prompt 编译与一致性校验必须对所有图像、视频 capability 使用同一裁剪函数。
- 如果提交器裁剪而编译器仍校验完整绑定集，超过上限的镜头会确定性失败，看起来却像模型或素材偶发错误。
# 单次 E2E 成功不能表述为流程稳定（2026-10-07）

- 一次 clean-room 自动到成片只证明 happy path 当前可用，不能证明可重复性、故障恢复和并发稳定性。
- 汇报必须区分：`链路打通`、`基础验收通过`、`稳定性验收通过`；只有连续多轮、无人工干预、无残留任务且恢复场景通过，才能使用“稳定”。
- 页面或 Harness 仍有非终态显示、revision conflict、内部重试等证据时，必须作为未关闭风险明确列出，不能被最终成片掩盖。

# 断言"缺某能力"前要扫全部注册处（2026-10-08）

- 曾只 grep `lib/index.js` 的工具名就断言"主 Agent 读不到项目结构"，实际 `lib/domain/tools.js` 已注册 `studio_project_get`、`studio_production_status`、`studio_shot_list` 等 32 个工具。
- 规则：判断工具/能力是否存在，先列出所有注册入口（`makeTools`、`domain/tools.js`、`script/tools.js`、hooks、skills）再下结论；结构上用唯一工具清单（S7）消除这类盲区。
