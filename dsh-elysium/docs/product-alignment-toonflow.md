## 四象限分类

### 必须补齐 — 缺了产品流程跑不通

| 功能 | 理由 |
|---|---|
| 导演：分镜场景拆解 | 从剧本到画面的核心桥梁，没有它无法正向生产 |
| 导演：镜头分解（机位、走位、时长） | 直接决定视频 prompt 质量，当前靠人工或反推补齐 |
| 角色档案生成 | 角色图生成能力已有，缺少从剧本自动提取角色描述的上游 |
| 提示词正向生成 | brain 只做反推，正向生产时无自动 prompt 生成链路 |

### 值得做 — 显著提升质量/效率

| 功能 | 理由 |
|---|---|
| 导演手册（风格偏好存储） | 低成本，一个 YAML/JSON 即可，保证多 episode 风格一致 |
| 角色一致性正向锚定 | 当前 anchor 帧是反推产物，正向生产需要独立的一致性方案 |
| 场景转场设计 | 提升长视频连贯性，可在 block JSON 层面增加转场标注 |
| 故事骨架生成 | LLM 擅长的任务，投入小收益大 |
| 批量资产生成 | factory 框架已有，补并行调度即可 |
| TTS 配音 | 成熟外部 API（如 CosyVoice），集成成本低 |

### 不需要 — 架构/场景不适用

| 功能 | 理由 |
|---|---|
| Web UI / 画布编辑器 | llm-ai-veo 是 CLI + Harness 驱动的管线，非桌面应用产品 |
| Electron 桌面端 | 同上，非面向终端用户的产品形态 |
| SQLite 项目数据库 | 当前用文件系统 + JSON 契约管理产物，够用且更透明 |
| 多语言 UI 本地化 | 无 UI，不适用 |
| 付费卡点规划 | 运营层面功能，不属于生产管线 |

### 代价太大 — 放弃或等外部方案成熟

| 功能 | 瓶颈 |
|---|---|
| 角色衍生状态（换装/变身） | 需要精细 ControlNet 或 IP-Adapter，当前模型不支撑稳定输出 |
| 逐帧编辑 & 时间线合成 | 需要完整视频编辑器，非 CLI 管线能承载 |
| 三层 Agent 自治架构 | 需要大量编排基础设施，当前 Harness Skill 模式足够 |
| 分镜质量审核（180 度线、连续性） | 需要空间推理能力，当前 VLM 不可靠 |
| 小说导入 & 事件图谱 | 完整 NLP 管线，与当前视频反推→生产的定位偏差大 |

## 导演模块专项分析

### Toonflow 的导演做了什么

1. **拆** — 剧本 → 场景列表（含情绪分、环境音提示、对白量）
2. **排** — 场景间转场设计（动作桥、情绪接力、空间连接）
3. **控** — 每场的机位、走位、角色空间关系、对白节奏（4 字/秒）
4. **存** — 导演手册，跨 episode 复用风格偏好

### 现有管线中隐含的导演能力

| 能力 | 位置 | 局限 |
|---|---|---|
| 42 锚点镜头描述（camera motion tag） | brain: `run_video_analyze.py` | 逆向分析，非正向创作 |
| 节奏重排（120 秒目标） | brain: `run_video_analyze.py` | 仅用于反推场景 |
| block JSON（7 × 6 video prompt） | brain → model | 数据结构可复用，内容来自反推 |

### 真正缺失的

| 缺失能力 | 说明 |
|---|---|
| 剧本→场景拆解器 | 输入文本剧本，输出结构化场景列表 |
| 场景→镜头 prompt 生成器 | 每个场景生成 camera angle、motion、duration |
| 风格一致性配置 | 面向镜头语言的偏好存储，非模型参数 |

### 最小可行导演方案（展开设计）

#### 设计原则

- 两阶段导演纪律（先忠实拆解、再分配画面）是正向生产的主线
- 不引入新基础设施，方法论用配置 + 提示词实现
- 产出直接进入插件的 `plan.json`（动态章节 × 6 锚点），无需中间转换

#### 整体流程

```
故事文本 + director-profile
        ↓
  [Producer Agent]
        ↓
  ┌─────┴─────┐
  │  第一阶段  │  故事 → 场景拆解
  │  scene     │  输出 scenes
  └─────┬─────┘
        ↓
  ┌─────┴─────┐
  │  第二阶段  │  场景 → 章节与锚点分配
  │  chapter   │  输出 plan (elysium-plan-2)
  └─────┬─────┘
        ↓
  Episode Orchestrator
  production-service
```

#### 实现状态：已落地并归位插件（2026-09-04）

早期实现在 `llm-ai-model` 仓库（`mvp-director` Skill + `director.yaml`，面向固定 12 镜的 `vmp-1`）。
业务能力归位后，该实现已从模型仓库删除，方法论与执行都在本插件内。本节只做导航，具体规则以对应
文件为准（避免和实现分叉后没人维护两份）：

| 组件 | 文件 |
|---|---|
| 导演配置 | `src/application/director-profile.js` |
| 两阶段提示词与校验 | `src/application/planning-service.js` |
| 方法论与红线（设计依据） | `docs/director-methodology.md` |
| 操作入口 Skill | `.dsh/skills/elysium-director/SKILL.md`（仓库根） |

**设计来源**：方法论蒸馏自 `/Users/mac/ai/Toonflow-app` 的真实技能包（`production_execution_director_plan.md` 导演规划、`production_execution_storyboard_panel.md` 分镜写入、`production_skills/storyboard_prompt_techniques.md` 提示词技法），不是本文档早期草稿里手造的字段。字段口径以此为准：台词条数/字数如实统计、情绪浓度 0-10、过渡先判断必要性再决定是否写（不为凑数硬造过场）、image_prompt 按首帧识别原则取静止定格态、同场景角色左右位置与朝向必须锁定。

**刻意偏离源项目的两处**（写在 `director.yaml` 文末）：
1. `image_prompt` 保留光影描述——Toonflow 靠场景参考图承担光影，本仓库每个 shot 只有 `cast.jpg` 角色参考，没有场景图，光影必须写进文本。
2. 不做 `@图N` 多资产编号绑定——Toonflow 有完整资产库，本仓库 MVP 只有单一角色一致性参考，没有绑定的落地对象。

**已验证**：`scripts/mvp/run_mvp.py --spec <episode.json> --stage check` 对 `examples/episode.example.json` 返回 `ok:true`；把 shots 砍到 11 个再跑，验证器准确拒绝（`shots 必须固定包含 12 镜`），证明校验真实生效。`check` 阶段只做结构校验和依赖文件存在性检查，不碰 GPU，符合 `llm-ai-model/CLAUDE.md` 的授权边界。

**验证清单**（`episode.json` 必须满足，已由 `run_mvp.py --stage check` 强制执行，非人工自查）：

| 检查项 | 规则 |
|---|---|
| schema_version | 必须为 `"vmp-1"` |
| episode_id | 匹配 `^mvp-[a-z0-9]+(?:-[a-z0-9]+)*$` |
| shots 数量 | 恰好 12，ID 连续 shot-01~12 |
| cast_prompt / negative_prompt | 非空字符串 |
| compliance | 四个字段全部显式为 `true` |
| image_prompt / video_prompt | 按 shot-assignment.md 的首帧识别原则、忠实性自检表生成 |

#### 不做的事

- 不生成音频/配音（独立模块，不属于导演）
- 不做 180 度线检测（需要空间推理，VLM 不可靠）
- 不管理角色衍生状态（依赖上游角色模块）
- 不自动执行 run_mvp.py（导演只产出 episode.json，执行由用户触发）
