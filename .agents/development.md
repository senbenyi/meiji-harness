# 开发流程

采用两步：**调研与计划 → 实施与验证**。项目职责、编码和数据规则见 [meiji-dev.md](meiji-dev.md)，档位按其第 11 节判定。

完整流程只要求一份计划和一份实施记录；调研结论合入计划，不再单独要求 `docs/research/` 文档。已有调研文档保留作历史线索。小改动只写简短计划，将验证结果回填计划，不另写实施记录。只回答问题、只做调研或只改文档不要求建立实施计划。

## 1. 调研与计划

本步不修改业务代码，改代码前写好 `docs/plans/{MMDD}-计划-{任务名}.md`。

文件命名：`MMDD` 为计划创建当天的月日（如 `1005-计划-基座能力接入.md`），按文件名排序即为先后顺序；之后修改计划不改文件名。实施记录使用对应计划的日期（如 `1005-实施-基座能力接入.md`）。

1. **明确规格**：写明一句话目标、非目标和验收标准（AC-1、AC-2…：给定输入/状态 → 可观测结果）。关键要求缺失或无法写出可验证的 AC 时询问用户，不用代码现状反推意图；继续不依赖答案的工作。
2. **取证并判定**：从实际入口追踪调用链，阅读源码、配置、运行产物或官方文档。已有文档只作线索。每条 AC 标「已确认」（附证据）、「未确认」（列缺口）或「未验收」（需人工验证）。需求歧义或重大决策交用户判断。
3. **形成改动计划**：每条改动写明仓库相对路径、函数或参数、当前 → 目标及对应 AC；同时写验证方法和预期结果。不对应任何 AC 的改动不做。

完整流程模板如下；小改动只保留类型、目标、改动、AC 和验证，不要求调用链与证据表。

```markdown
# {任务名}

- 类型：{新功能 / Bug 修复 / 重构 / 小改动}
- 目标：{一句话}
- 非目标：

## 验收标准与调研结论
| AC | 输入/状态 → 可观测结果 | 已确认/未确认/未验收 | 依据或缺口 |
|---|---|---|---|

## 调用链与证据
{入口 → 关键节点 → 问题点 / AC 判定点，含分支和失败路径}

| 来源（文件:行） | 支持的结论 |
|---|---|

## 问题
| AC | 预期 | 实际 | 根因 |
|---|---|---|---|

## 待用户决定
{没有写「无」}

## 改动
### 阶段 1：{阶段名}
1. `{文件}:{位置}` — {当前 → 目标} → AC-N

验证：{命令或人工步骤} — {预期结果}

## 验证结果
未执行。
```

## 2. 实施与验证

- 用户已提出实施需求时，计划完成后直接执行，不等二次确认；只有用户明确要求只调研、只出方案或等待确认时才停在第一步。
- 按计划逐阶段做最小改动，每阶段完成后运行对应测试，记录实际结果，不用配置或推断代替运行证据。测试要求按 `meiji-dev.md` 第 14 节执行。
- 计划与代码不符时，按源码证据补充或修正同一份计划，再继续；不扩大需求范围。
- 只有缺少无法推断的关键信息或需要超出授权时才暂停，说明发现、已完成的改动和需要的决定。
- 完成后核对每条 AC，回填计划的「验证结果」。全部 AC 通过才完成；存在缺陷时返回第一步补证据或调整计划，再实施验证。

完整流程写入 `docs/implement/{MMDD}-实施-{任务名}.md`（日期与对应计划相同）：

```markdown
# {任务名}实施记录

## 已修改文件
- `{文件}` — {改动摘要}

## 验收标准核对
| AC | 状态 | 验证方式与证据 |
|---|---|---|

## 测试
{基线与改动后的通过、失败、取消数；新增失败项及原因；未执行的验证明确标注}

## 人工待办
{没有写「无」}
```
