# meiji 后续任务开发指引

本文用于指导后续生成任务的新增、修改与重构，以摘要和剧情的现有实现作为参考。目录职责见 `architecture.md`，开发流程与强制规范见 `development.md`。

文本分镜直接使用已通过的每秒指令，由一个 Model 转换输出结构并绑定多模态引用。基础 skill 只约束忠实转写、素材用途和引用关系，角色、声音格式及输出协议写在 Model。生成、修订与人工编辑审核共用本镜资料，只核对转写差异和绑定，不重审上游创作或整集剧情。固定图片编号与素材快照，补充按当前集 `storyboard:Sxx` 保存；视频提交前校验模式与引用，按快照顺序读取本地图片转 Base64。

## 1. 按职责修改代码

| 位置 | 应放置的内容 |
|---|---|
| `server/flow/operations/` | 操作入口、前置条件、步骤计划及结果保存协调 |
| `server/generate/` | 执行生成与审核、解析和校验模型结果 |
| `server/prompts/models/` | 当前任务的输入结构及最终提示词组装 |
| `server/prompts/interfaces/` | 为 Model 选择技能、约束、输出协议 |
| `server/generate/gateway.js` | API 请求与响应处理 |
| `server/data/` | 项目、任务、步骤和内容快照的持久化 |

不要在网络层或页面中另行拼接业务提示词。页面与会话工具复用同一操作流程。

## 2. 为生成任务设计提示词 Model

- 按独立生成目标设计 Model，字段只包含该任务需要的资料、参数、规则及意见。
- 通过代码给 Model 赋值，由 Model 提供最终提示词组装函数；Model 不调用 API、不保存项目。
- 生成、按意见修订和审核分别提供入口，复用资料结构，不混用执行指令。
- 输出语言由代码读取配置、校验并确定默认值，提示词直接指定本次生成语言；不要求模型读取 outputLanguage、选择默认语言或根据输入推断。
- 在提示词中明确岗位职责；文本请求区分 `system` 规则与 `user` 资料，图片请求按接口要求输出完整 `prompt`。
- 同类步骤共用一个 Model，差异写成配置（剧情四类用 StoryModel/storyKinds，镜头与提示词改写用 TextStepModel/textSteps）；请求结构统一由 request.js 组装，不在各 Model 内重复摆放顺序。
- 任务资料以结构化对象 `{ task, review, facts }` 传入，不拼接大段文本再解析标记；审核使用 review 审核目标与审核 skill，不复用生成指令和生产规则。
- 提示词预览复用实际组装入口，避免预览与提交内容不同。

参考：`episode-summary-model.js`、`story-model.js`、`text-step-model.js`、`request.js`。

## 3. 拆分任务步骤

可以独立调用、审核或保存的工作，应设计为独立步骤；后续步骤使用本轮最终结果。

剧情大纲始终依据当前本集摘要生成，重新生成只排除旧大纲和历史意见。生成与修订将任务、目标合为「本次任务」，随后放本集摘要及参数（时长、项目风格）；项目摘要与剧本作背景参考，前后集作衔接，不能替代本集摘要或提前演出后集事件。审核独立编排，核对同一份本集摘要。

角色区只写身份。本次任务只说明依据和要做什么，可引用基础规则、补充规则；具体约束放在规则区，返回格式放在输出协议，避免在任务中重复。大纲当前节点补充 skill 统一进入「补充规则」，审核时仅作为验收依据。

摘要按同一分区原则编排：角色只写分集编剧；任务说明依据项目摘要、剧本生成或修订指定集摘要；user 分开提供项目摘要、剧本、参数（用户时长、项目风格）和前后集资料。语言、基础规则、summary 节点补充规则与输出协议放 system，跨集衔接和悬念要求不在资料区重复。首次、重新生成、修订、审核与预览共用这份编排，时长保持用户设定值。

例如剧情流程分为大纲、人物提取、场景提取三个目标，各自调用模型，前项未通过时停止后项。

需要文本自审的任务复用 `text-steps.js`：

```text
生成 → 自审 → 不通过时自动修订一次 → 复审
```

步骤通过 `runStep` 记录，任务状态从步骤推导。图片、视频等任务按实际工作拆分，不机械套用文本审核流程。

## 4. 明确修改范围

- 重新生成使用本次指定的上游资料，不沿用当前目标的旧稿与历史意见。
- 按意见修订必须提供基稿和本次意见，只修改受影响内容及必要关联。
- 自动修订使用本轮失败稿和审核意见；复审重新检查最新结果。
- 下游提取使用最新上游结果，不自动继承上游的修改意见。
- 修改成功后清理已提交意见，失败保留；不能清除任务执行期间新输入的意见。

## 5. 节点页面的开发要求

| 入口 | 要求 |
|---|---|
| 查看任务历史 | 每个操作处都提供入口，进入当前操作的任务列表，再进入单个任务查看步骤详情 |
| 人工输入意见修改 | 保存当前节点的意见，提交时携带最新基稿和本次意见；修改成功清理已提交意见，失败保留，新输入不被旧任务清除 |
| 查看 skill | 基础 skill / 补充 skill 两个 tab，默认基础；补充整段编辑保存 |

道具卡标题旁提供“删除道具”按钮，支持人工删除当前剧集的指定卡片，删除任务保存到历史；当前阶段暂不处理下游内容，素材库文件保留。

每个有生成或开发约束的节点，都必须提供独立的「查看 skill」及补充 skill 管理入口，不能只在上层页面提供一个统一入口。例如剧情页面下的**大纲、人物角色、场景**三处，都要分别支持查看基础 skill、查看补充 skill，以及增加、修改和删除本节点的补充 skill。各入口只展示和使用当前节点对应的约束与补充内容。

每个实际操作所在位置都必须提供「查看任务历史」入口，默认按当前项目、剧集、节点及操作范围展示，页面层级为：

```text
操作处的「查看任务历史」 → 任务列表 → 单个任务的步骤详情
```

剧情页的大纲、人物角色、场景卡片没有独立生成操作，只保留各自的「查看 skill」，不重复设置任务历史入口；统一在顶部剧情生成操作处查看任务历史。人物和场景详情页的生图操作仍保留任务历史入口。

任务详情复用现有步骤信息，显示步骤顺序、状态、审核意见、失败原因和起止时间，并保留内容快照及完整实际提示词的查看入口。

当前任务必须支持状态的响应式更新，复用服务端事件推送与任务查询机制，无需手动刷新即可看到任务状态、正在执行的步骤及后续步骤状态。当前步骤明确高亮，步骤开始、完成、失败或跳过后及时更新；任务结束后显示最终结果。

节点标题与辅助操作放在同一标题区：「查看任务历史」「查看 skill」放在标题旁，或与其他按钮组成一行，不为每个辅助入口单独占一行；窄面板允许整组自然换行。

新增项目、新增剧集、编辑、提示词查看和素材预览等弹窗只在短剧面板范围内展示与遮罩，不遮挡、模糊或锁住 Harness 会话区。复用 `showPanelDialog`，支持取消及 Esc 关闭；多层弹窗只关闭最上层。

人工修改意见用于本次修订；补充 skill 是节点持续使用的生成要求，两者分开保存和组装。

## 6. 基础 skill 与补充 skill

- **基础 skill**：当前任务对应的约束文档（`skills/task/`），作为提交给 AI 的基础要求展示，不由节点补充内容覆盖。
- **补充 skill**：支持人工输入、增加、修改和删除；仅对当前剧集的当前节点生效，切换剧集或节点时读取各自内容，不继承上一处内容。
- 组装时由当前接口选择基础文档，读取当前节点补充内容，再交给 Model 一起组装；预览与实际请求使用同一份资料。
- 补充要求应用于该节点的生成和修订，审核时仅作为验收依据，不让审核执行生成指令，也不能覆盖输出协议。
- 任务开始时固定本轮使用的 skill 内容；编辑补充 skill 对后续任务生效，任务历史保留实际使用版本。

补充 skill 保存到**每集的数据 JSON**，按节点键区分。建议结构：

```json
{
  "supplementalSkills": {
    "summary": [{ "id": "s1", "content": "结尾保留与当前冲突相关的悬念" }],
    "outline": [],
    "characters": [],
    "scenes": [],
    "storyboard:S01": []
  }
}
```

节点键复用任务中的目标标识；具体人物、场景或镜头也应各自区分。增删改请求必须校验项目、剧集和节点归属，只修改对应集合，不影响其他节点。

**当前范围**：摘要、大纲、人物、场景已支持节点补充与独立入口；其他节点新增或修改时按同样规则实现。旧的摘要/剧情项目补充使用 `scripts/migrate-node-skills.js` 备份迁移，新剧集不继承。所有提交给生成模型的内置 skill 统一存放在 `skills/task/`，每个功能只保留一份基础生产规则；`skills/session/` 只用于 Harness 会话操作。

## 7. 保持结果与状态一致

- 输出协议、解析、校验和保存结构一起修改；程序管理 ID、路径与素材关联。
- 格式有效的草稿按阶段保存，审核失败保留内容和意见；接口或格式错误不覆盖旧内容。
- 节点即使尚无可用正文，也必须显示本轮执行或自审失败原因；未发布草稿在任务历史查看，无可用正文时禁用提交修改和人工放行，保留重新生成入口。
- 后续失败不能抹掉已经通过的阶段；更新上游时复用现有下游清理与素材保留规则。
- 使用现有提示词快照机制，让实际请求能在任务步骤中查看，不用当前资料重建历史请求。

## 8. 每次修改的检查项

1. 先读架构与开发规范，按要求完成调研和计划。
2. 确认影响的输入、Model、接口、步骤、保存逻辑与调用方，同时核对节点的任务历史、意见修改和 skill 入口。
3. 验证相关生成、修订、审核及失败路径，测试范围遵循本次用户要求。
4. 修改后端后重启 Harness，刷新页面，确认实际运行服务已加载新代码。
5. 同步必要文档；代码修改完成后按仓库要求集中更新 GitNexus 索引。

查看 skill 页面顶部仅保留返回键和标题，正文使用「基础 skill」「补充 skill」两个 tab，默认选择基础。基础全文只读；补充只使用一个整段文本框和保存按钮，不展示逐条列表或增删按钮。切换 tab 保留编辑草稿，空文本保存清空补充。旧条目按顺序合并显示，整段保存原子替换为一条，沿用现有数组结构。移除提示词预览、输出协议、分区导航及解释文案。失败保留输入，读取失败可重试；实际请求提示词在任务步骤中查看。

每个需要大模型参与的步骤对应独立编排 Model。一个功能只使用一份基础生产规则，生成与审核共用，修订增加基稿及意见；角色、语言、审核与修订的执行边界由 Model 代码决定。constraints 仅放按功能命名的平铺 Markdown，注册信息与输出协议在代码中维护，不保留独立通用、审核、修订、共享或指导 skill。

人物和场景图片统一在各自详情编辑页生成、按意见重绘和确认，列表只提供详情入口。已有候选图在列表提示进入详情，不再使用独立图片生成/确认页；铅笔分镜保持自身流程。生图标题旁并排放置查看图片任务历史、查看对应基础 skill 的入口，附属素材生成也需要这两个入口。图片历史使用当前剧集范围，进入任务后查看步骤和实际提示词。

基础 skill 文件统一放在 `skills/task/`，文件名以 `-skill.md` 结尾。正文只写可直接提交大模型的任务要求、条件与约束，不写展示标题、skill 用途介绍或程序分工说明。条件必须写成明确执行句，不能因删除标题而丢失适用范围；身份、配置读取与提示词编排由 Model 代码处理。


约束文件统一使用小写 kebab-case「动作-对象-skill.md」：生成用 `generate-`，提取用 `extract-`。例如 `generate-shot-table-skill.md`、`extract-story-characters-skill.md`。文件名描述主要职责，生成、审核和按意见修订仍由同一 Model 编排并共用基础正文；改名只更新 catalog 和引用，不改变运行时 skill ID。

不创建独立 revise/review 约束文件。单镜修订复用 `generate-shot-table-skill.md`；指定镜头、基稿、意见、编号时长与修改范围由 ShotRevisionModel 编排，审核对照同一生产规则。

图片提示词改写没有独立基础 skill：保留原主体、限定外观修改、禁止编造素材等由 ImagePromptModel 编排。生成、审核、修订不是新增基础文件的理由；仅真实生产功能维护约束正文。

skills 目录分为 `task/`（具体任务 skill）和 `session/`（会话 skill）；不再使用旧目录名。保留 catalog.js、load.js、protocols.js，分别负责映射、加载校验、输出协议；只有 session 内容注册到 Harness 会话，task 内容经 Model 编入实际请求。

提示词分工：Model 明确“根据哪些输入完成什么任务”，单列当前资料、实际提供的上下文、基础约束、节点补充、修改意见及输出结构。基础 skill 只写生产规则，避免重复任务模式、接口协议和程序说明。输出结构必须保留可读的小节、段落与换行，保存和页面展示使用同一份正文。

提示词按本次任务、上游事实、衔接上下文、基础与补充规则、基稿与意见、输出结构组织，空上下文省略。生成、修订、审核读取同一组任务事实与规则；输出协议只涉及当前步骤。人物图首次生成、参考生成和意见修改都经人物图 Model，画幅由调用方赋值。

可确定的输出格式与时长由程序校验，校验结果必须参与步骤结论和自动修订。失败保留有效草稿；审核只报告有具体证据的问题，按受影响镜头编号保存，全集意见去重。大纲使用独占一行的小节标题及真实换行；人物提取只建实际可见身体卡，场景提取只描述无人物环境。
